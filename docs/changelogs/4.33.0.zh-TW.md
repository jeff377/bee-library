# Bee.NET 4.33.0 — 詳細變更說明

[English](4.33.0.md) ・ [繁體中文](4.33.0.zh-TW.md) ・ [← CHANGELOG](../../CHANGELOG.zh-TW.md)

本文件是 [CHANGELOG.zh-TW.md](../../CHANGELOG.zh-TW.md) 中 `[4.33.0]` 條目的詳細版本。主 CHANGELOG 每項變更一行；本檔保留完整敘述——每項變更背後的**原因**、限制與設計脈絡。

> 存進資料庫的 `DateTime` 改由伺服端全權負責。`FormBusinessObject.Save` 不再採用呼叫端送來的 `DateTime`：新增列取伺服端的 UTC 讀數，既有列保留資料庫裡的值，`sys_insert_time` 與 `sys_update_time` 由框架戳記。有了這一層，Connector 不再把存檔的 `DataSet` 轉成 UTC，只轉過濾條件。運算式裡的「現在」依 `DataSet` 所在的那一側取基準；異動記錄改以 `DataSet` 回傳異動內容，也不再被過去會讓它失敗的值擊倒。**破壞性變更依 pre-stable 政策以 minor 發佈。**

## 破壞性變更

### `Save` 不採用呼叫端傳入的 `DateTime`

`FormBusinessObject.Save` 在 `EnforceWriteScope` 之後、`DoBeforeSave` 之前呼叫新的 `protected virtual NormalizeDateTimes`。對 `FormSchema` 宣告的每個 `FieldDbType.DateTime` 欄——`Date` 欄不處理：

| 列狀態 | 欄位拿到的值 |
|--------|-------------|
| Added | `sys_insert_time`、`sys_update_time` 與沒有 `DefaultValueExpression` 的欄位填入當次存檔的 UTC 讀數；有運算式的欄位清空，交給運算式求值 |
| Modified / Deleted | 兩個列版本都改成資料庫存放的值；修改列的 `sys_update_time` 再填入 UTC 讀數 |

修改或刪除的列若已不在資料庫中，存檔在任何寫入之前以 `UserMessageException` 中止。`UPDATE` 不再以 payload 覆寫 `sys_insert_time`。

**為何這樣改**：用戶端以使用者時區持有 `DataSet`，而 payload 裡沒有任何資訊說明一個值屬於哪個時區。過去由 Connector 在送出時轉回 UTC，而那段轉換的每一個缺口——DST 回撥時一個牆上時間對應兩個時刻、改寫時遺失修改列的其他欄位、繞過 guard 的過濾值——最後都變成資料庫裡的錯誤值。讓伺服端根本不讀這些值，是把整類問題拿掉，而不是逐一補洞。

這條適用於每一種呼叫端，包含在同一程序內呼叫 `Save` 的其他 BO。代價是使用者無法直接編輯 `DateTime` 欄位。需要接受呼叫端值的 BO 覆寫 `NormalizeDateTimes`：先讀出呼叫端的值，呼叫基底實作，再把值轉成 UTC 寫回。此時授權與寫入範圍檢查都已執行過。

**相容性**：`NormalizeDateTimes` 是純新增；行為變更影響每一張含 `DateTime` 欄的表單。詳見 [ADR-032](../adr/adr-032-datetime-timezone.md) 選項 5 與 D14。

### `IDataFormRepository.GetRowsByRowId`

明細列沒有現成的讀回方法，因此 `IDataFormRepository` 新增 `GetRowsByRowId(tableName, selectFields, rowIds)`，任一張表都以 `sys_rowid IN (...)` 分批讀回。`DataFormRepository` 提供實作。

**相容性**：介面新增成員，對直接實作 `IDataFormRepository` 的型別是原始碼與二進位破壞性變更。繼承 `DataFormRepository` 的型別不受影響。

### 請求方向不再轉換 `DataSet`

`PayloadZoneConverter.ToUtc` 改名為 `IsolateRequest`。`SaveRequest` 的 `DataSet` 只深拷貝、值不換算，事後還原呼叫端的實例；`GetListRequest` 的過濾條件照舊從使用者時區轉為 UTC。`DateTimeZoneConverter.UserToUtc(DataSet)` 與 `UserToUtc(DataTable)` 移除——留著等於替「伺服端不採用用戶端的 `DateTime`」開後門。

`SaveRequest` 的 `DataSet` 現在不論 session 有沒有時區都會複製。伺服端會就地改寫存檔的 `DataSet`，同程序呼叫時少了複製，改寫會落到呼叫端自己那一份。

**相容性**：對呼叫被移除或改名成員的呼叫端，是原始碼與二進位破壞性變更；框架內唯一的呼叫端是 `ApiConnector.ExecuteAsync`。wire 上 `SaveRequest` 的 `DateTime` 儲存格不再保證是 UTC。詳見 [ADR-032](../adr/adr-032-datetime-timezone.md) D3、D4 與 D14。

### `DateTimeBasis`：「現在」隨 `DataSet` 所在的那一側

伺服端的 `FormExpressionCalculator.ApplyFieldExpressions` 與 `ValidateRules` 以 session 時區求值 `Now()`，把得到的牆上時間放進以 UTC 表示的 `DataSet`：寫入的值、以及規則裡與儲存格的比較，都差一個時差。

新增的 `Bee.Base.DateTimeBasis { UserZone, Utc }` 把這件事定下來。「今天」一律依使用者時區；「現在」依它要放進的 `DataSet` 的基準——用戶端為使用者時區，伺服端為 UTC。新增 `FrameworkClock.Now(string, DateTimeBasis)`，並在下列方法尾端加上 `DateTimeBasis basis = DateTimeBasis.UserZone`：

- `IExpressionEvaluator.Evaluate` / `Evaluate<T>`
- `DynamicExpressoEvaluator.Evaluate` / `Evaluate<T>`
- `FormRowDefaults.Apply` / `DefaultForDbType`

`DataFormRepository.GetNewData` 與伺服端兩道 pass 傳 `Utc`；用戶端預覽傳 `UserZone`。

**相容性**：原始碼相容——既有呼叫端不需修改即可編譯。二進位不相容：以 4.32.0 編譯的呼叫端須重新編譯，`IExpressionEvaluator` 的外部實作須補上參數（編譯期即失敗，不會在執行期悄悄出錯）。`FormRowDefaults` 改用選用參數而非新增多載，是因為 `RS0027` 不允許在帶選用參數的既有多載旁新增參數更多的多載。詳見 [ADR-032](../adr/adr-032-datetime-timezone.md) D12。

### `AddColumn` 不再寫入時鐘預設值

`DataTableExtensions.AddColumn(name, FieldDbType)` 對 `Date` 與 `DateTime` 把建欄當下的 UTC 讀數存進 `DataColumn.DefaultValue`。這個值遮住了 `FormRowDefaults`（已有值的欄位會略過）：

- `GetNewData` 的 `Date` 預設值是 UTC 的今天，不是 session 時區的今天。
- `DefaultValue` 隨表格送到用戶端，用戶端新增的明細列拿到的是伺服端建骨架那一刻凍結的 UTC 讀數。
- `FormValueBinding.BuildEmptyDataSet` 建的空表同樣如此。

**相容性**：`AddColumn` 建立的 `Date` 或 `DateTime` 欄，`DefaultValue` 改為 `DBNull`、`AllowDBNull` 為 true。沒有經過 `FormRowDefaults` 的新列，該欄為 `DBNull`，存檔時由資料庫的 `NOT NULL` 約束擋下。Blazor 的 `InitializeNewMaster` 屬此類，其文件原本就註明僅供測試與離線預覽。

### `IGetChangeDetailResponse.DataSet`

介面新增 `DataSet` 屬性——見[新增](#getchangedetail-以-dataset-回傳異動內容)。

**相容性**：對在框架外實作 `IGetChangeDetailResponse` 的型別，是原始碼與二進位破壞性變更；框架內的兩個實作已補上。

## 新增

### `GetChangeDetail` 以 `DataSet` 回傳異動內容

`GetChangeDetail` 原本只回傳攤平的 `Fields`，呼叫端看不到主檔與明細的結構。回應新增 `DataSet`，三種事件共用：

| 事件 | `DataSet` 內容 |
|------|---------------|
| 新增 | `Added` 列 |
| 修改 | 帶原值的 `Modified` 列 |
| 刪除 | 刪除前的原單（`Unchanged` 列） |

`Fields` 照舊填入。沒有 schema 的舊 DiffGram、舊的 `DeletedRow` 標記、空白與損毀的 payload，`DataSet` 為 `null`；舊的刪除記錄照原樣回傳 `Deleted` 列，不另做轉換。`DataSet` 的 `DateTime` 值與 `GetData` 一樣換算成使用者時區；`Fields` 裡的時間字串仍為 UTC。

wire 合約新增 `dataSet?`，不認得此成員的用戶端會忽略它。詳見 [ADR-040](../adr/adr-040-audit-trail-taxonomy.md)。

### `DateTimeBasis` 與 `FrameworkClock.Now(string, DateTimeBasis)`

見[上方的破壞性變更](#datetimebasis現在隨-dataset-所在的那一側)。

## 修正

### 存檔修改列不再遺失其他欄位的修改

`DateTimeZoneConverter` 改寫修改列的原值版本時先呼叫 `RejectChanges`，而它會還原整列；事後只放回時間點欄的目前值，該列其他欄位的修改就被靜默丟掉。這與時區無關，任何含 `DateTime` 欄的表單在存檔時都會發生。轉換器現在在 `RejectChanges` 之前擷取整列的兩個版本。存檔路徑已不再執行這段轉換（見上方），回應方向保留這項修正。

### `DateTimeWireGuard` 移到時區換算之前

`ApiConnector.ExecuteAsync` 原本先換算過濾條件樹，之後才跑 guard。換算會先把 `Kind` 設為 `Unspecified` 再平移，所以登入後——只要有使用者時區——guard 看到的一律是 `Unspecified`，`Kind=Local` 的過濾值因此通過。這正是 [ADR-032](../adr/adr-032-datetime-timezone.md) D6 否決的「修正後放行」。guard 現在在換算之前檢查呼叫端交來的原值。

**行為變更**：登入後以 `Kind=Local` 的 `DateTime` 當過濾值的呼叫端，會從默默通過變成 `InvalidOperationException`。

### 經 `ToColumnValue` 寫入的時刻欄為定寬

`GridControl` 儲存格與兩個 head 的 `FormDataObject.SetField` 共用 `FormValueBinding.ToColumnValue`，它原本對字串原樣寫入，`"8:30"` 會破壞時刻欄「字典序即時序」的保證；只有 `TimeEdit` 與 Blazor 的時刻輸入自己補零。宣告為 `Time` 的欄位現在經 `CTimeString` 正規化為 `HH:mm` 寫入；無法解析的輸入擲 `FormatException`，儲存格因此與 `TimeEdit` 一樣保留前一個有效值。

### Blazor 時刻輸入保留前一個有效值

`DynamicForm` 的 `TimeEdit` 分支把 `CTimeString` 的結果直接交給 `SetField`，而 `CTimeString` 對無效輸入回傳空字串，打錯一個字（`"25:00"`）就會清空欄位。現在空白輸入寫回空字串、可解析的輸入正規化為 `HH:mm`、無法解析的輸入不寫入。輸入改用 `@bind:get` / `@bind:set`，被拒絕的輸入會被推回瀏覽器，而不是留著錯字。

### SQLite 表單讀回 `DateTime` 欄

SQLite 以文字存放 `Date` 與 `DateTime`，`DataFormRepository` 讀回的欄位型別是 `string`。`DateTimeZoneConverter` 只挑 `DataType` 為 `DateTime` 的欄，於是同程序（Local）呼叫讀回的表單時間欄不做 UTC 到使用者時區的換算。Remote 呼叫不受影響，wire 會依宣告型別重建欄位。

宣告為 `Date` 或 `DateTime` 卻裝 `string` 的欄位，現在換成 `DateTime` 欄並保留 `FieldDbType` 標記（`Date` 欄照舊不平移）。無法剖析的文字擲 `InvalidOperationException`；空字串讀成 `DBNull`。存檔時由驅動依參數型別格式化，與 Remote 呼叫一致。

### 稽核序列化失敗不再讓已 commit 的寫入回傳失敗

異動稽核在資料庫交易 commit 之後才序列化。欄位值含 XML 不允許的字元（例如貼入 U+0001）時，`AuditDiffGram.Serialize` 會擲例外：資料已寫入，API 卻回傳失敗、稽核沒記到、`AfterSave` / `AfterDelete` 與外掛被跳過。部署層的 `CreateApiKey` 更嚴重，金鑰已寫入卻交不回祕密段。

commit 後的整個稽核步驟改為 best-effort：失敗時記錄 log（prog id、作業名、記錄鍵，不帶欄位值）後照常完成。payload writer 也不再被這些值擊倒：控制字元與 U+FFFE / U+FFFF 寫成字元參照並讀回原值；CR 與 CRLF 不再被正規化成 LF；沒有任何 XML 表示法的落單 surrogate 換成 U+FFFD。既有稽核資料不受影響。詳見 [ADR-040](../adr/adr-040-audit-trail-taxonomy.md) 第六、八節。

### 刪除的異動記錄存完整原單

`Form.Delete` 以 `sys_rowid` 刪除，不經過 `DataSet`；刪除稽核卻把刪除前原單的每一列標成 `Deleted` 再寫成 DiffGram——而且是在共用的 `context.Snapshot` 上。稽核開啟時，讀取欄位的 `DoAfterDelete` 與 `AfterDelete` 外掛會擲 `DeletedRowInaccessibleException`；稽核關閉時同樣的寫法正常。

原單現在以新 root `AuditDeletedRecord` 原樣寫出，snapshot 只讀不改。`ChangeDiffGramReader` 依 root 分派，刪除事件產出的 `Fields` 與過去相同。既有的刪除記錄不遷移、照讀。詳見 [ADR-040](../adr/adr-040-audit-trail-taxonomy.md) 第十節。

**降版**：早於 4.33.0 的讀取端讀不懂新 root，會從新的刪除記錄讀出一筆無意義欄位；資料本身是完整的。

### `FieldDbType` 標記經 XML 讀回後仍有效

`DataSet.ReadXml` 會把 `msprop:Bee.FieldDbType` 註記還原成字串，而 `GetDeclaredFieldDbType` 原本只接受列舉值，XML 讀回的欄位於是退回以 CLR 型別推斷：`Date` 變 `DateTime`、`Time` 變 `String`。交給 `DateTimeZoneConverter` 時，這樣的 `Date` 欄會被當成時間點平移。方法現在也接受字串形式，但只採用與成員名稱完全一致的字串；數字字串、逗號清單、大小寫或空白不同者仍視為未標記。框架內唯一的 XML 讀回點（`ChangeDiffGramReader`）不讀標記，不受影響。

### 預設 `AuditRule` 表單的 `sys_insert_time` 為唯讀

`sys_insert_time` 與 `sys_update_time` 由 `Save` 戳記，宣告它們的表單一律標 `ReadOnly="true"`，預設的 `AuditRule` `FormSchema` 與 `FormLayout` 已補上。`FormField.ReadOnly` 只在產生版面時才抄到 `LayoutField`，既有的手寫或已產生的版面要手動補。

## 變更

### 文件搬入語言資料夾

公開文件搬入 `docs/en/` 與 `docs/zh-TW/`，以 `docs/README.md` 為語言入口頁；`docs/zh-TW/` 是源文件，其他語言為譯本。舊的 `docs/<name>.md` 與 `docs/<name>.zh-TW.md` 路徑已不存在，指向它們的連結需要更新。定位同時由 ERP 改為以表單為基礎的企業資訊系統，ERP 保留為複雜度基準。

### 套件圖示

NuGet 套件圖示更換。已發佈的版本保留原圖示。

### `apps/Bee.Northwind`

`AuditRule` 的 `FormSchema` 與 `FormLayout` 將 `sys_insert_time` 標為唯讀，與框架預設一致。

## 升級指引

**先升級伺服端，或與用戶端一起升級。** 4.33.0 的伺服端不採用存檔中的 `DateTime`，所以仍會把它們轉成 UTC 的舊用戶端照常可用。4.33.0 的用戶端不再轉換，而 4.32.0 的伺服端會把使用者時區的值當成 UTC 存入。session 沒有時區的部署不受影響。

**讓使用者編輯 `DateTime` 欄的表單。** `Save` 現在會取代該值：新增列為存檔時間，既有列保留資料庫的值。要採用使用者的值，在該表單的 BO 覆寫 `NormalizeDateTimes`：先讀出值，呼叫 `base.NormalizeDateTimes(context)`，再把值轉成 UTC 寫回。`Date` 欄不需處理。

**直接實作框架介面者**補上新成員：

```csharp
// IExpressionEvaluator
- object? Evaluate(string expression, IReadOnlyDictionary<string, object?> variables, Type returnType, string timeZoneId = "")
+ object? Evaluate(string expression, IReadOnlyDictionary<string, object?> variables, Type returnType, string timeZoneId = "", DateTimeBasis basis = DateTimeBasis.UserZone)
- T Evaluate<T>(string expression, IReadOnlyDictionary<string, object?> variables, string timeZoneId = "")
+ T Evaluate<T>(string expression, IReadOnlyDictionary<string, object?> variables, string timeZoneId = "", DateTimeBasis basis = DateTimeBasis.UserZone)

// IDataFormRepository (types deriving from DataFormRepository need nothing)
+ DataTable GetRowsByRowId(string tableName, string selectFields, IReadOnlyCollection<Guid> rowIds)

// IGetChangeDetailResponse
+ DataSet? DataSet { get; }
```

**被移除的轉換成員。** `PayloadZoneConverter.ToUtc` 改為 `IsolateRequest`；`DateTimeZoneConverter.UserToUtc` 沒有替代品，因為伺服端已不讀取存檔 `DataSet` 的 `DateTime` 值。

**以 `AddColumn` 建立的表格。** `Date` 或 `DateTime` 欄不再預設為當下時間。對這種表格新增列卻沒有經過 `FormRowDefaults.Apply` 的程式碼必須自行給值，否則存檔時會被 `NOT NULL` 擋下。

**已編譯的相依組件。** 呼叫 `IExpressionEvaluator`、`DynamicExpressoEvaluator` 或 `FormRowDefaults` 的組件必須以 4.33.0 重新編譯。
