# Bee.NET 4.30.0 — 詳細變更說明

[English](4.30.0.md) ・ [繁體中文](4.30.0.zh-TW.md) ・ [← CHANGELOG](../../CHANGELOG.zh-TW.md)

本文件是 [CHANGELOG.zh-TW.md](../../CHANGELOG.zh-TW.md) 中 `[4.30.0]` 條目的詳細版本。主 CHANGELOG 每項變更一行；本檔保留完整敘述——每項變更背後的**原因**、限制與設計脈絡。

> 本版的主軸是**宣稱與實作對不上**，而三條線各自來自不同的地方。散文那條：兩份 ADR 描述了一個從未兌現的好處，而沒有任何機制會發現。測試那條：多 provider 測試名義上覆蓋五家、實際全部打在同一家，把覆蓋改對之後兩個缺陷當場現形。診斷那條：壓測報告指名的場景未必是壞掉的地方——「GetList 100% 失敗」的真相是登入先炸。

## 安全性

### SQLite 上已過期的 API 金鑰照樣通行

`ApiKeyRepository` 以 `expiredAt is DateTime dt ? dt : null` 讀 `expired_at`。SQLite 沒有日期型別，驅動在臨機查詢下交回 `string`，於是有到期時間的金鑰讀成 `ExpiredAt = null`、`IsExpired` 永遠為 `false`——**已過期的金鑰照樣通行，而且無聲**。改走 `ValueUtilities.CDateTime(object?)`。

這與下節 Oracle 的 `RAW(16)` 是**同一個形狀**：驅動交回的 CLR 型別不是宣告型別，而裸 `is T` 把「型別不符」與「值不存在」壓成同一個答案。兩則都記進 [gotchas/database.md](../repo-ops/gotchas/database.md)。

**它為什麼活得下來**：framework repository 的多 provider 測試名義上覆蓋五家，實際全部打在 SQL Server——`[DbFact(DatabaseType.X)]` 只起了 env var 閘門的作用，建 repository 時沒有換掉 router。把覆蓋改對之後，這個缺陷與下一節的方言缺陷當場現形。執行期盤點的結果與判別訊號已寫進 [tests/CLAUDE.md](../../tests/CLAUDE.md)。

## 修正

### Oracle：參數改以名稱綁定

`Oracle.ManagedDataAccess` 的 `BindByName` 預設 `false`，SQL 裡第 n 個 bind 變數拿到參數集合的第 n 筆、與名稱無關。其餘四家皆以名稱綁定，而框架 `{0}` / `{Name}` 佔位符 API 的語意就是名稱對應。

外顯與根因差很遠。登入時 `SessionRepository.UpdateSession` 的佔位符順序是 `{1} {2} {0}`，於是 `DateTime` 被送進 `access_token`（`RAW(16)`）；壓測報告寫的是「GetList 100% 失敗」，實際是**登入先炸**，VU pool 快取了 faulted task 之後每個 iteration 立即重擲。**壓測報告指名的場景未必是壞掉的地方**——這條記進了 plan。

修在 `DbCommandSpec.CreateCommand`：對 Oracle 的 text command 設 `BindByName`，以反射進行，因為 `Bee.Db` 不參考任何 ADO.NET driver。**逐句改寫 SQL 去遷就位置綁定不是解**——那要求每個寫 SQL 的人記住一條沒有機制檢查的規則，而型別相容時的錯位根本不會報錯。

`DbDefineStorage` 的 Oracle upsert 因此回到與 SQL Server 相同的 `USING` 形狀：先前刻意讓每個參數只寫一次是為了遷就位置綁定，現在那不再是綁定上的要求。

### Oracle：`RAW(16)` 讀得回 `Guid`

Oracle 沒有 UUID 型別，`FieldDbType.Guid` 對映 `RAW(16)`、讀回來是 `byte[]`。寫入端早已處理，讀取端沒有：`GetData` / `Save` 擲「Cannot coerce value of type 'System.Byte[]' into Guid」，且回傳的 `DataTable` 宣告 `Guid` 卻裝 `byte[]`，每個 `is Guid` 分支都會走錯。

`MarkFromSchema` 就地換成真正的 `Guid` 欄位，`TryCoerceToGuid` 補上該分支。`ValueUtilities.CGuid` 本來就認 16-byte 陣列——會漏是因為 `DataFormRepository` 自帶一份平行實作。

### Common scope 的方言取自自身 `DatabaseId`

Common scope 的 repository 以 `GetConnectionInfo(DbCategoryIds.Common)` 取方言去 `QuoteIdentifier`，指令卻對 `DatabaseId` 執行。兩者在正式部署恆等（框架強制 common 的 `Id == CategoryId == "common"`），所以**既有部署沒有行為缺陷**；但方言來源是寫死的字面值而非這個 repository 自己的目標，scope 一指到別的引擎就整批 `syntax error at or near "["`。

改為一律取自 `DatabaseId`——`DataFormRepository` 與 `AuditLogRepository` 本來就是這樣寫的。`AuditRuleRepository.NotifyRulesChanged` 維持不動：它寫的是 cache-notify 表，本來就在 common，且該 repository 是 null scope。

## 變更

### `changes_xml` 改存帶內嵌 XSD 的 DataSet DiffGram

[ADR-027](../adr/adr-027-audit-trail.md) 與 [ADR-040](../adr/adr-040-audit-trail-taxonomy.md) 都把「讀取時還原成 DataSet 即可直接顯示」列為選擇 DiffGram 的好處。但寫入端輸出的是**無 schema 的裸 DiffGram**，用全新 `DataSet` 讀回會得到**零張表**（實測六種 `XmlReadMode` 皆同）。讀取端因此只能以 `XDocument` 自解、靠 `diffgr:id` 配對 before 列。

**該項好處從未兌現，而且沒有任何機制會發現**：編譯器不看散文，測試驗的是讀取端自己那條路。

寫入端改為在 DiffGram 前加寫一份內嵌 XSD，兩者包在單一外層元素 `AuditChanges` 內（`DataSet.WriteXmlSchema` + `DataSet.WriteXml`，純 BCL）。payload 自帶欄位結構，可用它自己的 schema 重建成真正的 `DataSet`，變更明細改由比對 `DataRowVersion.Original` 與 `Current` 得出。

**不用 `XmlSerializer`**：`DataSet` 實作 `IXmlSerializable`，其 `WriteXml` 就是上述兩支 BCL 方法，payload 等價（實測差 10 bytes）；不走它是為了讓 [ADR-025](../adr/adr-025-define-types-aot-xmlserializer-compat.md) 的反射路徑疑慮永久不必再論證。附帶查證：`changes_xml` 的讀取端只存在於伺服端（`Bee.Business` 不被任何行動／WASM head 引用），且該欄位從不上 wire——client 收到的是已攤平的 `RecordFieldChange`。

**相容性**：既有資料**一列都不遷移**。新舊 payload 以 root 元素分派（`AuditChanges` / `diffgr:diffgram` / `DeletedRow`，三者互斥），舊格式的解析逐字搬進 `SchemalessDiffGramReader` 並標為 frozen，**不設落日期限**——舊 parser 的維護成本遠低於一次資料遷移的風險。公開 API 表面與 wire 形狀均未變更（改動全在 `internal` 型別）。

**外部直接解析該欄位的程式需要同時支援兩種形狀。** 判別依據就是 root 元素，不需要版本欄位。

**代價**：內嵌 XSD 是固定成本，與資料量無關（Northwind 訂單那組 26 欄／2 表約 +4.2 KB／列）。異動記錄寫進獨立的 `log` 資料庫，不壓到業務庫。

值一律以 `XmlConvert` 字串化，與舊格式的 XML 原文逐字一致且 culture 無關。用 `ToString()` 會讓同一筆異動因儲存格式不同而顯示不同——`DateTime` 在所有 culture 下都不同，`decimal` 在逗號小數點的 culture 下不同，`bool` 則是 `True` 與 `true` 之別。

## 新增

### `tools/Bee.LoadTests`

壓測工具，支援 **Local**（in-process backend bootstrap）與 **Remote**（打真實 HTTP 端點）兩種模式、四家資料庫 provider，涵蓋 Login / GetList / GetData / Save 與深分頁場景，輸出 Markdown 與 JSON 報告。non-shipping tool（`IsPackable=false`）。

兩項在使用上會直接撞到的設計：

- **連線字串必須能以資料庫名隔離。** 不含 `{@DbName}` 佔位符即拒絕執行，並指示改設 `BEE_LOADTEST_CONNSTR_{DBTYPE}` 指向專用 schema。這條的由來是 Oracle：它的連線字串指的是服務而非資料庫、沒有那個佔位符，於是前綴完全無效，25 張表與 100,000 筆資料全落進單元測試自己的 schema。判準通用，不對 Oracle 特判。
- **登入是明確的前置步驟**，不在量測迴圈內。`VirtualUserPool` 以 `Lazy<Task<VirtualUser>>` 快取登入結果，失敗時 faulted task 被快取、之後每個 iteration 立即重擲——錯誤既記在場景頭上，又因為失敗極快而讓封閉模型的迴圈全速空轉，把「登入失敗一次」放大成「GetList 失敗 2,100 萬次」。改為執行場景前先 `SignInAllAsync`，失敗即中止並點名是哪個 VU、哪個帳號、底層錯誤是什麼。

## 文件

### 深分頁的 `OFFSET` 成本：量過，決定不處理

跨四家引擎量測後確認：頁數越深越貴，且倍數在各引擎間接近，與 provider 無關。**決定不處理**——ERP 畫面都有篩選、結果集通常在數十頁內，不值得為此換掉跳頁能力（keyset pagination 的代價正是不支援跳頁）。

落地兩處：[gotchas/database.md](../repo-ops/gotchas/database.md) 記下數字與成因；`PagingOptions.Page` 的 XML doc 補上「成本隨頁碼成長」，讓呼叫端在 IntelliSense 就看得到。**決定可逆**，沒有做任何會擋住 keyset pagination 的事。外部佐證另收於 [pagination-prior-art.md](../repo-ops/pagination-prior-art.md)。

### SourceLink 升版（CVE-2026-62900）

`Microsoft.Build.Tasks.Git` 10.0.202（由 `Microsoft.SourceLink.GitHub` 傳遞帶入）命中 CVE-2026-62900（CWE-212 資訊洩漏，CVSS 5.9 中度），配上 `TreatWarningsAsErrors` 讓 NU1902 直接成為建置錯誤。

**不能只升小版**：通報中 10.0.200–10.0.204 這段的修補版是「No patched NuGet version; the 10.0.2xx SDK feature band is no longer serviced」——留在 10.0.2xx 無論怎麼升都不會過，必須跨 feature band。選 10.0.303（10.0.3xx 線的第一個修補版；10.0.301 仍在受影響區間內）。

**消費端不受影響**：SourceLink 是 `PrivateAssets="All"` 的建置期相依、不進 nuspec，10.0.303 新帶的 `System.IO.Hashing` 同樣不流向消費端。
