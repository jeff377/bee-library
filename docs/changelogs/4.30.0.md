# Bee.NET 4.30.0 — Detailed Release Notes

[English](4.30.0.md) ・ [繁體中文](4.30.0.zh-TW.md) ・ [← CHANGELOG](../../CHANGELOG.md)

This document is the detailed version of the `[4.30.0]` entry in [CHANGELOG.md](../../CHANGELOG.md). The main CHANGELOG lists one line per change; this file keeps the full narrative — the *why*, the constraints, and the design context behind each change.

> This release is about **a claim that does not match the implementation**, along three threads that each start somewhere different. In prose: two ADRs described a benefit that was never delivered, and nothing could have noticed. In test coverage: multi-provider tests nominally covered five engines and in fact all ran against one, and correcting that surfaced two defects on the spot. In diagnosis: the scenario a load-test report names is not necessarily the thing that is broken — "GetList fails 100% of the time" turned out to be login failing first.

## Security

### Expired API keys kept working on SQLite

`ApiKeyRepository` read `expired_at` through `expiredAt is DateTime dt ? dt : null`. SQLite has no date type, and for an ad-hoc query the driver hands back a `string`, so a key with an expiry read as `ExpiredAt = null` with `IsExpired` permanently `false` — **an expired key kept working, and silently**. It now goes through `ValueUtilities.CDateTime(object?)`.

This is **the same shape** as the Oracle `RAW(16)` defect below: the CLR type the driver returns is not the declared type, and a bare `is T` collapses "wrong type" and "no value" into the same answer. Both are recorded in [gotchas/database.md](../repo-ops/gotchas/database.md).

**Why it survived**: the framework repositories' multi-provider tests nominally covered five engines and in fact all ran against SQL Server — `[DbFact(DatabaseType.X)]` acted only as an environment-variable gate, because the repository was built without swapping the router. Correcting the coverage surfaced this defect and the dialect defect below immediately. The audit results and the signals that identify the pattern are recorded in [tests/CLAUDE.md](../../tests/CLAUDE.md).

## Fixed

### Oracle binds parameters by name

`Oracle.ManagedDataAccess` defaults `BindByName` to `false`, so the nth bind variable in the SQL receives the nth entry of the parameter collection regardless of name. The other four engines bind by name, and the framework's `{0}` / `{Name}` placeholder API means name correspondence.

The symptom was far from the cause. At login, `SessionRepository.UpdateSession` uses the placeholders in the order `{1} {2} {0}`, so a `DateTime` was sent into `access_token`, a `RAW(16)` column. The load-test report said "GetList fails 100% of the time"; in fact **login failed first**, and the virtual-user pool cached the faulted task so every subsequent iteration rethrew it immediately. *The scenario a load-test report names is not necessarily the thing that is broken.*

The fix is in `DbCommandSpec.CreateCommand`: set `BindByName` on Oracle text commands, through reflection because `Bee.Db` references no ADO.NET driver. **Rewriting each statement to suit positional binding is not a fix** — it would require everyone who writes SQL to remember a rule nothing checks, and a mis-ordering between type-compatible parameters raises no error at all.

`DbDefineStorage`'s Oracle upsert consequently returns to the same `USING` shape as SQL Server: writing each parameter exactly once was a concession to positional binding, and that is no longer a binding requirement.

### Oracle reads `RAW(16)` back as `Guid`

Oracle has no UUID type; `FieldDbType.Guid` maps to `RAW(16)` and reads back as `byte[]`. The write side already handled this and the read side did not: `GetData` / `Save` threw "Cannot coerce value of type 'System.Byte[]' into Guid", and the returned `DataTable` declared `Guid` while holding `byte[]`, so every `is Guid` branch took the wrong path.

`MarkFromSchema` now replaces the column with a real `Guid` column in place, and `TryCoerceToGuid` gains the branch. `ValueUtilities.CGuid` already accepted a 16-byte array — the gap existed because `DataFormRepository` carried a parallel implementation of its own.

### Common-scope dialect comes from the repository's own `DatabaseId`

Common-scope repositories took the dialect for `QuoteIdentifier` from `GetConnectionInfo(DbCategoryIds.Common)` while executing the command against `DatabaseId`. The two are always equal in a real deployment — the framework requires `Id == CategoryId == "common"` — so **no shipped deployment misbehaved**. But the dialect came from a hard-coded literal rather than from this repository's own target, so pointing the scope at another engine produced `syntax error at or near "["` across the board.

It now always comes from `DatabaseId`, which is what `DataFormRepository` and `AuditLogRepository` already did. `AuditRuleRepository.NotifyRulesChanged` is left alone: it writes the cache-notify table, which lives in common by definition, and that repository is null-scope.

## Changed

### `changes_xml` stores a DiffGram with an inline XSD

[ADR-027](../adr/adr-027-audit-trail.md) and [ADR-040](../adr/adr-040-audit-trail-taxonomy.md) both listed "restore into a DataSet on read and display it directly" as a benefit of choosing a DiffGram. But the write side emitted a **bare DiffGram with no schema**, which yields **zero tables** when read into a fresh `DataSet` — measured across all six `XmlReadMode` values. The read side therefore had to parse the payload with `XDocument` and pair before-rows by `diffgr:id`.

**The benefit was never delivered, and nothing could have noticed**: compilers do not read prose, and the tests exercised the read side's own path.

The write side now emits an inline XSD ahead of the DiffGram, both wrapped in a single `AuditChanges` element (`DataSet.WriteXmlSchema` + `DataSet.WriteXml`, plain BCL). The payload carries its own field structure, so it rebuilds into a real `DataSet` from its own schema, and the change detail comes from comparing `DataRowVersion.Original` against `Current`.

**`XmlSerializer` is not used**: `DataSet` implements `IXmlSerializable`, and its `WriteXml` is those same two BCL calls, so the payload is equivalent (10 bytes apart when measured). Avoiding it keeps the audit path off the reflection route [ADR-025](../adr/adr-025-define-types-aot-xmlserializer-compat.md) covers, permanently. Two related checks: the read side exists only on the server (`Bee.Business` is referenced by no mobile or WASM head), and the column never crosses the wire — clients receive the already-flattened `RecordFieldChange`.

**Compatibility**: **no stored row is migrated**. The two shapes are told apart by their root element (`AuditChanges` / `diffgr:diffgram` / `DeletedRow`, mutually exclusive); the older parser moves verbatim into `SchemalessDiffGramReader` and is marked frozen, with **no sunset** — maintaining it costs far less than the risk of a data migration. Public API surface and wire shape are unchanged; the work is entirely in `internal` types.

**Code outside the framework that parses this column directly needs to handle both shapes.** The root element is the discriminator; no version column is involved.

**The cost**: the inline XSD is a fixed overhead independent of data volume — about +4.2 KB per row for the Northwind order schema (26 columns across two tables). Change records go to the separate `log` database, so this does not land on a business database.

Values are stringified through `XmlConvert`, matching the older format's raw XML text exactly and independent of culture. Using `ToString()` would make the same logical change display differently depending on which shape it was stored in — `DateTime` differs under every culture, `decimal` under comma-decimal cultures, and `bool` as `True` versus `true`.

## Added

### `tools/Bee.LoadTests`

A load-testing tool supporting **Local** (in-process backend bootstrap) and **Remote** (against a real HTTP endpoint) modes across four database providers, covering Login / GetList / GetData / Save and deep-paging scenarios, emitting Markdown and JSON reports. Non-shipping tool (`IsPackable=false`).

Two design points you meet immediately in use:

- **The connection string must be isolatable by database name.** Without the `{@DbName}` placeholder the tool refuses to run and directs you to set `BEE_LOADTEST_CONNSTR_{DBTYPE}` at a dedicated schema. This came from Oracle: its connection string names a service rather than a database and has no such placeholder, so the prefix had nothing to substitute into and 25 tables plus 100,000 rows landed in the unit tests' own schema. The check is general rather than an Oracle special case.
- **Sign-in is an explicit prerequisite**, not part of the measured loop. `VirtualUserPool` cached sign-in through `Lazy<Task<VirtualUser>>`, so a failure cached a faulted task that every later iteration rethrew at once — attributing the error to the scenario, and, because failing is fast, spinning the closed-model loop at full speed and inflating "one failed login" into "21 million GetList failures". Sign-in now happens via `SignInAllAsync` before scenarios run, aborting with the virtual user, the account, and the underlying error named.

## Documentation

### The cost of deep `OFFSET` paging: measured, then deliberately left alone

Measurement across the four engines confirmed that deeper pages cost more, by similar multiples on every engine and independent of the provider. The decision is **not to address it** — ERP screens filter, result sets usually run to tens of pages, and it is not worth trading away the ability to jump to a page (which is exactly what keyset pagination gives up).

Two landing places: [gotchas/database.md](../repo-ops/gotchas/database.md) records the numbers and the cause, and `PagingOptions.Page` gains an XML doc remark so callers see it in IntelliSense. **The decision is reversible** — nothing was done that would obstruct keyset pagination later. Supporting external evidence is collected in [pagination-prior-art.md](../repo-ops/pagination-prior-art.md).

### SourceLink upgrade (CVE-2026-62900)

`Microsoft.Build.Tasks.Git` 10.0.202, pulled in transitively by `Microsoft.SourceLink.GitHub`, is covered by CVE-2026-62900 (CWE-212 information disclosure, CVSS 5.9 medium). With `TreatWarningsAsErrors`, NU1902 became a build error outright.

**A patch-level bump is not available**: for the 10.0.200–10.0.204 range the advisory says "No patched NuGet version; the 10.0.2xx SDK feature band is no longer serviced" — nothing within 10.0.2xx would pass, so the move crosses a feature band. 10.0.303 is the first patched version on the 10.0.3xx line (10.0.301 is still inside the affected range).

**Consumers are unaffected**: SourceLink is a `PrivateAssets="All"` build-time dependency that never enters the nuspec, and `System.IO.Hashing`, newly pulled in by 10.0.303, likewise does not reach consumers.
