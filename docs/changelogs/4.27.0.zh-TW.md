# Bee.NET 4.27.0 — 詳細版本說明

[English](4.27.0.md) ・ [繁體中文](4.27.0.zh-TW.md) ・ [← CHANGELOG](../../CHANGELOG.zh-TW.md)

本文件是 [CHANGELOG.zh-TW.md](../../CHANGELOG.zh-TW.md) 中 `[4.27.0]` 條目的展開版。主 CHANGELOG 每項變更一行；本檔保留完整脈絡——每項變更背後的**為什麼**、限制條件與設計考量。

> 瀏覽器前端呼叫不了編碼過的端點。body 只有 MessagePack 一種，而本框架的 MessagePack wire 是三十餘支手寫 formatter——在另一個語言鏡像它們，等於為同一份合約建立第二個權威來源，而兩邊漂掉時沒有任何機制會發現。本版把 body codec 的選擇從部署層設定改為在信封上**逐請求宣告**，並在 MessagePack 之外新增 JSON codec。JavaScript client 於是只需要 JSON、gzip、AES-CBC-HMAC 與 RSA，全是原生 API。隨之發布兩份產物，讓另一個語言的 client 有東西可以驗自己、而不是一份文件要遵守：26 個 wire body 樣本，以及由訊息型別反射產生的 TypeScript 合約。見 [ADR-044](../adr/adr-044-payload-codec-negotiation.md)。

## 破壞性變更

### 移除 `ApiPayloadOptions.Serializer`

codec 改為逐請求宣告之後，這個設定只剩一個作用：客戶端沒宣告時，server 要用哪個解。而那個答案只能是 `messagepack`——所有早於協商機制的客戶端都不宣告、且送 MessagePack，設成 `json` 會讓它們同時全部解碼失敗。它已經不是部署選擇，而是一個相容性常數；一個只有唯一正確位置的旋鈕，比沒有旋鈕更糟。

依 pre-stable 政策以 minor 發佈，且**明列而非靜默**。

既有的 `SystemSettings.xml` 不必修改。`XmlSerializer` 會忽略未知元素，殘留的 `<Serializer>` 元素無害、反序列化照樣成功——但它是**被忽略**而不是被採用，正是那種「趁還記得為什麼的時候順手刪掉」的東西。

## 新增

### body codec 逐請求宣告

`ApiPayload.Codec` 在信封上承載 codec 名稱，`TransformTo` 與 `RestoreFrom` 都改從 payload 讀，不再讀設定。名稱來自 wire，因此先驗形狀再回顯——小寫英數與連字號，並設長度上限。

`PayloadCodecNames` 收兩個名稱（`json`、`messagepack`）；`ApiServiceOptions.AcceptedPayloadCodecs` 與 `ResolvePayloadSerializer` 負責把名稱解析成 serializer。未宣告 codec 的請求一律讀為 MessagePack——那正是所有早於協商機制的客戶端所送的——因此不帶 codec 的信封與先前 byte-for-byte 相同。

兩種 codec 恆可用，不設啟用閘門。閘門實作過又移除，因為它的前提是錯的：原本的推理是「多一個 codec 等於多一個匿名可達的解析器」，但 `System.Text.Json` 早就在那條路徑上——信封本身是 JSON、`Plain` body 由 `ApiInputConverter` 反序列化、`System.Login` 依設計即為匿名。JSON body codec 沒有引入任何原本不可達的解析器類別。

### `JsonPayloadSerializer` 與值封套

JSON 分不出 `decimal` 與 `double`，也分不出 `Guid` 與 `string`。因此宣告型別為 `object` 的 wire 成員以判別式封套 `[code, value]` 傳遞，由內部的 converter 寫出；少了它會**靜默錯值**，那比報錯更糟。判別碼沿用既有的 `WireValueCode`，因此 `WireValueCodePinTests` 同時釘住兩條 wire。

`decimal`、`long`、`ulong` 一律寫成 JSON 字串。JSON number 對每個 JavaScript 讀取端都是 `double`，既撐不住 `decimal` 精度，也撐不住 2^53 以上的整數。

### transformer 的 codec-aware 多載

`IApiPayloadTransformer` 新增三參數的 `Encode` 與 `Decode`。兩者是 **default interface member 且預設擲回** `NotSupportedException`，不靜默退回部署預設 codec：退回會用呼叫端沒要求的 codec 編碼，而對方會用它要求的那個解碼。未宣告 codec 的呼叫仍走既有的兩參數多載，因此早於協商機制寫成的自訂 transformer，服務那些呼叫時完全不受影響。

### `ApiConnector.PayloadCodec`

讓 .NET client 宣告 codec。未設定即維持 MessagePack，既有 client 程式碼不受影響。

### wire body 樣本

`wire-fixtures/bodies/` 收 26 個樣本，由 `WireFixtureTests` 產生並驗證；`wire-fixtures/README.md` 說明信封結構與六條讀者最容易做錯的規則。讀者是另一個語言的 client 作者，故以英文撰寫。

樣本覆蓋的是**每一條編碼規則**而非每一個 wire 型別。逐型別會產出上百個幾乎同構的檔案，卻仍漏掉真正會錯的地方；現在涵蓋的是 22 個 wire value 判別碼、`DataTable`（含 `rowState` 與 Modified 列的 original/current 配對）、`DataSet`，以及兩個代表性的訊息型別。

只固定 body 原文，不固定壓縮或加密後的 bytes。gzip 輸出跨 .NET 版本不保證一致、AES-CBC 每次隨機 IV，那兩層本質上不可固定，改由各語言自己的 library 保證。

樣本不符時測試即紅，並指示以 `BEE_REGENERATE_WIRE_FIXTURES=1` 重新產生後讀 diff。那份 diff **就是** wire 的變更說明。

### 由訊息型別產生的 TypeScript 合約

在 TS 那端手抄一份型別表，就是同一份 API 合約的第二個權威來源：伺服端改了欄位名，抄本不會知道，而症狀是欄位靜默消失、不是錯誤。`wire-contracts/messages.d.ts` 改由反射產生，`WireContractGeneratorTests` 讓「合約變了」在這裡就紅。

它描述的是 **wire 形狀**而非 CLR 形狀，因為讀者要知道的是「這個 JSON 長什麼樣」：`Guid` 與 `DateTime` 都是 `string`，列舉是字串字面值聯集（伺服端以 `JsonStringEnumConverter` 輸出），`object` 成員是 `[code, value]` 封套，`DataSet` / `DataTable` 依它們的自訂 converter。最後那幾個形狀反射看不出來，因此手寫在產生器的前言裡，並由測試中的 canary 釘住。

產出涵蓋 91 個 interface 與 11 個列舉，且沒有任何產生出來的屬性落成 `unknown`——型別對映沒有缺口。

`wire-contracts/type-names.ts` 是第二個檔案，承載 assembly-qualified 型別名。編碼過的 payload 必須在信封裡指名型別，伺服端據以解析並先過白名單；那串名字含命名空間與組件名，跨 repo 手抄在訊息型別第一次搬家時就會漂——而症狀是執行期被拒、不是編譯錯誤。之所以分成兩個檔案，是因為 `.d.ts` 不能帶值；兩者由同一組測試釘住。

### 匿名攻擊面改為具名申報

免登入即可呼叫的方法**就是**框架對外的匿名攻擊面，而宣告它的只是一個 attribute 參數——新增一個標了 `Anonymous` 的方法，不會有任何東西要求說明理由。`AnonymousApiSurfaceTests` 就是那個要求：未申報即紅，且每一項都必須寫明「未登入者從這個回應能知道什麼」。白名單裡的幽靈條目同樣會紅，避免下一次安全盤點誤判攻擊面的大小。

它同時釘住一件先前沒有被寫下來的事實：**兩層把關的判斷來源不同，且並未對齊。** `ApiAuthorizationValidator` 在 HTTP 層以硬編方法名清單決定要不要 `Authorization` header，`ApiAccessValidator` 在 BO 層讀 attribute 決定要不要驗 token。結果是四個標了 `Anonymous` 卻不在 HTTP 層清單裡的方法（`GetCommonConfiguration`、`CheckPackageUpdate`、`GetPackage`、`ExecFuncAnonymous`）需要一個 header，但那個 header 只被檢查能不能 parse 成 `Guid`，而 BO 層因為方法是 `Anonymous` 又不驗證它——送任意 GUID 即可通過兩層。

這不是漏洞，那四個方法標 `Anonymous` 本來就是設計意圖；問題在於那道 header 檢查讓它們**看起來**有保護。測試以實際呼叫 `Validate` 探測並斷言此行為，因此它是可執行的事實，而不是註解裡的宣稱。

同時，`ApiAccessControlPinTests` 釘住每個 API 方法的保護等級與驗證需求。把某方法從 `Public` 調到 `Encrypted`、或從 `Anonymous` 改為 `Authenticated`，會讓既有客戶端當場被拒——包含不隨框架一起發版的前端——而先前沒有任何機制會發現：attribute 的參數不進 `PublicAPI.Shipped.txt`，analyzer 看不到；wire 樣本也看不到，因為它改變的是「誰能送」而不是 payload 的形狀。期望值寫成字串而非列舉引用，因此把成員改名不會讓清單與測試一起靜默跟著改。

## 修正

### `Plain` 路徑上送出的 `Filter` 會丟失整棵子樹

`GetListRequest.Filter` 的宣告型別是抽象基底 `FilterNode`，而 `System.Text.Json` 綁的是宣告型別——於是指派給它的 `FilterGroup` 只寫出 `{"kind":"Group"}`。運算子與整棵篩選樹消失，不擲例外也不留紀錄。

這不是本次 codec 工作引入的。`FilterGroup.Nodes` 早有 `FilterNodeCollectionJsonConverter`，但單一節點的那一半沒有，而編碼過的 body 一直只走 MessagePack（那端有自己的 filter node formatter），所以缺陷只在 `Plain` 路徑上壞著、沒人踩到。JSON body codec 上線後，它會在最常用的清單查詢上生效。

`FilterNodeJsonConverter` **標在屬性上而非型別上**。標在 `FilterNode` 上會被子類繼承，寫 `FilterGroup` 時再度進入同一個 converter，遞迴到 stack 爆掉——那是 segfault 不是可捕捉的例外，實作過程中已實際踩過一次。

守護兩層：`FilterNodeJsonConverterTests` 驗行為，`FilterNodeConverterCoverageTests` 以反射掃描，新增可寫入的 `FilterNode` 屬性卻忘了標註即紅。get-only 的屬性不納入——`DeleteContext.ScopeFilter` 是其一，同一個物件還帶著 repository 介面，從不經過 JSON。

**這是一次行為變更。** 先前送出 `Filter` 的 `Plain` 請求會丟失篩選條件，等同無條件查詢；現在條件會正確送達。依賴該錯誤行為的呼叫端幾乎不存在，但原本回傳全部資料的查詢，現在會回傳篩選後的結果。

## 變更

### ADR-044，以及它與 ADR-014 的關係

codec 協商會影響外部使用者——信封多一個欄位、一個設定被移除、自訂 transformer 可能要實作新多載——因此升格為 ADR，而不是留在階段性的 plan 裡。

[ADR-014](../adr/adr-014-jsonrpc-plain-public-default.md) 早已為同一個問題鋪了一條路（`Plain` 加上七個方法降級為 `Public`），並明確拒絕了為 JS 前端做 JS 版加密管線。兩則 ADR 談同一主題卻不互相引用，正是後人會踩的坑，因此 ADR-044 逐條回應那次拒絕：三條理由裡有兩條的前提已經改變——「逐 byte 對齊成本高」正是 wire 樣本在解的問題，「多個前端框架各自再實作一份」正是把它做成單一 npm 套件的理由。第三條是真正的立場分歧，取決於「HTTPS 夠不夠」，那是部署方的判斷而非技術問題。

ADR-014 依 repo 慣例不改寫內文，只在狀態行加註記指向 ADR-044，讓兩邊雙向可達。它**沒有被取代**：`Plain` 仍是 JS 前端的預設路徑，七個方法仍是 `Public`。

## 升級

無事可做。未宣告 codec 的請求，信封 byte-for-byte 不變，行為與先前完全相同。

三件事值得看一下：

- **把 `SystemSettings.xml` 裡的 `<Serializer>` 元素刪掉**（若還在）。它是被忽略而不是被採用，留著無害但會誤導。
- **自訂的 `IApiPayloadTransformer`** 對所有未宣告 codec 的呼叫照常運作。要服務會協商 codec 的 client，請實作三參數的 `Encode` 與 `Decode` 多載；在那之前它們會擲 `NotSupportedException`，而不是靜默用錯 codec。
- **帶 `Filter` 的 `Plain` 請求**現在會真的套用該篩選。若下游有任何東西是照著「未篩選的結果」寫的，這一版就是它改變的時候。

.NET client 要送 JSON body：

```csharp
connector.PayloadCodec = PayloadCodecNames.Json;   // 未設定即為 MessagePack
```
