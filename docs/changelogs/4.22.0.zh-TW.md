# Bee.NET 4.22.0 — 詳細變更說明

[English](4.22.0.md) ・ [繁體中文](4.22.0.zh-TW.md) ・ [← 版本變更記錄](../../CHANGELOG.zh-TW.md)

本文是 [CHANGELOG.zh-TW.md](../../CHANGELOG.zh-TW.md) 中 `[4.22.0]` 條目的詳細版。主 CHANGELOG 每項變更一行，本檔保留完整脈絡——**為什麼**要改、有哪些限制、以及背後的設計考量。

> 本版篇幅小、性質是修正，而四項當中有兩項共用同一個主題：**機制擺在那裡、看起來好好的，實際上什麼也沒做。**
>
> analyzer 把定義檔注入打包在 `build/`，而 NuGet 只對**直接** `PackageReference` 匯入該資料夾——於是遞移取得 `Bee.Definition` 的專案照常載入 analyzer 組件、卻一個檔案都讀不到，所有規則靜默通過。`BEE1004` 真的觸發時，訊息描述的後果也只對它所涵蓋的一半屬性成立。圍繞這兩項的是兩個破壞性變更：稽核軌跡的 change 軸收編回它原本就重複的共用清單合約，以及「宣告了卻解析不出型別」的 BO 綁定改為直接拋，不再靜默退回通用 CRUD。

## 破壞性變更

### AuditLog change 軸收編共用清單合約

`IGetChangeLogResponse` 與 `ILogListResponse` 的成員完全相同——`Table` 與 `Paging`。這是分期實作的殘留：Phase 2a 先做 change 軸，當時它是唯一一條 list，因此開了專屬合約；同一天的 Phase 2b 加入 login、access、anomaly 三軸並抽出共用的 `ILogListResponse`，卻沒有回頭收編 Phase 2a。後來搬 namespace 時原樣保留了這份重複。

移除三個型別，change 軸改用 `LogListResult` / `LogListResponse`：

- `Bee.Api.Contracts.AuditLog.IGetChangeLogResponse`
- `Bee.Api.Core.Messages.AuditLog.GetChangeLogResponse`
- `Bee.Business.AuditLog.GetChangeLogResult`

連帶兩個簽章改變——`LogBusinessObject.GetChangeLog` 改回傳 `LogListResult`、`LogApiConnector.GetChangeLogAsync` 改回傳 `Task<LogListResponse>`。兩者都是把回傳型別放寬至共用型別，對「曾以型別名宣告過舊型別」的消費端而言，**原始碼與二進位皆不相容**。

**wire 格式本身不變。** 兩個型別的成員與序列化形狀完全相同，舊 client 收到的 payload 與先前一致。`ApiOutputConverter` 走 `XxxResult` → `XxxResponse` 名稱慣例，因此 `LogListResult` → `LogListResponse` 自然成立、不需額外註冊；這次移除也一併拿掉 `WireContracts.AuditLog.cs` 的一筆 formatter 註冊，以及 `DateTimeWireGuard` 與 `PayloadZoneConverter` 各一個與相鄰 case 同 body 的冗餘分支。

### 宣告了卻解析不出型別的 BO 綁定改為直接拋

`ProgramSettingsBoTypeResolver` 對一般 progId 的處置與其他每一軸都相反：綁定所指的型別載不到時，它退回 `FormBusinessObject` 並記一筆錯誤日誌，而 Repository 與 Plugin 兩軸都是直接拋。兩軸採相反的失敗策略背後沒有任何正當理由——那是分期實作的結果，不是設計。

那條退路換到的只有「看起來還在跑」。`FormBusinessObject` 的建構子接受任何 progId，因此一定建構成功；故障於是浮現得晚，面貌是「方法不存在」或「本該有客製邏輯的地方跑出通用行為」，而診斷方向被指向 API 層而非註冊表。多租戶部署下，客製檔裡打錯一個字會靜默失效——而客製化正是註冊表存在的主要動機。

改動只涵蓋一條路徑：**宣告了一個名字，而那個名字解析不出可用的型別。**

- 型別載不到（`FileNotFoundException`、`FileLoadException`、`BadImageFormatException`，或 `GetType` 回 `null`）→ 擲 `InvalidOperationException`
- 型別不衍生自預期基底 → 擲 `InvalidOperationException`

例外訊息一律帶 progId、型別名，以及該綁定的宣告來源（套裝設定，或哪一份客製檔）。保留字 progId 額外以 `ReservedProgIdBinding.ExpectedBaseType` 約束基底型別；一般 progId 只需衍生自 `BusinessObject`。

**「沒宣告」仍然不是失敗。** 註冊表沒有這筆 progId、或 `BusinessObject` 元素留空時，照舊解析為框架預設——一般 progId 得到 `FormBusinessObject`、保留字得到該軸的框架物件。啟動自我註冊與漸進採用皆不受影響。

解析失敗不會寫進 type cache：`GetOrAdd` 的 value factory 擲例外時不寫入，因此每次呼叫都會拋，不會第二次起就靜默通過。

公開表面零變更——`ILogger` 建構子多載保留，參數改為忽略——因此本項**二進位相容、行為破壞性**。決策與其修訂記於 [ADR-034](../adr/adr-034-progid-type-registry.md)。

## 修正

### analyzer 載入了、卻讀不到檔案，於是全部通過

`Bee.Definition.targets` 的職責是把消費端專案的定義檔注入 `AdditionalFiles`，讓 `BEE1xxx` / `BEE2xxx` 規則有東西可讀。它被打包在 `build/`，而 **NuGet 只對直接 `PackageReference` 匯入套件的 `build/` 資料夾。**

於是凡是遞移取得 `Bee.Definition` 的專案——只引用 `Bee.Business`、`Bee.Db`、`Bee.Api.AspNetCore` 或 `Bee.Hosting` 的都算——都拿到了 analyzer 組件（它確實會遞移流入並正常載入），卻沒有任何檔案可分析。所有規則通過，而建置過程對此隻字未提。這個失效完全沒有症狀，是外部 repo 消費 4.21.0 套件時實測到 `AdditionalFiles` 為 0 筆才發現的。

targets 改放 `buildTransitive/`。本機以兩組套件對「只引用 `Bee.Business`」的消費端實測：baseline 遞移 0 筆、直接 3 筆；改後遞移與直接皆 3 筆，來源均為 `buildTransitive/`。端到端測試中，一份 `CategoryId` 非法的 `FormSchema` 在 baseline 下零診斷，改後正確擲出 `BEE1001`。「兩處都放」也實測過——不會 double-import，因為直接消費者仍只選 `buildTransitive/`——故 `build/` 屬純冗餘，只保留一處。

`BeeDefinitionFilesGlob` 的預設維持以專案目錄為根。往上層搜尋會讓方案根的定義檔被每個引用框架的專案各撈一次，同一批診斷重複報 N 次；同理，「撈到 0 筆就警告」會對方案內本就沒有定義檔的專案全數誤報。可觀測性改以兩個零噪音手段補上：在 `normal` 詳細度印出 glob 與比對筆數，以及 opt-in 的 `BeeRequireDefinitionFiles` → `BEE9003`。

`BuildAssetPackagingGateTests` 把資料夾位置與 `PackagePath` 變成可執行檢查——正因為這個失效沒有任何症狀可供察覺。

**消費者需要本次發版才會生效**——打包方式本身就在套件裡。

### `BEE1004` 描述的後果只對它一半的屬性成立

`BEE1004` 同時涵蓋 `ListFields` 與 `LookupFields`，但原訊息「Unknown entries are skipped silently」只對後者成立。`FormSchema.GetLookupFields` 以 `master.Fields.Contains` 過濾，未知的 lookup 項目確實會靜默消失。

`ListFields` 只有版面那一半是靜默的——`ListLayoutGenerator` 套用了同一個 `.Where(master.Fields.Contains)`。查詢那一半不經過濾：`ListView.ComputeSelectFields` 直接切開原字串送出、`DataFormRepository.GetList` 在 `selectFields` 為空時回退 `_schema.ListFields`，最後 `SelectBuilder.Build` 對未知欄位擲 `InvalidOperationException`。開發者照舊訊息會預期「少一個欄位」，實際拿到的是執行期失敗。

`s_listAttributes` 改為 `(Name, Consequence)` 配對，messageFormat 開 `{3}` 收後果句；descriptor 的 description 一併改為同時交代兩種後果。測試補上分岔斷言，避免訊息再漂回單一措辭。

僅診斷訊息文字，無公開 API 變更。

### 全 repo 的 XML doc 漂移

對 `src/**/*.cs` 的文件註解做了一次完整盤點（26,263 行 / 991 檔），找出十筆實質錯誤，其中八筆是漂掉的清點數字。`IFormCommandBuilder` 與五個 provider 實作宣稱產生 Select/Insert/Update/Delete，實際只剩 `BuildSelect`、`BuildCount`、`BuildDelete`——而六份 summary 全都漏掉 Count。`CustomizeDefineReader` 與 `CustomizeOnlyStorage.GetChangeSource` 寫「four customizable types」，實際五種。`CacheInfo.Initialize` 指向已不存在的 `CacheBootstrapper`。`RepositoryBase` 寫「nine framework repositories」，映射表實際 11 筆。

這些會隨各套件的 `.xml` 一起發佈，直接出現在消費端的 IntelliSense，因此列在這裡而非視為內部文件。

`<see cref>` 本來就有把關——指空會是 `CS1574`，在 `TreatWarningsAsErrors` 下建置失敗——但散文中的 `<c>` 不受保護，`check-xmldoc-refs.sh` 補上這一段。清點數字本身不是 analyzer 判定得了的事，因此改以編輯守則消除來源：文件註解列名稱而不列數字，因為名稱錯了讀者看得出來，數字錯了看不出來。

僅改動文件註解，未動任何簽章，`PublicAPI.*.txt` 不受影響。

## 新增

- `Bee.Definition`：`SystemActions.CheckPackageUpdate` 與 `SystemActions.GetPackage`。新增的 `ActionSurfaceTests` 閘門首次執行即抓到這兩筆——`SystemBusinessObject.CheckPackageUpdate` 與 `GetPackage` 是 anonymous 可呼叫的 API 表面，卻沒有對應的 action 常數，呼叫端只能用魔術字串。純新增。

## 內部

`ActionSurfaceTests` 以 `*Actions` 常數類為單一權威來源，雙向驗證 JSON-RPC 的動作表面。既有的配對測試守的是「型別有沒有配對契約介面」，但 JSON-RPC 的 method 是**字串**——`JsonRpcExecutor` 拿 action 直接呼叫 `GetType().GetMethod(action)`。常數打錯字時兩個配對測試全綠，症狀是執行期的 `MissingMethodException`；反向漏登記常數則讓呼叫端只能用字面值。新閘門驗證：每個常數在對應 BO 上都有 public 方法、單一 `BusinessArgs` 參數、回傳 `BusinessResult`、且被 `[ApiAccessControl]` 覆蓋；以及反過來，每個這樣的方法都有對應常數。

## 升級指引

機械式替換：

```diff
- Bee.Api.Contracts.AuditLog.IGetChangeLogResponse
+ Bee.Api.Contracts.AuditLog.ILogListResponse

- Bee.Api.Core.Messages.AuditLog.GetChangeLogResponse
+ Bee.Api.Core.Messages.AuditLog.LogListResponse

- Bee.Business.AuditLog.GetChangeLogResult
+ Bee.Business.AuditLog.LogListResult
```

需要確認而非替換：

- **檢查 `ProgramSettings.xml`（含各租戶客製檔）裡每一個 `BusinessObject` 型別名都確實解析得到。** 綁定所指型別載不到時，原本會退回通用 CRUD 並記一筆錯誤日誌，現在該 progId 的每一次請求都會拋。一直靠靜默退路在跑的部署，升級後會明顯失敗——這正是本項變更的目的，但在升級前發現比升級後發現好。

AuditLog 那項不需要 client 與 server 同時部署：兩個型別的序列化結果完全相同，舊 client 與新 server 可照常互通。
