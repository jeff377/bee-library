# Bee.NET 4.26.0 — Detailed Release Notes

[English](4.26.0.md) ・ [繁體中文](4.26.0.zh-TW.md) ・ [← CHANGELOG](../../CHANGELOG.md)

This document is the detailed version of the `[4.26.0]` entry in [CHANGELOG.md](../../CHANGELOG.md). The main CHANGELOG lists one line per change; this file keeps the full narrative — the *why*, the constraints, and the design context behind each change.

> A captured JSON-RPC packet could be resent and would execute again. The payload is authenticated — an attacker cannot alter it — but authentication says nothing about *uniqueness*, and a resent `Save` is a valid, correctly signed `Save`. This release adds a wire frame carrying a timestamp and a sequence number, and a per-session sliding window that refuses a sequence already accepted. Introducing the frame is a wire break, so it ships behind a switch that defaults to off. Alongside it, the exception-to-error-code mapping the two ends had each held privately becomes one ordered registry, and schema upgrade gains description sync on all four dialects.

## Added

### Replay protection for the `Encoded` and `Encrypted` wire formats

`ApiPayloadFrame` is 17 bytes — a version byte, an 8-byte timestamp in milliseconds, and an 8-byte sequence number, all big-endian. It is prepended **after** `Encode` and **before** `Encrypt`, which is the whole point of where it sits: inside the envelope, the payload HMAC covers it. A frame carried in a plaintext field of `ApiPayload` would be rewritable by the attacker at will, which is the same as having no frame.

The server does **not** detect whether a frame is present. Both ends read `ApiServiceOptions.RequireWireFrame`, and a server that inferred the frame's presence from the packet could be downgraded by an attacker who simply removed it. The consequence of fail-closed is that the switch is not negotiated: turning it on at one end alone fails every call. It defaults to `false`, so upgrading the package changes nothing on its own.

The version byte exists so that the layout can change later without a second guessing game; `Version1Size` is the constant that pins the current one.

### The sequence window

`ReplayWindow` is a scaled-down IPsec anti-replay window (RFC 6479): per session it keeps the highest sequence seen plus a 64-bit bitmap — 16 bytes — and a decision is a few bit operations with no database round trip.

Tolerating out-of-order arrival is a requirement rather than a bonus. Taking a number is atomic, but the order in which concurrent requests *arrive* is not fixed, so a strictly-increasing rule would reject honest traffic.

`MaxForwardJump` is 1,000,000. Without a ceiling, a single client-side arithmetic slip that sends a sequence near `long.MaxValue` would put every subsequent legitimate request outside the window for that session — with a valid token and correct keys, and essentially undiagnosable.

Window lifetime is twice the timestamp tolerance and is deliberately decoupled from session lifetime: a replay using an old sequence necessarily has an expired timestamp too, which the timestamp check already refuses, so the window only has meaning inside that span and needs no logout-time cleanup. The memory bound is "sessions active within the tolerance window".

Anonymous calls (`Guid.Empty`) are not sequence-checked. Sequences are per session, and anonymous callers all share one token; checking them would have different clients consuming each other's numbers and rejecting each other in bulk.

`IReplayWindowStore` is an interface because that is the exit for multi-node deployments. The default keeps windows in this process's memory. Behind a load balancer without token affinity each node keeps its own — a captured packet is replayable once per node, still bounded and far better than unbounded — and a deployment that needs strict cross-node behaviour substitutes a shared implementation.

### Declaring which calls require a unique sequence

`ApiAccessControlAttribute.ReplayProtection` takes `ApiReplayProtection.None` (the default, so existing declarations are unaffected) or `UniqueSequence`. Five methods carry it: `Save`, `Delete`, `ExecFunc`, `EnterCompany` and `LeaveCompany`. That is the complete set of remotely reachable methods with side effects — the remaining write methods (`SaveDefine`, `SaveCustomizePluginSettings`, `SetDeploymentAdmin`) are all `LocalOnly` and cannot be reached remotely.

### `AnomalyKind.Replay`

Classified in `JsonRpcExecutor`'s existing failure-recording path. Folding it into the generic `Error` kind would lose the one signal that matters here: a burst of refusals from a single session is either a client whose clock has drifted out of the accepted window, or someone resending captured packets. Neither is visible if they are filed as generic errors.

The full set of decisions — including three things deliberately left out (idempotency keys, narrowing `ApiProtectionLevel.Public`, and dropping business-layer guards) — is in [ADR-042](../adr/adr-042-api-replay-protection.md).

### Description sync across the four dialects

`IDescriptionSyncCommandBuilder` is reached through `IDialectFactory.CreateDescriptionSyncCommandBuilder()`. SQL Server continues to use extended properties; PostgreSQL and Oracle use `COMMENT ON`; MySQL uses `ALTER TABLE ... COMMENT` and `MODIFY COLUMN`.

The factory member is a **default interface member returning `null`** — an external `IDialectFactory` implementation keeps compiling and running unchanged. Making it abstract would have been a breaking change for no gain; `null` is also the correct answer for a dialect with nowhere to store a description.

## Changed

### One registry for the error contract

The server's `MapException` turns an exception into an error code; the client's `FinalizeResponse` turns the code back into an exception. The two are inverses, and nothing kept them in step. `ReplayRejectedException` drifted exactly that way: the server threw it in four places and mapped it to `-32005`, while the client was missing the branch entirely — so the `catch (ReplayRejectedException)` promised by that type's own documentation could never be entered, and it compiled and tested green.

`JsonRpcErrorContract` declares, in one ordered table, which exception takes which code and who rebuilds it. Both ends now read that table.

Order sensitivity is not pretended away. Type matching has to be assignability-based (`ArgumentNullException` belongs under `ArgumentException`), so the registry declares the invariant that a derived type must precede its base, and a test verifies it pair by pair, naming which two rows shadow each other. The old implementation depended on order just as much; the difference is that getting it wrong there produced no signal.

The fallback stays outside the registry on purpose. The `InternalError` branch reads `SysInfo.IsDebugMode` — that is an information-disclosure policy — and the client's generic branch is a message format. Neither is a type-to-code mapping.

`ADR-043` records the decision, including why "make these exceptions inherit `UserMessageException`" was rejected: it would not have removed a single `if`, because those four types are not on the whitelist to begin with. See [ADR-043](../adr/adr-043-error-contract-single-registry.md).

One side effect worth noting: the client no longer needs to know any concrete exception type, and `ApiConnector` dropped its `Bee.Base.Exceptions` using directive altogether.

### Error-code documentation corrections

Four drifts in the public documentation are fixed: the error-code table was missing `-32005`; the description of `-32001` did not match reality (authentication failure actually answers `-32600` with HTTP 401, and `-32001` has no producer at all); and the development-constraints document claimed only `UserMessage` was rebuilt on the client, when `PermissionDenied`, `CompanyAccessDenied` and `CompanyNotEntered` had always had their own types. Both language editions are updated, and the mapping table now points at `JsonRpcErrorContract` rather than restating it.

## Fixed

### Oracle: a phantom difference on LOB columns aborted the upgrade

`OracleTableSchemaProvider` marked every `String` / `Text` column it read back as `AllowNull=false`. That was there to align with the declared case: Oracle treats `''` as `NULL`, so the DDL builder always emits the column as nullable, and a column declared `AllowNull="false"` would otherwise never match. The cost was that a column declared `AllowNull="true"` could never match its own read-back — every comparison produced an `AlterFieldChange`.

On a `String` the resulting `MODIFY` is a harmless no-op. On a `CLOB` it is not: Oracle refuses any `MODIFY` that restates a LOB column's type, including `CLOB` to the same `CLOB`, with `ORA-22859`. Because the stage order is `AlterColumns` then `AddColumns`, the upgrade aborted before the new columns were added — `st_log_anomaly_api` and `st_log_anomaly_db` were permanently stuck two columns short of their definition.

Three changes:

- `TableSchemaComparer.CompareField` normalises nullability for Oracle's `String` / `Text` / `Time` before comparing. Under that dialect the definition cannot control it, so the two sides are not comparable in the first place.
- `OracleTableAlterCommandBuilder` emits only `DEFAULT` and nullability for a LOB-to-same-LOB change, never the type, and emits nothing at all when there is no difference left to apply. Crossing the LOB boundary is reclassified as a rebuild — `String(100)` → `Text` and `String(100)` → `String(5000)` hit the same wall, and `AlterCompatibilityRules` puts both in the same type family.
- `OracleTypeMapping.IsLobType` is derived from `GetOracleType`, so the two cannot drift apart.

### Descriptions were only synced on SQL Server

`AppendDescriptionSyncStage` recognised `SqlDialectFactory` alone. On every other dialect, a column added by an `ALTER` never received its caption. Worse, `TableSchemaDiff.IsEmpty` counts `DescriptionChanges`, so those tables reported a difference on every subsequent comparison and every `Plan` produced an `Alter` with zero stages. No error, no SQL executed — but the question "is this table up to date?" was answered *no*, permanently.

`DescriptionSyncChanges.Collect` now also picks up the caption on an `AddFieldChange`. The comparer only reports a description difference for columns present on both sides, so without that step a freshly added column had to wait a full round before its caption arrived.

**MySQL's `MODIFY COLUMN` replaces the whole column definition.** Syncing a caption-only drift on MySQL means issuing `MODIFY COLUMN`, and `GetColumnDefinition` does not include `AUTO_INCREMENT` — hitting `sys_no` stripped the auto-increment, after which every `INSERT` failed. `GetModifyColumnDefinition` preserves it (without `PRIMARY KEY`, which the table already has). This one is recorded in the repo's gotchas because of how it hid: a second run went green, because the rebuild path self-heals — that was damage being masked, not a flaky test.

**SQLite has no `COMMENT` facility** and reads every caption back as an empty string, so the comparer reports no description difference at all under that dialect. Adding a SQLite builder would not have helped — it could not produce any statement, and the difference would have stayed in the diff. The fix has to be that the comparer does not call it a difference.

### `Bee.Northwind`: partial seeds survived forever

`ft_order_detail` held 11 of its 12 seed rows. The missing one was the last, so order 10252 showed a total of 1995 instead of the seed file's 2235.

Two things combined. The idempotence gate is `SELECT COUNT(*) > 0` — non-empty means skip the whole batch — and the insert loop executed row by row with no transaction. If the first seed failed part-way, the earlier rows had landed and the later ones had not; on the next start the table was non-empty, the gate skipped, and it stayed incomplete permanently. Neither the gate nor the loop notices that the row count disagrees with the seed file, and nothing is logged.

The fix aligns atomicity with the gate's granularity: the gate is per table, so the transaction is per table. `ResolveRowId` takes an optional transaction, because a lookup performed during the insert must run on the same transaction — otherwise it reads through a second connection and cannot see uncommitted rows. (The deferred pass runs after every table has committed and continues to pass none.)

### `Bee.Northwind`: the Browser head showed tofu boxes for Chinese labels

The browser sandbox has no system font to fall back to, and Inter carries no CJK glyphs, so under a Chinese-locale browser every field label rendered as boxes. The other three heads borrow PingFang or Noto CJK and were unaffected — the problem had always been there and only became visible when zh-TW language resources were added.

Embedding a subset of Noto Sans TC was the intended approach until two numbers came in: the Chinese actually displayed amounts to 24 keys (34 unique characters), and the smallest usable CJK font is 5.4 MB. Carrying 5.4 MB for 24 keys is out of proportion for a demo, so the Browser head pins `CurrentUICulture` to `en-US` and the labels fall back to the English captions on the `FormSchema` itself. Only the Browser head changes; the other three display Chinese correctly and continue to follow the system locale.

## Upgrade

Nothing to do. `ApiServiceOptions.RequireWireFrame` defaults to `false`, and every public API change in this release is additive.

To turn replay protection on, upgrade **both** ends first, then set the flag on the client and the server together:

```csharp
// Server and client, at startup — both, or neither.
ApiServiceOptions.RequireWireFrame = true;
```

Four limits are worth knowing before flipping it:

- The `Plain` format is not protected. The frame lives inside the encoded/encrypted envelope, which is what makes it tamper-evident; there is no equivalent for plaintext.
- A request that times out and is retried **fails** rather than quietly succeeding. That is the point of the mechanism, and a client that retries transparently needs to be aware of it.
- Anonymous calls are not sequence-checked.
- Within the timestamp check alone, a captured packet stays replayable for `WireFrameTimestampTolerance` (five minutes by default). The window has to absorb client clock skew — a desktop with misconfigured NTP is routinely minutes out — and narrowing the remaining gap is the sequence window's job, not the tolerance's.
