# Bee.NET 4.29.0 — Detailed Release Notes

[English](4.29.0.md) ・ [繁體中文](4.29.0.zh-TW.md) ・ [← CHANGELOG](../../CHANGELOG.md)

This document is the detailed version of the `[4.29.0]` entry in [CHANGELOG.md](../../CHANGELOG.md). The main CHANGELOG lists one line per change; this file keeps the full narrative — the *why*, the constraints, and the design context behind each change.

> `PluginSettings.xml` named types and nothing else. Which stage each plugin ran at came from reflection over the class, so the file could not answer the one question anyone opens it to ask. [ADR-035](../adr/adr-035-business-logic-plugin.md) had accepted that cost on the promise of a maintenance tool that would compute and display the stages — a tool that was never built, leaving the readability cost as a net loss. This release puts the stage in the file and binds one plugin to exactly one stage. What it gives up is named plainly, because ADR-035 called it that mechanism's only real advantage: a plugin can no longer carry state from `BeforeSave` to `AfterSave` in an instance field, because those are now two classes.

## Breaking changes

### `PluginItem` declares its stage, and one plugin binds to one stage

```xml
<PluginItem Type="Acme.Plugins.CreditLimitCheck, Acme.Plugins" Stage="BeforeSave" />
<PluginItem Type="Acme.Plugins.OrderSync, Acme.Plugins"        Stage="AfterSave" />
```

`Stage` is required, and the class must override that stage and no other. A check before saving followed by a notification afterwards is therefore two classes with no shared field between them: what the `After` class needs it reads or recomputes.

The reasoning is single responsibility rather than a type constraint. The four stage signatures differ only across the save and delete pipelines — `BeforeSave` and `AfterSave` both take `SaveContext` — so one class doing both was always possible. It stops being allowed because the two do different kinds of work, and because a file that names the stage is a file you can read for what runs where.

No migration guidance accompanies this, and none is needed: no `PluginSettings.xml` exists anywhere in the repository, packaged or sample, and the format has no consumers.

### Reflection stays, as the check rather than the source

Loading a chain now reconciles the declaration against the class, and refuses on any disagreement — the type overrides nothing, overrides more than one stage, declares no `Stage`, or declares one it does not override. The message names the stages the class actually overrides, so the fix is in the message.

Two gates enforce it, and they are not redundant. `SystemBusinessObject.SaveCustomizePluginSettings` rejects at save time, so the person editing the bindings learns immediately. `PluginSettingsResolver` rejects at resolve time, which is the only gate a hand-authored file ever passes — the packaged layer at `{DefinePath}/PluginSettings.xml` has no maintenance API at all.

The cost is honest and worth stating: changing which stage a class overrides now means changing the XML too. Previously redeploying the assembly was enough. The failure is loud rather than silent, and it lands on the person editing that file.

### API changes

- `Bee.Business.Form.FormPluginStage` is **removed**. The declaration type has to exist in `Bee.Definition`, where `PluginItem` lives, and the dependency runs Business → Definition. `Bee.Definition.Settings.PluginStage` replaces it as the single enum. Keeping the old name in the new namespace was rejected: two same-named enums produce `CS0104` in any consumer that uses both namespaces.
- `PluginStage.None = 0` is a sentinel for "no stage declared", rejected by both gates. It exists for diagnosis, not for compatibility: a missing XML attribute deserializes to the enum's zero value with no error, and reserving zero is what lets the message say "you declared no `Stage`" instead of comparing two stages that happen not to match.
- `PluginItem(string type)` becomes `PluginItem(string type, PluginStage stage)`, and `PluginItemCollectionExtensions.Add` likewise. No overload is kept — an entry point that builds a `PluginItem` without a stage is exactly what the change removes. The public parameterless constructor stays, for `XmlSerializer`'s reflection-only path.
- `PluginSettings.GetPluginTypes` and `CustomizeOverlay.GetPluginTypes` become `GetPluginBindings`, returning `IReadOnlyList<PluginBinding>` — a `readonly record struct` of type name and stage. Value copies, not the `PluginItem` instances: the settings object is process-wide cached, and handing out its items would invite mutation of what every session reads. The two-layer semantics are untouched — base chain first, then the tenant's, still no tombstone.
- `FormPluginChain.Create` takes the progId and `IReadOnlyList<FormPluginBinding>`; `HasStage` and `TypesForStage` take `PluginStage`.

**Binary compatibility: broken, and accepted.** Removing a public enum and changing constructor and method signatures breaks any compiled consumer. Business plugins have no consumer — the format shipped in 4.17.0, no definition file uses it in this repository, and nothing outside `src/` reads `PluginSettings`.

## Changed

### Plugins are constructed on demand

`FormPluginRunner` built the entire chain on first use, including plugins bound only to delete stages. That was necessary while a later stage had to find the same object; with one stage per plugin it is pure waste. A plugin is now constructed the first time its own stage runs, and not at all otherwise, so a save never constructs a delete-stage plugin. Construction still goes through `ActivatorUtilities`, so a plugin may declare injected dependencies beyond the three positional arguments.

Instances remain per operation and are never shared between calls, so no locking is needed. What they no longer carry is state across stages.

### The `DeleteContext.Snapshot` load condition is unchanged in behaviour

`FormBusinessObject.Delete` still asks the chain whether any plugin runs at a delete stage before deciding to load the snapshot. The answer now comes from the declaration rather than from reflection, and since the two are reconciled the value is identical to before.

## Documentation

[ADR-035](../adr/adr-035-business-logic-plugin.md)'s decision three is rewritten rather than superseded by a new ADR: this is a different answer to the same decision, and its other five decisions are untouched. The rewrite records what was given up, and that the readability compensation was never implemented — that being the direct reason for the change.
