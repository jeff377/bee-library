# Bee.NET 4.31.0 — Detailed Release Notes

[English](4.31.0.md) ・ [繁體中文](4.31.0.zh-TW.md) ・ [← CHANGELOG](../../CHANGELOG.md)

This document is the detailed version of the `[4.31.0]` entry in [CHANGELOG.md](../../CHANGELOG.md). The main CHANGELOG lists one line per change; this file keeps the full narrative — the *why*, the constraints, and the design context behind each change.

> This release replaces three **silent fallbacks with loud failures**. Each fallback looked harmless where it was written, and each one's cost appeared somewhere else: a figure rounded to decimals nobody chose, tenant overrides switched off while every request still succeeded, and a missing registration reported as a missing constructor. **Both breaking changes ship as a minor under the pre-stable policy.**

## Breaking Changes

### A company's default currency is required

`NumberFormatResolver` resolves an amount's decimals from its reference currency: the field's `CurrencyField`, else the master row's `sys_currency`, else the company's `DefaultCurrency`. Until now an empty company default currency was accepted, and the chain fell through to the framework default of two decimals.

It now throws `InvalidOperationException` when all three hold: the amount has no reference currency, a company is in context, and that company's `DefaultCurrency` is empty or whitespace. **With no company context at all** — a client before a company is entered, or `RoundingContext.ForCompany(null)` — the framework default still applies, because that is not a configuration error. The check does not depend on whether a currency master is deployed.

**Why a fallback was wrong here**: two decimals looks correct, but it is not a figure any currency of that company chose, and nothing downstream can tell. A home-currency amount (`home_amount`) rounds to the same wrong decimals.

**Why it fails at calculation rather than at load or company entry**: the framework does not write `st_company` — company master data is maintained outside it — so there is no write path to validate on. Rejecting at `EnterCompany` would also fail every call that only needs the company's name.

Where it surfaces:

| Path | Throws? |
|------|---------|
| Server-side save rounding (`FormBusinessObject` → `FormExpressionCalculator` → `RoundByKind`) | Yes |
| Client live computation (`FormLiveComputation`) | Yes — and it is **not** absorbed by the degrade path, which exists for authored expressions that fail, not for configuration errors |
| Display formatting in `NumericEdit` / `GridControl` | No — these build their context without a company and take the currency code as a parameter |
| Schema delivery (`NumberFormatApplier.Bake`) | No — amounts are never baked |

The framework does not pick a default currency, and `st_company.default_currency` still has no database default: whoever creates the company record supplies it.

**Compatibility**: binary compatible, and the public API is unchanged. `CompanyInfo.DefaultCurrency` still defaults to an empty string so the serializers can round-trip an unset value. The decision is recorded in [ADR-026](../adr/adr-026-numeric-semantics-rounding.md)'s revision record.

### `RepositoryFactory` delegates type resolution to `IRepositoryTypeResolver`

The prompt was SonarCloud's S107 (eight constructor parameters), but the change is not a parameter object. The seventh and eighth parameters (`customizeReader` / `sessionInfoService`), together with `ResolveFormRepositoryType`, `FindProgramItem` and `GetCustomizeId`, were one job: *progId → repository type, including the tenant customization overlay*. The business-object axis already had that job separated as `IBoTypeResolver`; the repository axis kept it inline in the factory. Extracting `IRepositoryTypeResolver` / `ProgramSettingsRepositoryTypeResolver` leaves the factory with construction alone.

Three design points:

- **The resolver takes the access token, not a customization id** — deliberately unlike `IBoTypeResolver`. The customization id may only come from the session, and a signature with no place to pass one in is what enforces that cross-tenant guard.
- **`typeResolver` is required.** A default that read only the base registry would mean a host that forgot to register the resolver loses every tenant's repository overrides at once, while every request keeps succeeding.
- **The factory checks what any resolver returns** derives from `DataFormRepository`, since the resolver is now replaceable.

API changes:

- `RepositoryFactory`'s constructor drops `customizeReader` / `sessionInfoService` and gains a required `IRepositoryTypeResolver typeResolver` before `cacheNotify`.
- **Removed**: `protected RepositoryFactory.ResolveFormRepositoryType`.
- **Added**: `IRepositoryTypeResolver`, `ProgramSettingsRepositoryTypeResolver`.

**Compatibility**: source- and binary-breaking — a compiled caller of the old constructor gets `MissingMethodException`. **Deployments that build the factory through `AddBeeFramework` are unaffected**; the hosting layer registers the resolver. Keeping the old constructor alongside a new overload was tried and rejected: it does not resolve S107, and `ActivatorUtilities` and the container would still pick the longer, old constructor.

## Fixed

### Hosting surfaces the dependency-injection failure

When `ActivatorUtilities` cannot satisfy a constructor parameter it throws an `InvalidOperationException` whose message names the missing service. `CreateConfigurableService` caught and discarded it, then tried the parameterless constructor; for a type without one, what finally surfaced was `MissingMethodException: Constructor on type ... not found` — nothing about a missing registration.

The catch now has an exception filter: it falls back only when the type declares a public parameterless constructor, and otherwise the original exception propagates unchanged. If the fallback itself fails, the original exception is attached as `InnerException`. Legacy implementations with only a parameterless constructor behave as before — `ActivatorUtilities` selects it on its own when present.

### `apps/Bee.Northwind`: `OrderBO` follows the framework's `isLocalCall` default

4.28.0 changed the `isLocalCall` default on `BusinessObject` and `FormBusinessObject` from `true` to `false`: constructing a BO directly is the one path that bypasses `ApiAccessValidator`, and trusting it by default left four second-line guards open on the path least in need of trust. `OrderBO` declared its own `= true`, so it **kept the behavior that had been deliberately removed** — with no compiler signal, since it is an independent default.

The demo's own exposure was limited (the only construction path passes the value explicitly), but `apps/Bee.Northwind` is written to be copied, and a template carrying a rejected default spreads further than the framework itself.

### `apps/Bee.Northwind`: order amounts display with two decimals

The order form showed `amount` as `252` and `total_amount` as `352`. Both `Order.FormLayout.xml` files (`Define/` and `Customize/northwind-demo/`) are hand-written and carried no `NumberKind`. The framework copies `NumberKind` from a `FormField` only when it **generates** a layout; a hand-written layout is not filled in at runtime, so the editors treated both fields as `NumberKind.None`.

| Field | Added | Why that is enough |
|-------|-------|--------------------|
| Detail `amount` (`LayoutColumn`) | `NumberKind="Amount"` | Grid cell text always goes through the number formatter regardless of `ControlType`; the currency branch resolves from the currency master and the company's default currency |
| Header `total_amount` (`LayoutField`) | `NumberKind="Amount"`, `ControlType="NumericEdit"` | `LayoutField.ControlType` defaults to `TextEdit`, and only `NumericEdit` applies a number format |

Both files change because a customized layout replaces the packaged one outright rather than merging with it.

Still unformatted, knowingly: `unit_price` (a company-sourced kind reads only a baked `NumberFormat` in the grid, which a hand-written layout does not carry, so adding `NumberKind` alone would change nothing), and the list's Total Amount column (the list layout is generated from the schema, whose `total_amount` declares no `NumberKind`). Having the framework fill a hand-written layout from its schema at runtime would address both; that is not part of this release.

## Changed

### `apps/Bee.Northwind`: the demo company has a default currency

The demo company's `default_currency` is `USD` (`NorthwindCredentials.DefaultCurrency`), and `Define/CurrencySettings.xml` — copied from the framework's scaffold defaults — is deployed. Without a currency master the resolver never consults the company's currency, so a required-but-unused value would have been all the demo showed.

The order `amount` binds no currency field, so its two decimals now come from the path the framework intends: company currency `USD` → currency master → `0.01`. Before this release it also showed two decimals, but through the framework default, with the currency playing no part.

An existing `northwind.db` is backfilled at startup rather than requiring deletion.

### `tools/Bee.LoadTests`: SonarCloud S2077 and S1075

These had gone unreported since the tool was created, because the Sonar analyzer runs only in the full CI mode.

- **S2077** — `SchemaPreparer.CreateDatabaseIfMissing` interpolated four strings of two different kinds. The PostgreSQL existence probe queries a *value* and is now parameterized. The three `CREATE DATABASE` statements interpolate an *identifier*, which no engine accepts as a bind parameter; the name is now validated by `GuardDatabaseName` right where it is interpolated, with a length cap of 63 (PostgreSQL's, the shortest of the three engines).
- **S1075** — the `serve` listen address moves from `Program.Serve` into `TargetOptions.ServeUrl`, with the default port as a named constant. `--help` points at the setting instead of repeating the default.

Non-shipping tool (`IsPackable=false`).

## Upgrade notes

Deployments that build the factory through `AddBeeFramework` need no code change. Two cases to check.

**Every company needs a default currency.** Without one, saving a document with a computed amount — and live computation in the client — throws after the upgrade. Set it before upgrading, choosing the right code for each company; the framework does not pick one:

```sql
UPDATE st_company SET default_currency = 'USD'
 WHERE default_currency = '' OR default_currency IS NULL;
```

The `IS NULL` arm is for Oracle, which stores an empty string as `NULL`.

**Code that constructs `RepositoryFactory` directly** passes a resolver in place of the two customization dependencies:

```csharp
- new RepositoryFactory(services, defineAccess, dbAccessFactory, connectionManager, router,
-     cacheNotify, customizeReader, sessionInfoService);
+ new RepositoryFactory(services, defineAccess, dbAccessFactory, connectionManager, router,
+     new ProgramSettingsRepositoryTypeResolver(defineAccess, customizeReader, sessionInfoService),
+     cacheNotify);
```

Pass both `customizeReader` and `sessionInfoService` when the deployment uses tenant customization: they are optional on the resolver, and leaving them out turns tenant repository overrides off without an error. A subclass that overrode `ResolveFormRepositoryType` implements `IRepositoryTypeResolver` instead.
