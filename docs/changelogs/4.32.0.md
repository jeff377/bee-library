# Bee.NET 4.32.0 — Detailed Release Notes

[English](4.32.0.md) ・ [繁體中文](4.32.0.zh-TW.md) ・ [← CHANGELOG](../../CHANGELOG.md)

This document is the detailed version of the `[4.32.0]` entry in [CHANGELOG.md](../../CHANGELOG.md). The main CHANGELOG lists one line per change; this file keeps the full narrative — the *why*, the constraints, and the design context behind each change.

> Quantities and weights now take their decimal places only from their unit. A field marked `Quantity` or `Weight` must bind a `UnitField`, and the company no longer supplies those decimals: a company has a home currency to fall back to, but no default unit. This lines the unit side up with how amounts already resolve by currency. **Both breaking changes ship as a minor under the pre-stable policy.**

## Breaking Changes

### Quantity and weight fields must bind a unit

A field marked `NumberKind.Quantity` or `NumberKind.Weight` must name the field holding its unit in `FormField.UnitField`. A value that needs no unit — a count whose unit is implied — is a plain numeric field with no `NumberKind`.

**Why**: amounts and quantities resolved their decimals along two chains that looked parallel but fell back to different things. An amount's chain yields a currency code at every step — the field's `CurrencyField`, the master row's `sys_currency`, the company's `DefaultCurrency` — so the company only chooses *which currency*, and the currency master decides the decimals. A quantity's chain went from its `UnitField` straight to the company's decimal places, so the company decided the decimals directly. Units have nothing to play the role of the home currency: a company has a default currency, but no default unit, and one order can sell PCS and KG side by side. The part of the currency chain that carries over to units is the binding itself. SAP draws the same line: the ABAP Dictionary requires every `QUAN` field to name a reference unit field.

Where a missing binding surfaces:

| Path | Throws |
|------|--------|
| Server-side save rounding (`FormBusinessObject` → `FormExpressionCalculator` → `RoundByKind`) | Yes, for a computed quantity or weight field |
| Client live computation (`FormLiveComputation`) | Yes — and it is **not** swallowed by degrade, which exists for mistyped expressions, not configuration errors |
| `NumericEdit` / `GridControl` display | No |
| Schema delivery (`NumberFormatApplier.Bake`) | No — quantities and weights are never baked |

This mirrors a company with no default currency, which also throws when an amount is computed and not when it is displayed. The runtime check only sees the fields it rounds, so an input-only quantity with no unit does not throw; the DefineEditor check below catches those at design time.

**Compatibility**: binary compatible, and the public API is unchanged. The decision is recorded in [ADR-026](../adr/adr-026-numeric-semantics-rounding.md)'s revision record.

### Quantity and weight decimals no longer come from the company

With the binding required, the company drops out of quantity and weight resolution altogether:

| Case | Before | Now |
|------|--------|-----|
| The row's unit code is empty | Company decimals, else the framework default | Not rounded — `RoundByKind` returns the value unchanged |
| The unit code is not in `UnitSettings` | 0 | Framework default (`Quantity` 0, `Weight` 3) |
| No unit master is deployed | Company decimals, else the framework default | Framework default |
| `Quantity`/`Weight` entries in `CompanyInfo.NumberFormats` | Used for unbound fields | No effect |
| `NumberFormatApplier.Bake` on a quantity or weight field | Baked with company decimals when unbound | Never baked |
| `RoundByKind(value, kind, company)` for a quantity or weight | Rounded to company or framework decimals | Returned unchanged (there is no unit code) |

**Why an empty unit is not rounded**: a new detail line can be computed before its unit is chosen. Rounding it to a decimal count that no unit chose would discard digits the real unit keeps — and unlike an amount, there is no home currency to resolve against instead.

**Why an unknown code resolves to the framework default**: it matches the currency side, where a code missing from `CurrencySettings` resolves to 0.01. `UnitSettings.GetDecimals` keeps its own plain-lookup fallback of 0; the resolver no longer uses it.

**Compatibility**: binary compatible, and the public API is unchanged. Behaviour changes for callers that relied on the company's quantity decimals, rounded quantities through the company overload, or bound a unit code that the master does not define.

## Added

### `tools/DefineEditor`: unit binding check

`FormSchemaValidator` reports an error when a quantity or weight field has no `UnitField`, and when its `UnitField` does not name a field of the same table with the same casing. Both mirror how the runtime reads the unit: `FormExpressionCalculator` looks it up in the row being computed, by declared field name, case-sensitively, so a unit field on another table or with different casing resolves as an empty unit code. Which kinds need a unit comes from `NumberKindProfile.GetDecimalsSource`, the same source the calculator uses.

A new `tests/Bee.DefineEditor.UnitTests` covers the check; it also brings DefineEditor into the CI build, which no workflow built before. Non-shipping tool.

## Changed

### `samples/Avalonia.DemoCenter`: the number-format demo binds units

The quantity and weight columns in `NumberFormatModule` bind unit fields (PCS, KG) and resolve their decimals per row, so the company toggle no longer changes them.

## Upgrade notes

Schemas with no `Quantity` or `Weight` field need no change. Three things to check.

**Every quantity or weight field binds a unit field of the same table.** Search the `FormSchema` files for `NumberKind="Quantity"` and `NumberKind="Weight"`; a computed one without `UnitField` throws when it is saved or computed live:

```xml
- <FormField FieldName="qty" Caption="Quantity" DbType="Decimal" NumberKind="Quantity" />
+ <FormField FieldName="qty" Caption="Quantity" DbType="Decimal" NumberKind="Quantity" UnitField="qty_uom" />
```

A count whose unit is implied — pieces, boxes — is better as a plain numeric field: drop `NumberKind` instead of inventing a unit column.

**Code that rounds a quantity or weight** passes the row's unit code through a `RoundingContext` carrying `UnitSettings`:

```csharp
- var qty = NumberFormatResolver.RoundByKind(value, NumberKind.Quantity, company);
+ var qty = NumberFormatResolver.RoundByKind(value, NumberKind.Quantity, ctx, unitCode);
```

The company overload has no unit code and now returns the value unchanged.

**Company number formats and unit codes.** `Quantity` and `Weight` entries in `st_company.number_formats_xml` no longer take effect; they can stay, since decimals now come from `UnitSettings`. A bound unit code that is missing from `UnitSettings` now rounds to the framework default, which for `Weight` is 3 rather than 0.
