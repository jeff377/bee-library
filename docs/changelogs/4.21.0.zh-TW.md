# Bee.NET 4.21.0 — 詳細變更說明

[English](4.21.0.md) ・ [繁體中文](4.21.0.zh-TW.md) ・ [← 版本變更記錄](../../CHANGELOG.zh-TW.md)

本文是 [CHANGELOG.zh-TW.md](../../CHANGELOG.zh-TW.md) 中 `[4.21.0]` 條目的詳細版。主 CHANGELOG 每項變更一行，本檔保留完整脈絡——**為什麼**要改、有哪些限制、以及背後的設計考量。

> 本版來自一次全框架體檢，而不是功能規劃，這決定了它的形狀：沒有新能力，但有一整批「還沒被人踩到、可是確實是錯的」東西。
>
> 重心在**並行正確性**。有四處各自假設了「只有一個使用者」「只有一個請求」或「只有一個呼叫端」，而每一處都是「單一 process 服務多人」的一般部署就會觸達的。圍繞它的是一批移除與改名（全部是原始碼層級的破壞性變更）、兩個「寫進契約卻從未接上」的機制，以及三處「成本跟錯了量」的效能問題。

## 安全性

### 漏掉的那一個 `EXEC` 字串常值

SQL Server 的「移除欄位 DEFAULT 條件約束」會組出一段批次，並經 `EXEC('...')` 執行。在那個常值裡面，只對識別碼加中括號是不夠的——名稱中的單引號仍會提前終結外層常值。同一個方法內相鄰的兩個常值本來就有做跳脫，漏的是這一處。

觸達面很窄：它位於結構升級路徑，而那是 `LocalOnly`，資料表名稱來自定義檔而非請求。之所以還是要修，是因為「很窄」不是一個能撐過重構的性質。

### `ApiKeyCache` 把攻擊者指定的 miss 快取了五分鐘

該快取的 key 就是呼叫端放在 `X-Api-Key` 標頭裡的識別碼，而 gate 每個請求都會跑，因此**每一筆負向條目都由攻擊者指定**——且該快取沒有容量上限。每個隨機識別碼保留五分鐘，是一根沒有對應效益的記憶體槓桿。

負向快取保留下來，但縮為一分鐘，因為它確實能解決它當初要解決的情境：設定錯誤的 client 拿著同一把已撤銷的金鑰重試。它從來就擋不住**隨機**識別碼的探測——不論 miss 保留多久，每個不重複的 id 都恰好打一次資料庫。原本的論證把這件事說反了，本次連同數值一併更正程式碼註解。

## 並行正確性

### per-session 的 client 狀態是 process-wide

`ApiClientInfo.ApiEncryptionKey` 與 `UserTimeZoneId` 是 static。在 `BeeBlazorProviderMode.Remote` 下，這代表最後登入者勝出：先前使用者的 `Encrypted` 請求會以別人的 session key 加密，server 端 HMAC 驗證失敗，該使用者等於被鎖到重新登入為止。

動手前得先更正一個前提：`ApiClientInfo` 上的三個 static 不是同一類東西。`ApiEncryptionKey` 與 `UserTimeZoneId` 是 per-user，而 `ApiKey` 是 per-deployment——它讀自設定檔，識別的是應用程式而非人。把它也搬成 per-session 會是錯的，不是更安全。

修法是新增 `ApiSessionContext` 承載那兩個 per-user 值，並附一個共用的 `Ambient` 實例。`ApiConnector` 與三個具象 connector 各新增一個接它的**建構子多載**——刻意不是在既有建構子加 optional 參數，那是二進位破壞性變更（4.20.0 的 `FormLiveComputation` 正是那個形狀）。未傳 session 的 connector 退回 `Ambient`，因此單使用者宿主的行為逐位元不變。`BeeApiConnectorFactory` 由 singleton 改為 **scoped** 並注入 scoped 的 context；它的方法簽章完全不動，呼叫端零改動。

session 傳 `null` 會擲例外，而不是靜默退回 `Ambient`。靜默退回會讓一個設定錯誤的多使用者宿主「看起來能跑、實際共用金鑰」，而那正是本次變更要防的失敗。

被否決的替代方案是「以 access token 為 key 的 process-wide 字典」。它只是把 process-wide 可變狀態換成 process-wide 可變**字典**——同一個形狀，還多出「誰在什麼時候清掉」的問題，而那正是先前那個無界鎖定計數表的來源。

### 冷 key 會每個呼叫端各建一份

`ObjectCache<T>.Get` 與 `KeyObjectCache<T>.Get` 是 read-create-write，而底層 provider 並未提供原子的 get-or-create。多個請求同時觸達一個冷 key，於是各自建出自己的物件——各自反序列化同一份定義檔，或各發一次相同的查詢。

浪費的運算還是次要的。**重複實例才是真正的缺陷**：`SessionInfo` 正是這樣快取的，經其中一份做的 `EnterCompany` 對持有另一份的請求完全不可見；而以參考相等判斷「是否重新載入」的解析器，會把重複實例讀成一次從未發生的變更。

去重以 key 為粒度，且只在建立進行中存在，因此以 access token 為 key 的快取不會累積任何東西——這點很重要，因為那種 key 的數量和 session 一樣多。

### `EnterCompany` 在解析完公司之前就公告了它

session 物件由同一個 access token 的所有並行請求共用，而 `CompanyId` 與 `Roles` 正是授權判斷讀的兩個輸入。`EnterCompany` 把寫入與查詢交錯，留下一段橫跨三次可能觸及資料庫之呼叫的窗口，期間並行請求可能以「**新**公司 + **前一家**公司的角色」做出授權決定。

角色、能力與記錄範圍身分現在全部先解析完，再一起寫入 session。

### 另外兩處交出或重建共用定義狀態的地方

`FormTable.RelationFieldReferences` 的反向索引建立在無保護的 null 檢查之後。兩個觸碰同一份快取 schema 的請求可能各建一份、拿到不同實例，而建立過程的驗證例外會從一個看起來只是讀取的 property getter 冒出來。

`FormDefinitionLoader.GetLocalizedSchemaAsync` 在未指定語言時直接回傳共用的快取 schema，儘管它的文件寫著「絕不交出快取實例」。`CultureInfo.InvariantCulture.Name` 是空字串，因此那是最常走到的路徑，不是邊角情形。

兩者都違反了[定義資料初始化後不可異動](../development-constraints.zh-TW.md)那條規則：所有經 `IDefineAccess` 取得的都是 process-wide 共用實例，呼叫端一 mutate 就會跨 session 洩漏。

## 破壞性變更

### 一批零消費端的公開表面

以符號級掃描全 repo 的結論是：**沒有任何完全死掉的型別**——`IDE0051` / `IDE0052` 搭配 `TreatWarningsAsErrors` 已經守住 private 與 internal 那一層。掃出來的是「沒有任何人到得了的公開 API」：

- **`Bee.Base.MemberPath`**、**`Bee.Base.ConnectionTestResult`**——全 repo 零參考、無文件記載。
- **`DataTableExtensions.NormalizeDateTimeMode(DataSet)`**——冗餘多載，`DataTable` 的那個仍在使用。
- **`Bee.Api.Core.Registry.ApiContractRegistry`**——`Register<>` 從未被呼叫，map 恆為空，而每個 payload 都要白跑一次 `GetInterfaces()` 迴圈去查它。它宣稱的用途（把商業物件回傳的純物件轉成 API 型別）`ApiOutputConverter` 已經在做。它不是刻意保留的擴充點，是被取代的重複實作。
- **`Bee.Api.Core.Messages.ApiErrorInfo`**——wire 上的錯誤形狀早已由 `JsonRpcError` 取代。它僅存的生命跡象是一個「建構它、再把欄位讀回來」的測試：足以在覆蓋率報告上顯示為已測試，但證不到有人在用。它另被註冊為 wire contract，卻從 wire 型別閉包到不了，因此漂移閘門也沒標記它。
- **`Bee.Api.Core.Messages.ApiCallContext.ShouldValidateEncoding`**——零呼叫端的計算屬性。它取反的 `IsLocalCall` 維持不變。
- **`Bee.Definition.Settings.AuditLogOptions.ExecEnabled`**——已出貨的設定合約，卻沒有任何讀取點。它宣告的執行軸從未實作，部署者讀它的 XML doc 會以為有一個實際上什麼都不做的開關生效。它的五個兄弟旗標各有真正的消費點；架構總覽的「六軸資料軌跡」一併更正為五軸，那本來就是它實際列出的數量。
- **`Bee.Db` 的五個 `Dml` 介面**（`IFromBuilder`、`ILimitBuilder`、`ISelectBuilder`、`ISortBuilder`、`IWhereBuilder`）——各只有一個實作，且沒有消費端以介面型別引用，因此實作它們達不到任何效果。具象 builder 不變。`IFormCommandBuilder` 與 `IParameterCollector` 保留：那兩個確實被當成型別消費。

### 稽核軸與定義軸離開商業物件介面

移除 `ILogBusinessObject` 與 `CreateLogBO` 擴充方法，以及 `ISystemBusinessObject` 的 `GetDefine` / `SaveDefine`。

軸介面存在的理由只有一個：讓一個商業物件呼叫另一個。查稽核記錄本質上不是商業物件之間會做的事，取定義同理——那直接經 `IDefineAccess` 即可。

**對應的 public 方法全部保留在具象商業物件上**，因此 `JsonRpcExecutor` 對外開放的表面不變。遠端呼叫端看到的方法完全一樣，縮小的只有 in-process 的介面表面。

`Login` 則作了相反的裁決、留在 `ISystemBusinessObject` 上：背景作業會以某身份登入以建立連線，再模擬該使用者操作，因此它確實有真正的內部呼叫端。兩個表面彼此獨立——`[ApiAccessControl]` 描述外部呼叫端能觸達什麼，軸介面描述內部呼叫端能觸達什麼，兩者不互相蘊含。

### 三個公開型別改名以避開撞名

| 原名 | 新名 |
|------|------|
| `Bee.Definition.Identity.IAuthorizationService` | `ICompanyAuthorizationService` |
| `Bee.ObjectCaching.Services.AuthorizationService` | `CompanyAuthorizationService` |
| `Bee.Base.Tracing.TraceListener` | `TraceDispatcher` |

舊名分別撞上 `Microsoft.AspNetCore.Authorization.IAuthorizationService`（ASP.NET Core 宿主預設就有它）與 `System.Diagnostics.TraceListener`。

兩處撞名都以 `CS0104` 現形在「同時 `using` 兩邊命名空間」的唯一位置：消費端註冊框架服務那段。這不是巧合，也正是「在框架內看起來沒問題的名字，仍可能是不該公開的名字」的原因。

**沒有 type forward。** 新名也讓它與 `IDeploymentAuthorizationService` 的對照讀得出來：一個在公司內授權，一個對整套安裝授權。`SysInfo.TraceListener` 與 `ITraceListener` 維持原名——它們並不撞名。

### `isLocalCall` 不再預設為 `true`

`IBusinessObjectFactory.CreateBusinessObject` 與 `CreateFormBO` / `CreateSystemBO` 擴充方法移除該預設值。本地呼叫會直接跳過 `ApiAccessValidator`，因此兩參數的寫法會靜默產生一個不做任何存取檢查的商業物件——而那正是自行撰寫 dispatcher 的宿主最先會寫出來的形式。

商業物件的建構子暫時保留預設值。直接 `new` 比呼叫工廠更像刻意行為，且改動它會波及每一處直接具現化。

### `SerializableData*` 改為 internal

五個 `MessagePack.SerializableData*` 型別（58 筆公開 API）是 wire 為 `DataSet` / `DataTable` 準備的中間形狀，只有並排的 formatter 用得到。[ADR-037](../adr/adr-037-wire-explicit-registration.md) 已把該資料夾 28 個型別中的 24 個收成 internal，這五個是僅存的破口，且框架內 `Bee.Api.Core/MessagePack/` 之外零引用。

### `StringUtilities.IsEmpty(object?)` → `IsEmptyText`

兩個 `object?` 多載是先把值轉成字串再判斷文字，與 `ValueUtilities.IsEmpty(object)` 問的不是同一個問題——兩者對 `Guid.Empty` 與 `DateTime.MinValue` 的結論相反，而舊名稱看不出呼叫端指的是哪一個。字串多載維持原名；框架內受影響的呼叫點只有一處。

## 宣告了但從未接上

以下兩項都寫進了契約，而背後都沒有實作。兩者都不是本輪產生的迴歸，而是體檢「讀契約、再去找對應程式碼」時翻出來的缺口。

### 公司數值格式套用在空氣上

`NumberFormatApplier` 自先前某版把 server 端的 bake 移除、並註明改由需求端接手之後就不再執行。需求端一直沒有補上——於是公司層級的數值格式對任何 head 都不生效，安靜地跨越了好幾個版本。

`FormDefinitionLoader.GetLocalizedSchemaAsync` 現在於兩條路徑（含空語系的早退）都會套用。公司來源是新增的 `CompanyAccessor` init 屬性，它收的是**委派而非值**，因為進入的公司會在 session 存續期間變動。Avalonia 與 Blazor 兩個 head 不需自行改動即受益。

### `-32002` 與 `-32003` 從未被拋出

[ADR-012](../adr/adr-012-session-company-context.md) 在 4.4.0 就把 `CompanyNotEntered`（`-32002`、HTTP 409）與 `CompanyAccessDenied`（`-32003`、HTTP 403）公告為前端契約的一部分。框架內從未有任何地方拋出它們。

`EnterCompany` 擲的是 `InvalidOperationException`；`RepositoryDatabaseRouter` 更是把錯誤碼的**名稱**當成訊息字串寫死——`throw new InvalidOperationException("CompanyNotEntered")`，還有測試釘住了那個字串。兩者都落在 `IsUserFacingException` 讀的 BCL 白名單內，因此都被對映成 `UserMessage`（`-32099`）。可見的結果是：使用者沒進公司就開表單，會看到一個寫著 "CompanyNotEntered" 的訊息框，而前端沒有任何可據以導向的東西。

現在兩者各自擁有專屬例外型別（`Bee.Base.Exceptions.CompanyNotEnteredException`、`CompanyAccessDeniedException`）、專屬的 `MapException` 分支與 client 端重建。

**這會改變前端在這兩種情況下收到的錯誤碼**，由 `-32099` 變為 `-32002` / `-32003`。原本靠訊息文字比對的 client 會不再匹配；那正是本次修正的目的。

## 效能

### 運算式求值快 4.7 倍

先前每次求值都把整列的所有欄位交給引擎，而非運算式實際引用的那幾個，成本因此與**欄數**成正比、與運算式無關。實測 30 欄 / 5 計算欄 / 1000 列：57.2 ms → 12.2 ms。

### 權限查詢不再隨部署規模惡化

`CompanyRolePermissions` 是存在 process-wide 快取的不可變快照，其授權筆數為 角色數 × 模型數——在 ERP 是數千到數萬，而每次檢查都會全部掃過。索引現在於建構時建好一次，查詢成本由 O(公司的授權筆數) 變為 O(使用者持有的角色數)：200 角色 × 100 模型下由 23.4 µs 降為 0.08 µs，且不再隨部署成長而變差。

### 未變更的列攜帶了兩份相同的值

MessagePack 與 JSON 兩個寫入端都對 `Unchanged` 列同時送出 Current 與 Original，而兩個讀取端都只由 Current 還原。且 `DataFormRepository.GetData` 回傳前呼叫 `AcceptChanges()`——這個行為寫進了 `IGetDataResponse` 的契約——因此**每一筆從資料庫讀出的列都是 Unchanged**。讀取路徑的 payload 與序列化成本原本都是應有的兩倍。

讀取端未變動，而且不論本版或舊版本來就只讀 Current，因此變小的 payload 舊 client 一樣讀得懂。

有一個測試斷言的正是舊行為、名稱也照著取。那不是需求，是把缺陷寫成規格；本次已反轉，而涵蓋真正需求（round-trip 保真）的那個測試未動且仍通過。

## 修正

### `WhereBuilder` 遺失 `SecondValue` 與 `IgnoreIfNull`

當查詢帶有 `selectContext` 而需要改寫條件的欄名時，改寫過程丟掉了兩個屬性。`BETWEEN` 因此失去上界，`IgnoreIfNull` 條件則變成 `= NULL`——在 SQL 裡永不成立，於是查詢靜默回傳零筆，而不是忽略該條件。

### 三處吞掉所有例外的 `catch`

client 的端點探測把任何錯誤都當成「伺服器連不上」，並把使用者送去連線設定畫面；快取的檔案監看 token 把任何錯誤都當成「無已知寫入時間」；`DataTable` 的 JSON 轉換器把任何錯誤都當成「原值放行」。三者現在都只捕捉它們原本要處理的失敗，其餘會浮現，而不是被報成別的東西。

### 五處函式庫 `await` 回到了呼叫端的 context

五處 `await` 漏了 `ConfigureAwait(false)`，而它們正位於 UI 宿主經 `JsonRpcExecutor.Execute` 觸達的路徑上——該方法會阻塞在非同步核心上，此時回到被捕捉的 `SynchronizationContext` 就是教科書死鎖。周邊程式碼本來就在遵循這個慣例。`Execute` 現在於文件註明它會阻塞，並指引非同步呼叫端改用 `ExecuteAsync`。

### `DatabaseSettingsChanged` 每次載入都觸發

它唯一的發布者是設定快取的載入路徑，而 `DbConnectionManagerService` 收到後會清空連線快取——且是在它自己的 `GetOrAdd` value factory 內被觸達，因此每次設定快取 miss 都會丟棄先前建立的所有連線項目。現在改為真正重新載入時才觸發，那正是外部編輯得以傳播到連線快取的機制。`DbConnectionManagerService` 另實作 `IDisposable` 並退訂：static 事件會持有訂閱者直到行程結束。

## 升級

改名——機械式替換，無行為變更：

```diff
- Bee.Definition.Identity.IAuthorizationService
+ Bee.Definition.Identity.ICompanyAuthorizationService

- Bee.ObjectCaching.Services.AuthorizationService
+ Bee.ObjectCaching.Services.CompanyAuthorizationService

- Bee.Base.Tracing.TraceListener
+ Bee.Base.Tracing.TraceDispatcher

- StringUtilities.IsEmpty(object?) / IsNotEmpty(object?)
+ StringUtilities.IsEmptyText(object?) / IsNotEmptyText(object?)
```

需要做決定而非替換：

- **每一處 `CreateBusinessObject` / `CreateFormBO` / `CreateSystemBO` 呼叫都必須言明 `isLocalCall`。** 從請求觸達的一律傳 `false`；`true` 會完全跳過 `ApiAccessValidator`。
- **若你呼叫過 `CreateLogBO` 或 `ISystemBusinessObject.GetDefine` / `SaveDefine`**，改走具象商業物件、`IDefineAccess`，或經 JSON-RPC——方法本身沒有變動。
- **若你的前端是以 `-32099` 處理「尚未進入公司」**，請加上 `-32002` 與 `-32003`。舊行為靠訊息文字比對，新錯誤碼才是 [ADR-012](../adr/adr-012-session-company-context.md) 當初訂下的。
- **若你在「單一 process 服務多人」的宿主中自行建構 connector**，請為每個使用者傳入自己的 `ApiSessionContext`。不傳會共用 `Ambient`，那只對單使用者宿主正確。使用 `BeeApiConnectorFactory` 的 Blazor Server 宿主由 scoped 註冊直接取得，無需改動程式碼。
- **若你引用過 `ApiErrorInfo`**，改用 `JsonRpcError`。

不需要 server 與 client 同版部署：本次 wire 變更移除的是一個從來沒有讀取端消費的值，兩個方向皆然。
