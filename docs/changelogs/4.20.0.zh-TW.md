# Bee.NET 4.20.0 — 詳細發行說明

[English](4.20.0.md) ・ [繁體中文](4.20.0.zh-TW.md) ・ [← CHANGELOG](../../CHANGELOG.zh-TW.md)

本文是 [CHANGELOG.zh-TW.md](../../CHANGELOG.zh-TW.md) 中 `[4.20.0]` 條目的詳細版。主 CHANGELOG 每項變更只留一行；本檔保留完整敘事——WHY、限制，以及每項變更背後的設計脈絡。

> 本版有三條主線。wire 型別白名單的一個反序列化漏洞被關上。wire 上的 `object` 值不再自報型別，改走判別式封套——這正是它們能在「沒有動態碼」的 runtime 上運作的原因。運算式抽象下沉至 `Bee.Base`，只讀定義的消費者不再繼承一個運算式引擎。
>
> 第一項是安全修正，另兩項是把上一版開始畫的邊界收尾。三者都會被呼叫端觀察到：兩項改 wire、一項改命名空間；此外框架登入有了可用的預設實作，對從未覆寫過的部署是行為變更。

## 安全性

### 型別白名單只檢查了外層型別

`ApiPayload.TypeName` 讓呼叫端指定 payload 該被反序列化成什麼型別。這是典型的反序列化 gadget 形狀，而框架一直以來的答案是白名單：型別必須落在允許的命名空間內才接受。

白名單套用的對象是 assembly-qualified name 第一個逗號之前的字串——理由是那個逗號分隔型別與組件。**對泛型型別而言並非如此。** 具現泛型的 assembly-qualified name 會把每個參數自己的 assembly-qualified name 包在中括號內，而**參數的逗號排在前面**：

```
Bee.Base.Collections.Dictionary`1[[Disallowed.Type, Other.Assembly]], Bee.Base
                                                  ↑
                                            第一個逗號在這裡
```

切在那裡得到 `` Bee.Base.Collections.Dictionary`1[[Disallowed.Type ``，仍以 `Bee.Base.` 開頭因而通過。參數從未被檢查，接著 `Type.GetType` 解析整串名稱——連組件一起。

有三件事讓它比「一個小的解析瑕疵」嚴重：

- **未認證即可觸達。** `System.Login` 標 `[ApiAccessControl(Public, Anonymous)]` 且位於免授權集合內。存取驗證刻意跑在解密之前，但它的對象是**方法**、不是 payload 的型別名；payload 還原緊接在後，而它才是消費 `TypeName` 的地方。
- **失效方向是放行。** 解析器看不懂的名稱產生的是一個恰好會通過的片段，而不是一次拒絕。
- **同一個形狀存在兩份。** 本輪開發期寫的 `WireValueFormatter` 從 `SafeTypelessFormatter` 接手逃生門時，逐字複製了同樣的切法。新程式碼從舊程式碼複製了缺陷。

修正以括號感知的解析器取代切割：收集名稱指涉的**每一個**型別——外層型別、每個泛型參數（遞迴）、陣列元素——全部通過才放行；解析不出來的名稱一律拒絕。另設巢狀深度與名稱長度上限，讓精心構造的名稱無法驅動無界的工作量。`SafeMessagePackSerializerOptions` 中「對已解析的 `Type` 檢查」那一半同步比照處理：改為走型別的**形狀**而非測試單一 `FullName` 字串，因為具現泛型的 `FullName` 內嵌了它的參數，測那一個字串只檢查得到外層。逃生門的寫入端原本也是測 `FullName`，現在改用同一套形狀走訪——一個安全邊界的兩端，不該對「自己在檢查什麼」有不同認知。

自 4.0.2（2026-04-12）起存在。無已知的實際利用；白名單的存在使可觸達範圍受限於伺服器 probing path 上實際部署了哪些組件。

**這是止血，而且刻意標示為止血。** 白名單真正的弱點不在解析器，而在它表列的**單位**：它列的是**命名空間**，於是接受集合等於五個命名空間下的全部 public 型別——一個沒有人維護、任何人新增型別就會變大的數字。與此同時，合法會跨 wire 的型別集合現在是**精確已知**的，因為 [ADR-037](../adr/adr-037-wire-explicit-registration.md) 要求每一個都必須註冊。長效的修法是讓 `TypeName` 對那份註冊表查表，徹底取消 `Type.GetType(任意字串)`——到那時字串解析就不再是安全邊界。那屬 wire 層級的設計變更，另案處理。

### 鎖定計數表是一個未認證的記憶體槓桿

`LoginAttemptTracker` 以呼叫端提供的 user id 為 key，而 `System.Login` 是匿名的——表內每一筆條目都是攻擊者指定的。移除只有兩條路徑：該使用者登入成功，以及**後續某次以同一把 key 進來時**發現鎖定已過期。**未達鎖定門檻的條目根本沒有到期時間**，也沒有任何東西會清掃它——於是一串不重複的隨機 user id 就能讓它無限成長（每個請求約一百位元組），而上述兩條移除路徑永遠不會觸發，因為攻擊者不會重複同一個 id。

三項改動：條目自帶到期時間並依排程清掃，不再只依賴「同一把 key 再次被提及」；失敗計數以視窗計算，相隔數月的打字錯誤不再累積成鎖定；追蹤帳號數設有上限。

**上限刻意只擋新帳號。** 若為了騰位置而驅逐既有條目，等於把同一個槓桿以更糟的形式交回去——灌一堆不存在的 id 進去，你真正想攻擊的那個帳號就失去鎖定狀態。洪泛期間不收新帳號，代價是尚未出現過的帳號暫時失去鎖定追蹤，這是兩害相權的輕者。

這個問題實際上是 4.18.0 引入的：tracker 更早就存在，但從未被註冊，所以 `RecordFailure` 從不執行。把它設為預設註冊，等於把一個沒人用的類別變成活的。

### API key gate 失效現在看得見

沒有啟用中的金鑰時，gate 接受任何非空的 `X-Api-Key`。這個退路是刻意的——它讓部署得以在發出第一把金鑰之前先升級。但**停用最後一把啟用中的金鑰會抵達同一個狀態**，而那是輪替的正常步驟；唯一的訊號是 `UseBeeFramework` 在啟動時記的一行 warning。**在 runtime 發生的降級完全沒有產物**：沒有 log、沒有 audit、營運端觀察不到任何行為差異。

現在停用最後一把金鑰會記一筆 error 並指名該金鑰。啟動檢查在非 Development 環境也由 warning 改為 error——它區分的是「有沒有 API key gate」，那不是 warning 該承載的量級。

**啟動刻意不設為失敗。** 前一輪體檢提的正是「非 Development 環境直接啟動失敗」，但那會讓每一個尚未發出金鑰的部署一升級就起不來——而那正是這個退路要服務的族群。要做成硬失敗，該放在 major 版並附 opt-out，不是 minor。

## 破壞性變更

### wire 上的 `object` 值改走判別式封套

少數 wire 成員宣告為 `object?`——`Parameter.Value`、`FilterCondition.Value` 與 `SecondValue`、`SerializableDataColumn.DefaultValue`，以及 `SerializableDataRow` 內的儲存格值。先前每個這樣的值都攜帶自己的 assembly-qualified 型別名，並經 MessagePack 的 typeless 機制派發。那套機制需要 `Reflection.Emit`，而 .NET for iOS 對每一種建置都關掉動態碼——因此在行動端這些值不是變慢，是直接擲例外。

現在它們走一個兩元素封套：整數判別碼加上值，讀寫由陣列索引選出的封閉泛型委派完成。框架自有的值型別全在封閉集內。具名型別的逃生門保留給宿主提供的型別，那也是唯一仍需要動態碼的部分。

兩個必須明講的後果：

- **wire 格式改變，而這些成員掛在每個 request 與 response 上。** 4.19 的 client 無法與 4.20 的 server 溝通，反之亦然。兩端一起部署。
- **payload 變小、路徑變快。** 每個值先前要寫入完整的 assembly-qualified 型別名（約 50–100 bytes），並經一次非泛型反射呼叫解析 formatter；現在寫入一個 byte 的判別碼、取一次陣列索引。對一張寬表而言，這是以 MB 而非 byte 計的差異。

註冊模型的完整脈絡見 [ADR-037](../adr/adr-037-wire-explicit-registration.md)。

### 運算式抽象移至 `Bee.Base`

`Bee.Definition` 參考 `Bee.Expressions`，而後者參考 `DynamicExpresso.Core`。定義層因此把那個套件交給相依鏈下游的每一個消費者——包含 `Bee.Cli` 與 `DefineEditor`，它們只讀寫定義檔，用不到運算式引擎。

抽象與實作現在分居兩處。`IExpressionEvaluator`、`ExpressionPolicy`、`ExpressionEvaluationException` 移至 `Bee.Base.Expressions`，其公開表面只用到 BCL 型別與一個框架列舉。`Bee.Expressions` 保留 `DynamicExpressoEvaluator` 與套件參考，由組裝層——`Bee.Hosting` 或某個 UI head——決定用哪個實作。

**沒有 type forward。** 對已搬遷的型別寫 `using Bee.Expressions;` 是編譯錯誤，而這正是預期的結果：靜默轉址會讓舊命名空間看起來還活著。改掉 `using`，其餘不動。

三個建構子收 evaluator 因而簽章改變：`FormExpressionCalculator`、`FormRuleProcessor`、`FormLiveComputation`。前兩者是必要參數，呼叫端在編譯期就會發現。**`FormLiveComputation` 的是選擇性參數**——這是必須講明的那一個：省略該引數的原始碼對新組件照樣編得過，但以 4.19 編譯出來的組件會在執行期擲 `MissingMethodException`。任何會建構它的東西都要重建。

判別準則與兩道建置期閘門見 [ADR-038](../adr/adr-038-definition-dependency-boundary.md)。

### 框架登入有了可用的預設實作

`SystemBusinessObject.AuthenticateUser` 是宿主覆寫來做認證的擴充點。它的預設實作無條件回 `false`——一個佔位，因為框架自己沒有可比對的憑證儲存。

現在它透過新的 `IUserRepository.VerifyPassword` 比對 `st_user`。**雜湊不離開 Repository**：把它回傳給呼叫端自行比對，等於讓一個憑證進入呼叫端的變數，那就多一個它可能流進 log 或例外訊息的地方。查無使用者與密碼錯誤一律回 `false`，這是刻意的——一個分得出兩者差別的呼叫端就是帳號列舉的 oracle。

**行為變更是單向的。** 有覆寫 `AuthenticateUser` 的部署不受影響；沒覆寫的部署原本根本沒有可用的登入，現在會接受 `st_user` 內的帳號。這是放寬，故即使「原本能運作的東西沒有停止運作」，仍列為破壞性。若你依賴預設實作拒絕所有登入，請覆寫它。

`IUserRepository` 新增成員，對框架之外自行實作該介面者為 source-breaking。

## 新增

### 兩道建置期閘門

**BEE9001** 把 `Bee.Base` 與 `Bee.Definition` 鎖到明確的相依允許清單。加在這兩者上的任何東西都會被框架的每一個消費者繼承，所以放寬是允許的，但必須是某個人刻意做出的決定。與它互補的是一個走 `Bee.Definition` 完整傳遞閉包的測試——兩者不是重複：target 在直接相依邊被寫下的當下攔截，測試則攔截「經由某個專案參考間接進來的套件」，而 `DynamicExpresso.Core` 正是這樣進來的。

**BEE9002** 要求 `Version`、`AssemblyVersion`、`FileVersion` 保持同步。為何是閘門而不是 checklist 上的一行字，見下方的版號修正。

兩者均已載入 [Analyzer 規則](../analyzer-rules.zh-TW.md)。

## 修正

### `LanguageEnum.Entries` 讓 iOS 的定義載入失敗

`Entries` 原本是對映為重複 `[XmlElement]` 的 get-only 集合屬性。在桌面上沒問題。但在 reflection-only 的 `XmlSerializer` 路徑上——iOS 用的正是這條，因為動態碼被關掉——這樣對映的成員是被**指派**而非被 `Add`，因此缺少 setter 會擲 `ArgumentException: Property set method not found`。它外顯為 `There is an error in XML document (行, 列)`，指向 XML 而非型別。

setter 採「清空既有集合後逐一填回」而非替換欄位，owner 反向連結因而得以保留。全 repo 掃描確認這是唯一一個同型的屬性。

以 `[XmlArray]` 對映的 get-only 集合**不受影響**——差別在成員的對映方式，不在集合本身。

### `st_user.password` 存不下密碼雜湊

該欄位長度 40，而 `PasswordHasher` 產出 79 字元。SQLite 不強制長度；其他四家會截斷，而截斷後的雜湊永遠無法驗證成功。在本版之前框架沒有任何地方把雜湊寫進 `st_user`，這就是這麼直接的缺陷卻一直沒被發現的原因。

### 組件 identity 又一次與套件版號脫節

4.17.0 發布的組件標的是 `4.16.0.0`。那在 4.18.0 被人工修正——然後 4.19.0 發布的組件標的是 `4.18.0.0`。

**而且一直有第三份副本在漂。** `tools/Bee.Cli` 會發布到 NuGet，卻不繼承 `src/`，因此自帶一份三個版號屬性，並附註解要求「與框架一起 bump」。它停在 4.8.0 整整十二個 minor；自 4.9.0 起每一版發布的 `Bee.Cli` 內組件標的都是 `4.8.0.0`。

最後這一項 per-project 閘門攔不到——BEE9002 檢查的是三個屬性**彼此**一致，而 4.8.0 / 4.8.0.0 / 4.8.0.0 自洽得無懈可擊。因此版號改放在 repo 根的單一 `Version.props`，由兩棵樹各自 import。閘門負責「單一專案自我矛盾」，單一來源負責「兩個專案各說各話」。

發生兩次就是機制問題，不是注意力問題。兩次都是把數字改對、沒有加上任何能攔下次的東西，而兩次都是靠人讀檔案才發現。BEE9002 現在會在三個屬性不一致時、於編輯發生的當下讓建置失敗。

**已發布的 4.19.0 套件不重新發布。** 其組件宣稱 `4.18.0.0`，以組件 identity 無從與 4.18.0 區分。若你的工具鏈是依 `AssemblyVersion` 而非套件版號判斷，這組版本需要知情。

## 變更

`Bee.Definition` 的套件不再列出 `Bee.Expressions`，因此也不再帶入 `DynamicExpresso.Core`。對只讀定義的消費者而言，這從相依圖上移除了一個運算式引擎。

移除 `samples/Avalonia.Demo`。Avalonia 的端到端示範改為 `apps/Bee.Northwind`，它以三個資料庫分類與真實登入涵蓋同樣的範圍。

## 升級指引

```diff
- using Bee.Expressions;
+ using Bee.Base.Expressions;
```

- **server 與 client 一起部署。** `object` 封套的變更影響每個 request 與 response。
- **任何會建構 `FormLiveComputation` 的組件都要重建**，包含沒有傳入 evaluator 的呼叫端。
- **若你自行實作 `IUserRepository`**，補上 `VerifyPassword`。
- **若你依賴 `AuthenticateUser` 拒絕所有登入**，請覆寫它——預設實作現在會比對 `st_user`。
