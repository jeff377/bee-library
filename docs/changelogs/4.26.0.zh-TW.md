# Bee.NET 4.26.0 — 詳細版本說明

[English](4.26.0.md) ・ [繁體中文](4.26.0.zh-TW.md) ・ [← CHANGELOG](../../CHANGELOG.zh-TW.md)

本文件是 [CHANGELOG.zh-TW.md](../../CHANGELOG.zh-TW.md) 中 `[4.26.0]` 條目的展開版。主 CHANGELOG 每項變更一行；本檔保留完整脈絡——每項變更背後的**為什麼**、限制條件與設計考量。

> 一個被側錄的 JSON-RPC 封包重送一次就會再執行一次。payload 有驗證——攻擊者改不動它——但驗證講的不是**唯一性**，而一個重送的 `Save` 就是一個有效、簽章正確的 `Save`。本版加上承載時戳與序號的 wire frame，以及 per-session 的滑動視窗，拒收已經收過的序號。引入 frame 是斷裂變更，因此掛在一個預設關閉的開關後面。同時，兩端各自私藏的「例外對錯誤碼」映射收斂為一張有序登錄表，schema 升級也補上四種 dialect 的描述同步。

## 新增

### `Encoded` 與 `Encrypted` 兩種 wire 格式的重放防護

`ApiPayloadFrame` 是 17 bytes —— 一個版本位元組、8 bytes 的毫秒時戳、8 bytes 的序號，全部 big-endian。它在 `Encode` **之後**、`Encrypt` **之前** prepend，而擺在這個位置正是重點：在封套之內，payload HMAC 就涵蓋得到它。若把 frame 放在 `ApiPayload` 的明文欄位，攻擊者可以任意改寫，那等於沒防。

伺服端**不偵測** frame 在不在。兩端都讀 `ApiServiceOptions.RequireWireFrame`；會從封包自述推斷 frame 存在與否的伺服端，攻擊者只要把 frame 拿掉就能降級。fail-closed 的代價是這個開關不做協商：只有一端打開，每一次呼叫都會失敗。它預設為 `false`，所以單純升套件不會改變任何行為。

版本位元組的存在是為了讓日後改佈局時不必再猜一次；`Version1Size` 是釘住目前佈局的常數。

### 序號視窗

`ReplayWindow` 是 IPsec anti-replay window（RFC 6479）的縮小版：每個 session 只存最高序號加上一個 64-bit bitmap —— 共 16 bytes —— 一次判斷是幾個位元運算，零資料庫往返。

容忍亂序抵達是必要條件而非額外好處。取號是原子的，但並行請求**送達**的順序不固定，嚴格遞增的規則會誤殺正常流量。

`MaxForwardJump` 定為 1,000,000。沒有上限的話，用戶端一次整數運算失誤送出接近 `long.MaxValue` 的序號，該 session 之後所有正常請求都會落在視窗外 —— 而 token 有效、金鑰正確，幾乎無法診斷。

視窗存活期是時戳容許時窗的兩倍，且刻意與 session 生命週期解耦：用舊序號的重放，其時戳必定也已過期、被時戳檢查擋下，因此視窗只在那段時間內有意義，不必掛在 logout 上清理。記憶體上界是「時窗內活躍的 session 數」。

匿名呼叫（`Guid.Empty`）不做序號檢查。序號是 per session 的，而匿名呼叫者共用同一個 token；若也檢查，不同用戶端會互相把對方的序號用掉，造成大量誤拒。

`IReplayWindowStore` 做成介面，是因為那是多節點部署的出路。預設把視窗放在本行程記憶體。在沒有 token affinity 的負載平衡之後，每個節點各持一份 —— 被側錄的封包每個節點可重放一次，仍然有界，也遠優於無限 —— 需要跨節點強一致的部署換上共享實作即可。

### 逐方法宣告哪些呼叫要求序號唯一

`ApiAccessControlAttribute.ReplayProtection` 取 `ApiReplayProtection.None`（預設值，因此既有宣告不受影響）或 `UniqueSequence`。標上的有五個方法：`Save`、`Delete`、`ExecFunc`、`EnterCompany` 與 `LeaveCompany`。那是「遠端可達且有副作用」的完整集合 —— 其餘寫入方法（`SaveDefine`、`SaveCustomizePluginSettings`、`SetDeploymentAdmin`）全為 `LocalOnly`，遠端不可達。

### `AnomalyKind.Replay`

在 `JsonRpcExecutor` 既有的失敗記錄路徑上分類。折進泛用的 `Error` 會失去這裡唯一重要的訊號：某個 session 連續被拒，不是用戶端時鐘漂出容許時窗，就是有人在重送側錄的封包。兩者只要被歸成一般錯誤就都看不見了。

完整的決策清單 —— 包含三項刻意不納入的（冪等鍵、收斂 `ApiProtectionLevel.Public`、業務層守門不因此省略）—— 見 [ADR-042](../adr/adr-042-api-replay-protection.md)。

### 四種 dialect 的描述同步

`IDescriptionSyncCommandBuilder` 經 `IDialectFactory.CreateDescriptionSyncCommandBuilder()` 取得。SQL Server 沿用 extended property；PostgreSQL 與 Oracle 用 `COMMENT ON`；MySQL 用 `ALTER TABLE ... COMMENT` 與 `MODIFY COLUMN`。

工廠上的那個成員是**回傳 `null` 的 default interface member** —— 外部既有的 `IDialectFactory` 實作不必改就能繼續編譯與執行。做成 abstract 成員會是破壞性變更且沒有任何收穫；而對一個無處可存描述的 dialect 來說，`null` 本來就是正確答案。

## 變更

### 錯誤契約收斂為單一登錄

伺服端的 `MapException` 把例外映成錯誤碼，呼叫端的 `FinalizeResponse` 再把碼映回例外。兩者互為反函數，而沒有任何機制保證它們同步。`ReplayRejectedException` 就是這樣漂掉的：伺服端四處丟出、映成 `-32005`，呼叫端卻整整少一條分支 —— 於是該型別自己的文件所承諾的 `catch (ReplayRejectedException)` 永遠不會進去，而且編譯得過、測試也沒紅。

`JsonRpcErrorContract` 以一張有序表宣告「哪個例外走哪個錯誤碼、該碼由誰重建」。兩端現在都讀這張表。

順序敏感性沒有假裝消除。型別比對必須用可指派（`ArgumentNullException` 要歸到 `ArgumentException` 之下），所以登錄表宣告「衍生型別必須排在基底之前」這條不變式，並由測試逐對驗證、指名互相遮蔽的是哪兩列。舊實作對順序的依賴一樣強，差別在於那裡弄錯了不會有任何訊號。

fallback 刻意留在登錄表之外。`InternalError` 那條讀 `SysInfo.IsDebugMode`，那是資訊揭露政策；呼叫端的通用分支則是訊息格式。兩者都不是型別對應碼。

ADR-043 記下決策，包含「讓這些例外直接繼承 `UserMessageException`」為何被否決：一個 `if` 都省不掉，因為那四個型別本來就不在白名單裡。見 [ADR-043](../adr/adr-043-error-contract-single-registry.md)。

一個值得一提的副作用：呼叫端不再需要認識任何具體例外型別，`ApiConnector` 連 `Bee.Base.Exceptions` 的 using 都移除了。

### 錯誤碼文件的四筆更正

公開文件修正四筆漂移：錯誤碼表缺 `-32005`；`-32001` 的描述與實際不符（認證失敗實際回 `-32600` 加 HTTP 401，`-32001` 零產生者）；開發限制文件誤稱只有 `UserMessage` 會在呼叫端被重建，實際上 `PermissionDenied`、`CompanyAccessDenied` 與 `CompanyNotEntered` 一直都有專屬型別。雙語版同步更新，且對映表改為指向 `JsonRpcErrorContract`，不再複寫一份。

## 修正

### Oracle：LOB 欄位的幻影差異讓升級中斷

`OracleTableSchemaProvider` 讀回 schema 時，把每個 `String` / `Text` 欄位都標成 `AllowNull=false`。那是為了對齊宣告端：Oracle 把 `''` 當 `NULL`，所以 DDL builder 一律把欄位輸出為可空，宣告 `AllowNull="false"` 的欄位否則永遠對不上。代價是宣告 `AllowNull="true"` 的欄位永遠對不上自己的讀回值 —— 每一輪比對都產生 `AlterFieldChange`。

在 `String` 上，產生的 `MODIFY` 是無害的 no-op。在 `CLOB` 上不是：Oracle 拒絕任何重述 LOB 欄位型別的 `MODIFY`，連 `CLOB` 改成同型 `CLOB` 也擲 `ORA-22859`。而階段順序是 `AlterColumns` 在前、`AddColumns` 在後，於是升級在新欄位加上去之前就中止 —— `st_log_anomaly_api` 與 `st_log_anomaly_db` 永久停在比定義少兩欄的狀態。

三項修改：

- `TableSchemaComparer.CompareField` 在比對前，對 Oracle 的 `String` / `Text` / `Time` 正規化可空性。在該 dialect 下定義本來就控制不了它，兩側不具可比性。
- `OracleTableAlterCommandBuilder` 對 LOB 改同型 LOB 只輸出 `DEFAULT` 與可空性、絕不輸出型別；沒有可改的差異時就完全不發語句。跨越 LOB 邊界則改判 Rebuild —— `String(100)` → `Text` 與 `String(100)` → `String(5000)` 會撞上同一面牆，而 `AlterCompatibilityRules` 把兩者歸在同一型別家族。
- `OracleTypeMapping.IsLobType` 由 `GetOracleType` 推導，兩者不會漂。

### 描述同步只在 SQL Server 生效

`AppendDescriptionSyncStage` 原本只認 `SqlDialectFactory`。在其餘每一種 dialect 上，`ALTER` 加進去的欄位永遠拿不到 caption。更麻煩的是 `TableSchemaDiff.IsEmpty` 把 `DescriptionChanges` 算進去，於是那些表往後每次比對都回報有差異、每次 `Plan` 都得到零 stage 的 `Alter`。不出錯、不跑 SQL —— 但「這張表是不是最新的」永遠答否。

`DescriptionSyncChanges.Collect` 現在也把 `AddFieldChange` 的 caption 納入。比對器只對兩側都存在的欄位判描述差異，少了這段，剛加的欄位得等下一輪才補得上。

**MySQL 的 `MODIFY COLUMN` 會整段換掉欄位定義。** 描述同步落到 MySQL 時，要對「只有 caption 漂移」的欄位下 `MODIFY COLUMN`，而 `GetColumnDefinition` 不含 `AUTO_INCREMENT` —— 撞到 `sys_no` 就把自增拔掉，之後所有 `INSERT` 全部失敗。`GetModifyColumnDefinition` 保住它（不帶 `PRIMARY KEY`，表上已經有了）。這一則記進了 repo 的踩雷誌，因為它藏得很好：第二輪重跑會轉綠，那是 Rebuild 路徑自癒 —— 破壞被掩蓋，不是 flaky。

**SQLite 沒有 `COMMENT` 機制**，每個 caption 一律讀回空字串，因此比對器在該 dialect 下完全不回報描述差異。補一個 SQLite builder 沒有用 —— 它產不出任何語句，差異照樣留在 diff 裡。正解是比對器根本不要把它列為差異。

### `Bee.Northwind`：部分 seed 永久殘留

`ft_order_detail` 只有 12 筆種子列中的 11 筆，缺的是最後一筆，於是訂單 10252 的總額顯示 1995 而非種子檔的 2235。

兩件事湊在一起。冪等 gate 是 `SELECT COUNT(*) > 0` —— 非空就整批跳過 —— 而插入迴圈逐筆執行、沒有 transaction。第一次 seed 若中途失敗，前面幾筆已落地、後面沒有；下次啟動時表非空，gate 直接跳過，於是永久停在不完整狀態。gate 與迴圈都不會發現列數與種子檔對不上，也沒有任何錯誤訊息。

修法是讓原子性對齊 gate 的粒度：gate 以表為單位，transaction 就以表為單位。`ResolveRowId` 加上選用的 transaction 參數，因為插入期間的查找必須走同一個交易 —— 否則會經由第二條連線讀取而看不到尚未 commit 的列。（deferred pass 在所有表 commit 之後才跑，維持不傳。）

### `Bee.Northwind`：Browser head 的中文標籤變豆腐方塊

瀏覽器沙箱沒有系統字型可 fallback，而 Inter 不含 CJK 字形，於是中文語系瀏覽器下所有欄位標籤都變成方塊。其餘三個 head 借得到 PingFang / Noto CJK 所以無症狀 —— 問題一直都在，是加入 zh-TW 語系資源後才顯形。

原本規劃內嵌 subset 過的 Noto Sans TC，直到量出兩個數字：要顯示的中文只有 24 個 key（34 個唯一漢字），而最小可用的 CJK 字型是 5.4 MB。為 24 個 key 讓 demo 背 5.4 MB 不成比例，因此 Browser head 改為釘住 `CurrentUICulture` 為 `en-US`，標籤回到 `FormSchema` 本身的英文 Caption。只改 Browser head；其餘三個平台中文顯示正常，仍跟隨系統語系。

## 升級指引

不需要做任何事。`ApiServiceOptions.RequireWireFrame` 預設為 `false`，而本版所有公開 API 變更都是加法。

要開啟重放防護，**兩端**先升套件，再把用戶端與伺服端的開關同時打開：

```csharp
// 伺服端與用戶端，啟動時 —— 要嘛都開，要嘛都不開。
ApiServiceOptions.RequireWireFrame = true;
```

開之前值得先知道四條限制：

- `Plain` 格式不受保護。frame 活在 encoded / encrypted 封套之內，那正是它能被驗出竄改的原因；明文沒有等價機制。
- 逾時重送的請求會**失敗**，而不是安靜地成功。那正是這個機制的用意，會自動重試的用戶端必須知道這件事。
- 匿名呼叫不做序號檢查。
- 單就時戳檢查而言，被側錄的封包在 `WireFrameTimestampTolerance`（預設五分鐘）內仍可重放。這個時窗必須吸收用戶端的時鐘偏移 —— NTP 設定不良的桌機動輒差好幾分鐘 —— 而收窄剩下那段落差是序號視窗的職責，不是容許時窗的。
