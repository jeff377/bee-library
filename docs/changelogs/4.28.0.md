# Bee.NET 4.28.0 — Detailed Release Notes

[English](4.28.0.md) ・ [繁體中文](4.28.0.zh-TW.md) ・ [← CHANGELOG](../../CHANGELOG.md)

This document is the detailed version of the `[4.28.0]` entry in [CHANGELOG.md](../../CHANGELOG.md). The main CHANGELOG lists one line per change; this file keeps the full narrative — the *why*, the constraints, and the design context behind each change.

> This release is the outcome of a systematic framework review. Nearly every finding turned out to be the same shape: **a protection mechanism whose real coverage is narrower than its apparent coverage, with nothing to say so.** That shape is worth stating plainly, because it is not a discipline problem. A guard that is skipped rather than failed, a gate that is green because it is asking the wrong question, a rule that cannot fire because the file it compares against is empty — none of these announce themselves, and none of them are fixed by remembering harder. So this release does two things at once: it closes the holes, and it puts the mechanisms that should have noticed under test themselves.

## Breaking changes

### `System.CheckPackageUpdate` and `System.GetPackage` are removed

Both were extension points whose base implementation threw `NotSupportedException`, intended for a host to override. Neither had a consumer. The test applied was the one that actually decides the question: **the direct consumer of an API contract method is the API connector.** `Bee.Api.Client` has no connector method for either, and the documentation stated outright that they were not for the JavaScript front end — so both paths were empty.

That test has one documented exception, and applying it honestly matters. Of the 40 public BO API methods, four are unreferenced by `Bee.Api.Client`. Three of them — `GetFormSchema`, `GetFormLayout`, `GetLanguage` — are per-type entry points for non-.NET clients; a .NET caller uses `GetDefineAsync`, so a wrapper would only duplicate. Removing them would break the clients they exist for. `GetPackage` was the only method genuinely without a consumer, and `CheckPackageUpdate` was its pair — the two form one flow, check for an update then download the package, so keeping half of it would have left something even less meaningful than the whole.

Removal reached eight and then seven files across three layers, plus `SystemActions` constants, `SystemBusinessObject` methods, five MessagePack wire registrations, 126 lines of `PublicAPI` baseline across four projects, six READMEs, four public documents and five test files. `MessagePackContractsTests` went with them — after both removals it was an empty shell. The contracts assembly now holds no enum at all, so the README rule about stable enum values lost its subject and went too.

ADR-014's decision text is preserved as the record it is, with a note that both methods have since been removed — a reader should not go looking for something that no longer exists.

### Contract collections narrow to read-only types

Four of the five collection members on the contract interfaces exposed concrete `List` / `Dictionary`, while the two newest — `IListApiKeysResponse.ApiKeys` and `IGetChangeDetailResponse.Fields` — already used `IReadOnlyList`. The convention had formed; these four were the old debt nobody went back for. Leaving them meant one contract carrying two conventions.

Two of the four went away with `CheckPackageUpdate`; the two that ship are `ISaveResponse.AffectedRows` and `IEnterCompanyResponse.Capabilities`. Serialization is unaffected. The eight implementing sites keep their concrete writable properties untouched and gain one explicit interface implementation each, copying the pattern `ApiKeys` / `Fields` already used rather than inventing one. Wire DTOs and BOs remain concrete writable collections, so binding is unaffected, and `wire-contracts/` and `wire-fixtures/` show zero diff.

What breaks is external code that takes the collection *through the contract interface* and wants to write to it. But the contract interfaces have always declared `{ get; }` — being able to reach a mutable collection through them was an accident of the declared type, not a design.

### `isLocalCall` defaults to `false`

Default `true` meant: constructing a BO directly — the one path that bypasses `ApiAccessValidator` — is treated as a trusted in-process call by default. Several methods use `IsLocalCall` as their second line of defence: minting an API key without deployment-admin rights, granting deployment admin, writing server-only definitions. Those guards were open on the default path and closed only for a caller that had explicitly written `isLocalCall: false` — which is the least likely caller to need stopping.

All four guards carried a comment saying "callers constructing the BO directly do not pass through `ApiAccessValidator`". Correct, and missing the second half: *therefore they are local by default.*

The blast radius turned out much smaller than expected. Nothing in `src/`, `apps/`, `samples/` or `tools/` constructs a BO directly; all 120-odd construction sites are in `tests/`, and `BusinessObjectFactory` always passes the value explicitly. This default had never been used inside the framework. It applied only to tests and to external consumers — and the latter are exactly the group with the least protection.

28 tests broke, all of them inside the areas those four guards protect. They had been passing *because* the default disabled the guards. Six construction sites now say `isLocalCall: true` out loud, which turns "I want the local path" into something stated rather than inherited.

Binary compatibility is worth being precise about: an optional parameter's default is baked in at the *caller's* compile time, so an already-compiled assembly keeps the old behaviour and only picks up `false` when recompiled.

### Moves and removals

`ApiCallContext` was being published into the generated TypeScript contract while never crossing the wire. Removing its MessagePack registration changed nothing, because the generator does not read the registration list — it reflects over the namespace. The root cause was that it did not belong in `Bee.Api.Core.Messages` at all: it is `ApiAccessValidator`'s input, built per call by `JsonRpcExecutor`. Moving it to `Bee.Api.Core.Validator` removed both it and `PayloadFormat` from the contract — and that second removal is the more valuable one, because `PayloadFormat` appeared there as a string union (`'Plain' | 'Encoded' | 'Encrypted'`) while the wire carries a number. The contract and the wire contradicted each other on a field of the same name.

`ApiPayloadOptionsFactory.CreateSerializer` had no production caller and its absence needed explaining rather than filling: the body codec is declared per request ([ADR-044](../adr/adr-044-payload-codec-negotiation.md)), not per deployment. Removing it does not close the dangerous door, though — `ApiServiceOptions.Initialize(serializer, …)` still takes one, and anyone can `new JsonPayloadSerializer()`. So that parameter now carries a warning saying what it actually means: not "which codec this deployment uses" but "which codec a request that declares none is read as", which is a compatibility constant. Changing it reads existing clients' bodies with a codec they never used, and the failure surfaces at server-side deserialization, far from the call.

`HttpUtilities` moved out of `Bee.Base` for the reason `rules/dependency-boundary.md` gives: `Bee.Base` is not a drawer. It is every project's dependency — including UI heads that only read definitions and offline definition tools — so anything placed there appears on every consumer's public surface whether or not it can be used. All three call sites were always in `Bee.Api.Client`. A gate now asserts that `Bee.Base`'s IL references do not include `System.Net.Http`, deliberately scoped to that one assembly rather than all of `System.Net`: `IPValidator`'s `IPAddress` use is CIDR value comparison and connects to nothing, and a gate that conflated the two would push someone into moving the wrong thing to get green.

## Security

### An empty hash segment verified against any password

`PasswordHasher.VerifyPassword` returned `true` when the stored value's hash segment was empty. PBKDF2 asked for zero output bytes returns an empty array, and `FixedTimeEquals` judges two empty spans equal. `v2.100000..` therefore verified against anything, on both the v2 and the legacy branch. `UserRepository`'s existing short-circuit only rejected a wholly empty string.

On its own that needs a write to `st_user.password`, which is why the second half matters: that column was not in `ProtectedFields`. Any deployment with a user-maintenance form over `st_user` could write it through the FormSchema data path. The two together are a complete privilege-escalation chain, so both halves are closed.

`ProtectedFieldsTests` had `("st_user", "password")` listed among its *unprotected* cases — the escalation path written down as specification. It is now a positive assertion with the reason recorded beside it.

No lower bound on `iterations` was added. A low iteration count is not a live bypass — exploiting it requires the write access this change removes — and a bound would lock out legitimate legacy hashes computed with fewer.

### A save carrying only detail rows skipped the record-scope check entirely

`FormBusinessObject.Save`'s level-two check assumed the master table was present in the DataSet: both `HasExistingMasterWrite` and `EnforceWriteScope` returned immediately when it was absent. But `DataFormRepository.Save` decides per table whether it is in the DataSet, and writes details regardless. So a save containing only the detail table never invoked the check at all — insert, update or delete of detail rows against out-of-scope master records.

This contradicted `Save`'s own comment: "Scope is master-only, so once the master passes the whole record persists with it." When the master is not in the payload, no master has passed anything.

Fixing that surfaced a second route through the same hole. A detail row's `sys_master_rowid` was taken from the payload verbatim — not in `ProtectedFields`, and `Modified` rows are rewritten with a full-column UPDATE. So an in-scope master with detail rows pointing at a different master passed just as easily, and `Modified` could move an existing detail row *out of* someone else's record. Fixing only the first would have manufactured the impression that the hole was closed, so both went together.

`EnforceWriteScope` is now called unconditionally — the payload shapes that get refused are precisely the ones that used to skip the call — with two structural checks: a declared master table with only detail rows pending is refused, and every pending detail row's `sys_master_rowid` must be one of the master rows this payload carries, which are the rows that just passed the scope check. `Modified` is checked on both Original and Current: moving data out of someone's record is as much a boundary crossing as moving it in.

Both are refusals rather than silent drops, because these shapes have no legitimate use. The framework's own detail-only editing carries an `Unchanged` master row, which is why `WriteScopeActionForRowState` maps that state to Update. Forms declaring no `PermissionModelId` remain entirely unaffected — the method returns on its first line — so deployments that have not adopted the permission model see no change.

`HasExistingMasterWrite` was removed with the fix: its two `false` cases (a pure insert, and the master table being absent) mean opposite things yet returned the same answer, which is the shape of the bug itself.

### Audit-log queries were fail-open on the tenant boundary

`company_id` — a tenant boundary — shared the same "skip when null" helper as optional filters such as `prog_id` and `user_id`. A session that had entered no company therefore had the condition disappear and received every company's audit records. Seven entry points are now fail-closed.

There is no legitimate cross-tenant read to preserve: `LogBusinessObject.CurrentCompanyId()` is the session's `CompanyId`, and deployment admin has no bypass.

Six existing tests asserted the opposite behaviour ("no company filter → both rows come back"). Each was read individually before being changed, because a test guarding the opposite is sometimes a deliberate decision written down. Here it was not — no comment declared cross-tenant reads legitimate, and this change is the statement that the shape is wrong. The tests now assert the new specification and additionally cover tenant isolation: seed data places two rows in one company and one in another, so a second tenant demonstrably cannot see the first's rows.

### A server path leaked to remote callers, and MySQL literals could escape

A definition file that failed to deserialize threw `InvalidOperationException`, which maps to `UserMessage`, and that branch returned `ex.Message` verbatim — so an authenticated remote caller who reached a corrupt definition file received the server's directory layout. This violates `scanning.md`'s rule that exception messages must not carry internal paths. The message now carries the file name only; the full path moves to `Exception.Data` under `SerializationErrorData.FilePath`, where server-side logging can still use it.

`MySqlSchemaSyntax.EscapeSqlString` only doubled quotes. MySQL is the one dialect here that treats `\` as an escape character by default — SQL Server, Oracle, SQLite, and PostgreSQL with `standard_conforming_strings` on do not — so a trailing backslash consumed the closing quote and the literal escaped into the following statement. Verified against a MySQL 8 container through the framework's own escaping: `ends with backslash \` produced a syntax error, as did `a\' , (SELECT 1) , '`.

**The correctness impact arrives before the injection surface.** A column description ending in a backslash — a Windows path in a note, say — is enough to make the generated DDL a syntax error, with no attacker involved. The review classified this as "definition author → arbitrary DDL at upgrade time", but a deployment would hit the broken-upgrade half first.

The report listed three sinks; there were four — `MySqlCreateTableCommandBuilder`'s table COMMENT was missing from it. All four go through the same function. Backslashes are escaped before quotes are doubled; with only these two rules the order does not change the result, but escaping the escape character first is the order that stays correct when a third rule is added. The stated premise is the server's default `sql_mode`: a deployment running `NO_BACKSLASH_ESCAPES` makes the backslash an ordinary character and would see doubled backslashes. This function has no connection and cannot read `sql_mode`; the PostgreSQL dialect has long made the same kind of assumption about `standard_conforming_strings`.

## Added

### BEE1008 — a form with no `PermissionModelId` is open to every authenticated caller

Level-one authorization reads the form's `PermissionModelId` and returns immediately when it is empty. That is deliberate — `FormBusinessObject.Authorize`'s XML doc calls it gradual adoption, and an unmarked form stays open — but the consequence was visible nowhere. A form that should have been marked and was not is open to every authenticated caller, while build, tests and every existing analyzer stay green.

`PermissionModelAnalyzer` reports it. Deliberately reports rather than enforces: making it a runtime failure would break every half-adopted deployment on the spot, which is the reason opt-in exists. What was missing was never a rule; it was that "this form is open" had nowhere to be said.

Severity is `Info`, and the cost of that honesty is written into `docs/analyzer-rules` in both languages: `Info` maps to an MSBuild message, is not printed at default verbosity, and the definition analyzers are `CompilationEnd` so the IDE does not surface them live either. The mechanism exists but is not visible by default. Raise it to `warning` in `.editorconfig` once adoption is complete — `warning` as the default would fail the build for every consumer mid-adoption, which is the opposite of gradual.

### Seams, shared rules and gates

`IApiKeyGateStateProvider` lets the API layer ask whether the API key gate is in force without resolving `ICacheContainer`, which is declared in `Bee.ObjectCaching` — the caching *implementation*. That layer has no business knowing the answer is cached, let alone which assembly caches it. The `null`-versus-throws distinction is preserved deliberately and written into the interface doc: `null` means "there is nothing to ask", an exception means "there is a store and it cannot be reached" — treating the second as the first makes an unreachable database read like an open door.

`FormValueBinding` and `FormDataGuard` collect the form-data rules that both UI heads had been carrying private copies of, with docs saying the parallel copies were deliberate and nothing enforced it. The drift had already happened: of five helpers, three were verbatim identical and two had diverged — and one of the two was a live bug, described under Fixed. They are split into two classes rather than one shared bag, and they live in `Bee.Api.Client` because both heads already reference it and it carries no `Bee.UI.*` semantics.

Six gates that claimed to check something and did not are now real. The architecture gate is the instructive one: its first version compared direct edges in `deps.json`, and **stayed green against a deliberately planted violation.** The SDK folds transitive project references into `@(ProjectReference)` before Build, so code can `using` an assembly that arrives only by transit, with that edge appearing in neither the csproj nor `deps.json`. `deps.json` catches "declared but unused"; it cannot catch "used but undeclared". Switching to `Assembly.GetReferencedAssemblies()` — what the compiled IL actually references — made the negative verification go red correctly.

## Changed

### Two performance changes, both measured

The write path never set `UpdateBatchSize`, whose ADO.NET default is 1 — one `ExecuteNonQuery`, and therefore one round trip, per changed row. Against a local SQL Server container: 100-row insert 32 ms → 3 ms, 500-row insert 145 ms → 9 ms. For perspective, the change deemed noise in the previous round was 0.50 µs per request; this one costs more than the entire serialization pipeline on a document with 100 detail rows, and a local container is already the most optimistic case.

Support is detected by asking the adapter, because `DbDataAdapter`'s base setter throws `NotSupportedException` — so the question *is* the check. A hard-coded provider list would be wrong in two directions: it would not follow a provider that gains support later, and it cannot know which factory a host actually registered for a given `DatabaseType`. The bound is 100 rather than 0 (as many as the provider will take): almost all of the gain is in leaving per-row round trips behind, and a bound avoids one pathological bulk save assembling an enormous command.

This also closed a coverage gap. Until now the adapter write path had DB tests on **SQLite only** — one of the two providers that cannot batch — so the three providers where batching actually engages had zero coverage of that path. The new suite asserts that batching does not change results (it passes with batching disabled, deliberately: unchanged behaviour is the acceptance criterion), while a separate test pins the measured support matrix so a provider changing its behaviour shows up as red.

`ApiServiceController.ReadRequestAsync` called `Request.EnableBuffering()`, wrapping the body in a `FileBufferingReadStream` that spills to a temporary file above 30 KB. The framework never rewound the body: this is the only place in the repo that reads `Request.Body`, and the controller has no `[FromBody]` parameter — the body is already at position 0 on arrival, so both `EnableBuffering()` and `Position = 0` were semantically inert. Every request over 30 KB paid a disk round trip for a capability nobody used, and `params.value` is a base64 gzip body (1.33× inflation), so any save or fetch carrying detail rows was above the threshold. Measured over a full HTTP round trip, 20-run averages: 16 KB 0.15 → 0.14 ms, 64 KB 0.46 → 0.22 ms, 1 MB 2.81 → 1.28 ms, 4 MB 9.51 → 4.76 ms. **The 16 KB row showing no difference is the causal proof** — the gain comes from crossing the 30 KB spill threshold, not from avoiding one extra string.

One behavioural difference is worth stating: a body of nothing but whitespace now reports `ParseError` rather than `InvalidRequest`. The HTTP status is still 400, and "what arrived is not valid JSON" is what `ParseError` means.

### An audit writer could take the deployment down

`AuditLogWriterService.ExecuteAsync` caught only `OperationCanceledException`. Anything else escaping `_sink.WriteBatch` faulted the `BackgroundService`, and .NET's default `BackgroundServiceExceptionBehavior.StopHost` stops the whole application — **one failed log write could take the deployment away.** [ADR-017](../adr/adr-017-db-cache-invalidation.md) had set this rule for `CacheNotifyPoller`; this was the one service that never got it.

The catch is deliberately unfiltered, and deliberately different from its sibling services. `CacheNotifyPoller` and `ExpiredSessionCleanupService` call framework-internal code whose failure types can be enumerated; this one calls `IAuditLogSink`, a public DI seam where a deployment's custom sink can throw anything, so there is no list to write. Losing a batch of log records is strictly better than stopping the application, and the failure is reported at error level rather than swallowed. The class doc's claim that "records are never silently lost" was true only of the queue-saturation path and has been corrected.

### The analyzer release history was empty, so the rule that guards it could never fire

`AnalyzerReleases.Shipped.md` had not a single line, while the analyzers had shipped with `Bee.Definition` since 4.16.0. It is backfilled from tag snapshots rather than from memory: 22 rules added at 4.16.0, BEE3003 at 4.18.0, BEE4001–BEE4004 removed at 4.19.0.

Negative verification proved the blind spot is closed: changing the id of an already-shipped rule (BEE1007) now trips RS2003 — "shipped in analyzer release '4.16.0', but is no longer a supported diagnostic". With `Shipped` empty that rule could never trigger, which is exactly how BEE4001–BEE4004 retired in 4.19.0 with nothing to say so. This is now recorded as the third release baseline alongside the two `PublicAPI` files.

### 239 prose type references move under the compiler

`check-xmldoc-refs.sh`'s header said that anything expressible as `<see cref>` should use it, so the compiler can check it — but nothing enforced that sentence. The script verified "does this name still exist"; it did not verify "should this have been a cref in the first place". First-party references in prose accumulated as `<c>`, unprotected.

239 of them across 144 files were converted, using the compiler as the verifier: convert everything, build, revert precisely what the compiler reports by file and line, iterate to convergence. Types in other namespaces use fully-qualified names rather than added usings — an added using would trip IDE0005, and a fully-qualified name is equally checked. Same-project residue fell from 88 to 26, of which 17 are file names (`Foo.xml`, `Bar.razor`) that should be `<c>` anyway. The reverse check is now in the script.

That check immediately caught four violations introduced in this same review — and the reason they had survived is that the script, which would have caught them, had never been run.

## Fixed

### Every `AuditRule.*` call over JSON-RPC threw

`AuditRuleBusinessObject` declared only a three-parameter constructor while `BusinessObjectFactory` always activates with four arguments. C# constructors are not inherited, so every call mapped to `InternalError` — the per-form audit-rule maintenance form shipped in 4.25.0 was never reachable remotely, from the day it shipped.

Its only test constructed the type directly and never went through the factory, so the whole thing was green at release. `ReservedProgIdConstructionTests` now covers this at two levels: through the real factory, and through pure reflection (which needs no container). Neither hard-codes the factory's argument shape — the reflection version derives it from `BusinessObject`'s base constructor.

### The cache-notify baseline sat in the future on a fresh deployment

`CacheNotifyReader`'s empty-table baseline carried its own dialect table returning local time (`getdate()`, `LOCALTIMESTAMP`, `CURRENT_TIMESTAMP(6)`), while every row's `sys_update_time` is stamped UTC by the write side — both the column DEFAULT and `CacheNotifyService.BuildUpsertSpec` read `IDialectFactory.GetDefaultValueExpression`. Four of the five dialects disagreed; only SQLite matched. This violates [ADR-032](../adr/adr-032-datetime-timezone.md) D1: databases store UTC, conversion happens at the client.

The consequence: on a fresh deployment the first poll cursor lands in the future, and every subsequent poll window comes back empty. Cache invalidation stops silently until the wall clock catches up — eight hours at UTC+8.

Live evidence from the negative verification: Oracle returned `15:18:34` while UTC was `07:18:34`. And Oracle's `LOCALTIMESTAMP` follows the **client** session's timezone, not the database's, so the baseline depended on which machine was running the poller — worse than a server timezone.

It went unnoticed because the four local containers and the GitHub runner all run UTC, where the two expressions are simply equal. Oracle is the one dialect that shows it, precisely because it looks at the client.

The reader now derives the expression from the same source as the writer, and the duplicate dialect table is gone. Two tables that must agree will drift, and this one drifted silently. The gate has two layers: the expression must be identical to the write side (pure logic — under UTC the values agree, so comparing expressions is the only way to verify the *basis*), and four dialects run the statement for real and check the value is close to UTC.

### A sweep could evict a replay window still in use

`MemoryReplayWindowStore` stamped `Entry.LastTouchedMs` after `GetOrAdd` created the entry, leaving it at 0 in between. A sweep landing in that gap read 0, judged the entry older than any cutoff, and removed a window in active use — the session then received a fresh window, silently resetting replay protection once.

The gate is deliberately a structural assertion rather than a behavioural test. This race cannot be isolated behaviourally: reaching it requires an eviction lifetime in the millisecond range, and at that scale a thread delayed by the scheduler past the lifetime is a *legitimate* eviction — the test went red once in three runs with the fix in place. The first attempt was worse still: a parallel test that stayed green with the bug reinstated, which is worse than no test.

### A serialization failure was permanent, not transient

`XmlCodec.Serialize` and `JsonCodec.SerializeCore` were both written as a straight line: `NotifyBefore` → serialize → `NotifyAfter`. When serialization throws, the last step never runs and the object stays in `SerializeState.Serialize` **permanently**.

Permanent is the point. What gets serialized is often a process-wide cached definition instance — `SerializeDefine` has six call sites operating on cached objects. After one failure, every empty-collection getter on that instance returns `null` (`IsSerializeEmpty` holds only in the `Serialize` state) while several callers dereference with `!`. An empty collection is a perfectly normal state — a table with no indexes, for instance. A transient failure had been converted into a permanent one.

The fix is a scope rather than a `try`/`finally` in each of two places: "`NotifyBefore` must be paired with `NotifyAfter`" is exactly the kind of invariant that suits a structural guarantee, and two copies of the same shape are a shape that will diverge. `SerializationLifecycle.BeginSerialize` returns a `readonly struct` scope, so `using` on the concrete type allocates nothing.

### A NOT NULL column received `DBNull` in the Blazor head

Comparing the two heads' private copies of the form-data helpers found three verbatim identical and two drifted. One of the two was a live bug: the Avalonia head had already fixed "a NOT NULL column whose `DefaultValue` is still `DBNull` must not receive `DBNull`" — otherwise `EndEdit` throws `NoNullAllowedException` — and the Blazor copy was still carrying it. A raw ADO.NET column is the normal shape of a server response, so this was not a corner case. Sinking the shared implementation carried the fix across.

### `ClientInfo`'s single-user limit is now stated, and its lazy initialization guarded

`ClientInfo` holds one signed-in user's state in process-wide statics: access token, capability snapshot, entered company, and a definition cache carrying that user's tenant customizations. That is correct for a desktop head — one process, one user — and wrong for a host serving several users, where every session writes the same fields, the last login wins, and earlier users read someone else's identity.

This is a known limit rather than an oversight, but **nothing in the type system marked the boundary**, so a server-side UI head built on this package would inherit the flaw silently. `Bee.Api.Client` had already been through this — its per-user statics moved to `ApiSessionContext`, one per session — so the counter-example sat right next door with only this one lacking the warning. It now carries a warning equivalent to `ApiSessionContext`'s, which reaches consumers through IntelliSense.

The three `??=` lazy initializations are also guarded. The getters are entered by the UI thread and by `ConfigureAwait(false)` continuations, so two threads can each build an instance. The wasted one is not the problem; **the orphan is** — `ResetDefineCache` clears the instance it holds while callers keep using the other, so a tenant switch leaves the old customized definitions in place. `Lazy<T>` was deliberately not used: these are *resettable*, and replacing the whole `Lazy` instance only relocates the race.

### Five false claims in the definition layer's README

The review reported two lines; the same README had five stale claims from shipped changes, and fixing two would have manufactured the impression it was clean.

The dependency list still named MessagePack, removed in 4.19.0 — a claim that directly contradicts the core conclusion of [ADR-036](../adr/adr-036-wire-serialization-externalized.md) and [ADR-038](../adr/adr-038-definition-dependency-boundary.md), in the document an external developer reads first. And "no business logic and no I/O" stood against 7 files and 1,121 lines of file IO in the definition layer. That second one is not a missed update but an active denial of a known, twice-recorded architectural issue. Since moving the IO out remains deferred, the text now states the situation and why it persists: `BackendDefaultTypes.DefineStorage`'s type name is written into every existing deployment's `SystemSettings.xml`, so the move requires a compatibility mapping for old type names — data migration rather than refactoring. Deleting the three words "no I/O" was deliberately not enough; what remained would still have read as a guarantee.

## Upgrade

Most deployments need no change. Six things are worth a look:

- **Reading a contract collection through the interface type.** `ISaveResponse.AffectedRows` and `IEnterCompanyResponse.Capabilities` are now `IReadOnlyDictionary`. Reading through the concrete `SaveResponse` / `SaveResult` is unaffected; only a declaration naming `Dictionary<,>` via the interface needs an edit.
- **Constructing a BO directly.** If the code relied on the in-process path, say so: `new SystemBusinessObject(sessionInfo, isLocalCall: true)`. Otherwise the four second-line guards now apply — which is the point of the change. Note that an already-compiled assembly keeps the old default until it is recompiled.
- **`HttpUtilities`** moved from `Bee.Base` to `Bee.Api.Client`. One `using` line; the calling style is unchanged.
- **`System.CheckPackageUpdate` and `System.GetPackage` are gone.** A host that implemented either extension point should remove its override. There is no replacement, and there was no caller.
- **A cross-language client reading `DataTable` cells** must accept `decimal`, `long` and `ulong` as quoted JSON strings. Its writer needs no change — the reader still accepts bare numbers, so a client written against the 4.27.0 fixtures keeps working in that direction.
- **Two behavioural changes to check downstream.** A deployment that computes password hashes itself and writes them into `st_user.password` through a FormSchema data path will now be refused by `RemoveProtectedFields`; the framework has no path of its own that writes that column. And audit-log queries issued without entering a company now return nothing rather than every tenant's records.

A MySQL deployment whose column descriptions or default values contain a backslash could not upgrade at all before — the generated DDL was a syntax error — and now writes correctly, assuming the server's default `sql_mode` without `NO_BACKSLASH_ESCAPES`.
