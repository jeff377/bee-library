# Bee.NET 4.27.0 — Detailed Release Notes

[English](4.27.0.md) ・ [繁體中文](4.27.0.zh-TW.md) ・ [← CHANGELOG](../../CHANGELOG.md)

This document is the detailed version of the `[4.27.0]` entry in [CHANGELOG.md](../../CHANGELOG.md). The main CHANGELOG lists one line per change; this file keeps the full narrative — the *why*, the constraints, and the design context behind each change.

> A browser front end could not call an encoded endpoint. The wire body was MessagePack and nothing else, and this framework's MessagePack wire is some thirty hand-written formatters — mirroring them in another language creates a second authority over the same contract, with nothing to notice when the two drift. This release moves the choice of body codec from a deployment setting to a per-request declaration on the envelope, and adds a JSON codec alongside MessagePack. A JavaScript client then needs only JSON, gzip, AES-CBC-HMAC and RSA, all of which are native. Two artefacts ship with it so a client in another language has something to check itself against rather than a document to obey: 26 wire body samples, and a TypeScript contract generated from the message types by reflection. See [ADR-044](../adr/adr-044-payload-codec-negotiation.md).

## Breaking changes

### `ApiPayloadOptions.Serializer` is removed

Once the codec is declared per request, this setting had exactly one remaining job: deciding what the server reads when a client declares nothing. And that answer can only ever be `messagepack` — every client predating negotiation declares no codec and sends MessagePack, so setting it to `json` would break all of them at once. It had stopped being a deployment choice and become a compatibility constant, and a knob whose only correct position is one of its values is worse than no knob.

Under the pre-stable policy this ships as a minor, listed rather than silent.

An existing `SystemSettings.xml` needs no edit. `XmlSerializer` ignores unknown elements, so a leftover `<Serializer>` element is inert and deserialization still succeeds — but it is inert, not respected, which is exactly the kind of thing worth deleting while you remember why.

## Added

### The body codec is declared per request

`ApiPayload.Codec` carries the codec name on the envelope, and both `TransformTo` and `RestoreFrom` read it from the payload rather than from configuration. The name arrives from the wire, so it is shape-checked before it is echoed — lowercase alphanumerics and hyphens, with a length cap.

`PayloadCodecNames` holds the two names (`json`, `messagepack`); `ApiServiceOptions.AcceptedPayloadCodecs` and `ResolvePayloadSerializer` resolve one into a serializer. A request that names none is read as MessagePack, which is what every client predating negotiation sends — so an envelope carrying no codec is byte-for-byte what it was before.

Both codecs are always available; there is no enablement gate. One was implemented and then removed, because the premise behind it turned out to be false: the reasoning was that another codec means another parser reachable anonymously, but `System.Text.Json` was already on that path — the envelope itself is JSON, a `Plain` body is deserialized by `ApiInputConverter`, and `System.Login` is anonymous by design. A JSON body codec introduces no parser class that was not already reachable.

### `JsonPayloadSerializer` and the value envelope

JSON cannot tell a `decimal` from a `double`, or a `Guid` from a `string`. Wire members typed as `object` therefore travel as a discriminated envelope, `[code, value]`, written by an internal converter; without it the wrong type arrives silently, which is worse than an error. The discriminator reuses the existing `WireValueCode`, so `WireValueCodePinTests` pins both wires at once.

`decimal`, `long` and `ulong` are written as JSON strings. A JSON number is a `double` to every JavaScript reader, which holds neither `decimal` precision nor integers above 2^53.

### Codec-aware transformer overloads

`IApiPayloadTransformer` gains three-argument `Encode` and `Decode`. They are **default interface members that throw** `NotSupportedException` rather than falling back to the deployment default: falling back would encode the body with a codec the caller did not ask for, and the caller would decode the answer with the one it did. Calls that declare no codec still go through the existing two-argument overloads, so a custom transformer written before negotiation existed keeps serving every one of them unchanged.

### `ApiConnector.PayloadCodec`

Lets a .NET client declare a codec. Unset means MessagePack, so existing client code is unaffected.

### Wire body samples

`wire-fixtures/bodies/` holds 26 samples produced and verified by `WireFixtureTests`, with a README that explains the envelope structure and the six rules a reader is most likely to get wrong. The audience is the author of a client in another language, so it is written in English.

They cover **every encoding rule** rather than every wire type. One sample per type would produce hundreds of near-identical files and still miss the places that actually go wrong; what is here is the 22 wire value discriminators, `DataTable` (including `rowState` and the original/current pair on a modified row), `DataSet`, and two representative message types.

Only the body text is fixed, not the compressed or encrypted bytes. gzip output is not guaranteed stable across .NET versions and AES-CBC uses a fresh IV every time — those two layers are inherently unpinnable, and each language's own library is what guarantees them.

When a sample stops matching, the test fails and tells you to regenerate with `BEE_REGENERATE_WIRE_FIXTURES=1` and read the diff. That diff *is* the description of what changed on the wire.

### A TypeScript contract generated from the message types

Hand-copying a type table into TypeScript is a second authority over the same API contract: rename a field on the server and the copy does not find out, and the symptom is a field silently missing rather than an error. `wire-contracts/messages.d.ts` is generated by reflection instead, and `WireContractGeneratorTests` turns "the contract changed" red here.

What it describes is the **wire shape**, not the CLR shape, because what a reader wants to know is what the JSON looks like: `Guid` and `DateTime` are both `string`, enums are string literal unions (the server writes them through `JsonStringEnumConverter`), an `object` member is the `[code, value]` envelope, and `DataSet` / `DataTable` follow their custom converters. Those last shapes are invisible to reflection, so they are hand-written in the generator's preamble and pinned by a canary in the test.

The output covers 91 interfaces and 11 enums, and no generated property falls back to `unknown` — the type mapping has no gaps.

`wire-contracts/type-names.ts` is a second file carrying the assembly-qualified type names. An encoded payload has to name its type in the envelope, and the server resolves it through an allowlist; that string carries a namespace and an assembly name, so a hand-copy drifts the first time a message type moves — and the symptom is a run-time rejection, not a compile error. It is a separate file because `.d.ts` cannot carry values, and both files are pinned by the same tests.

### Named declaration of the anonymous attack surface

Methods callable without a login *are* the framework's anonymous attack surface, and the only thing declaring one is an attribute argument — adding a method marked `Anonymous` asks nobody for a justification. `AnonymousApiSurfaceTests` is that request: an undeclared method fails, and every entry must state what an unauthenticated caller learns from the response. Phantom entries fail too, so the next security review is not misled about the surface's size.

It also pins something that had never been written down: **the two gates decide from different sources, and they are not aligned.** `ApiAuthorizationValidator` decides at the HTTP layer from a hard-coded method-name list whether an `Authorization` header is required; `ApiAccessValidator` decides at the business-object layer from the attribute whether a token is validated. Four methods marked `Anonymous` are absent from the HTTP list (`GetCommonConfiguration`, `CheckPackageUpdate`, `GetPackage`, `ExecFuncAnonymous`) and so require a header — but that header is only checked for being parseable as a `Guid`, and the business-object layer does not validate it because the method is anonymous. Any GUID passes both.

This is not a vulnerability; those four are anonymous by design. The problem was that the header check made them *look* protected. The test asserts the behaviour by calling `Validate`, so it is an executable fact rather than a claim in a comment.

Alongside it, `ApiAccessControlPinTests` pins the protection level and access requirement of every API method. Raising a method from `Public` to `Encrypted`, or from `Anonymous` to `Authenticated`, rejects existing clients on the spot — including front ends that do not ship with the framework — and nothing used to notice: attribute arguments do not appear in `PublicAPI.Shipped.txt`, so the analyzer cannot see them, and the wire samples cannot either, because the change alters who may send a payload rather than its shape. The expected values are written as strings, not enum references, so renaming a member cannot quietly move the list and the test along with it.

## Fixed

### A `Filter` sent on the `Plain` path lost its entire subtree

`GetListRequest.Filter` is declared as the abstract `FilterNode`, and `System.Text.Json` binds to the declared type — so a `FilterGroup` assigned to it wrote out `{"kind":"Group"}` and nothing else. The operator and the whole filter tree disappeared, with no exception and no trace.

This predates the codec work. `FilterGroup.Nodes` has had a `FilterNodeCollectionJsonConverter` for some time, but the single-node half was missing, and encoded bodies only ever went through MessagePack, which has its own filter node formatter. The defect sat on the `Plain` path where nobody hit it. With a JSON body codec it would have taken effect on the most common query there is.

`FilterNodeJsonConverter` is applied **on the property, not the type**. Applied to `FilterNode` it would be inherited by the subclasses, so writing a `FilterGroup` re-enters the same converter and recurses until the stack goes — a segfault, not a catchable exception. That was hit for real during implementation.

Two layers guard it: `FilterNodeJsonConverterTests` for behaviour, and `FilterNodeConverterCoverageTests`, which scans by reflection so that a new writable `FilterNode` property without the annotation turns red. Get-only properties are excluded — `DeleteContext.ScopeFilter` among them, an object that also carries a repository interface and never goes through JSON.

**This is a behavioural change.** A `Plain` request that sent a `Filter` previously lost its conditions, which made the call equivalent to an unfiltered query; the conditions now arrive. Callers depending on the old behaviour are near-inconceivable, but a query that used to return everything will now return a filtered set.

## Changed

### ADR-044, and its relationship to ADR-014

Codec negotiation reaches external users — an extra field on the envelope, a setting removed, a custom transformer that may need a new overload — so the decision is recorded as an ADR rather than left in a plan.

[ADR-014](../adr/adr-014-jsonrpc-plain-public-default.md) had already laid a path for the same problem (`Plain` plus seven methods lowered to `Public`) and explicitly rejected building a JavaScript encryption pipeline. Two ADRs on one subject that do not cite each other is a hole someone falls into later, so ADR-044 now works through that rejection point by point: two of the three reasons rest on premises that have changed — the cost of aligning byte-for-byte is what the wire samples exist to solve, and "every front-end framework reimplements it" is the argument for shipping one npm package. The third is a real difference of position, and it turns on whether HTTPS alone is enough, which is the deploying party's judgement rather than a technical question.

ADR-014 keeps its text per repo convention; a note on its status line points to ADR-044 so the two are reachable from each other. It is **not superseded**: `Plain` remains the default path for a JavaScript front end, and the seven methods remain `Public`.

## Upgrade

Nothing to do. A request that declares no codec produces a byte-for-byte identical envelope and behaves exactly as before.

Three things are worth a look:

- **Delete the `<Serializer>` element** from `SystemSettings.xml` if it is still there. It is ignored rather than honoured, so leaving it in place is harmless but misleading.
- **A custom `IApiPayloadTransformer`** keeps working for every call that declares no codec. To serve clients that negotiate one, implement the three-argument `Encode` and `Decode` overloads; until then they throw `NotSupportedException` rather than silently using the wrong codec.
- **`Plain` requests carrying a `Filter`** now apply that filter. If anything downstream was written against the unfiltered result, this is the release that changes it.

To send a JSON body from a .NET client:

```csharp
connector.PayloadCodec = PayloadCodecNames.Json;   // unset means MessagePack
```
