# Bee.NET 4.23.0 — Detailed Release Notes

[English](4.23.0.md) ・ [繁體中文](4.23.0.zh-TW.md) ・ [← CHANGELOG](../../CHANGELOG.md)

This document is the detailed version of the `[4.23.0]` entry in [CHANGELOG.md](../../CHANGELOG.md). The main CHANGELOG lists one line per change; this file keeps the full narrative — the *why*, the constraints, and the design context behind each change.

> This release closes a hole in the rule that a `FormLayout` is the authority on what a form shows. That rule already held for tenant customization — adding a field to a base schema does not make it appear on a tenant's customized screen — but it did not hold when the layout file was absent: the runtime quietly derived one from the `FormSchema`. A derived layout is a projection nobody reviewed and that exists nowhere, which is exactly what an authority is supposed to rule out. **Layouts are now produced at design time and read as stored; a missing one is a configuration error.** The generator stays in the framework and becomes public API, and `tools/DefineEditor` grows the command that produces the file.

## Breaking Changes

### `FormLayout` is produced at design time; the runtime no longer derives one

`FormSchema.GetFormLayout(string)` is **removed**. It was a one-line call to `FormLayoutGenerator`, and its shape was the problem: `Schema.GetFormLayout()` is what a runtime path reaches for without deciding to. Generation now requires naming the generator explicitly — `FormLayoutGenerator.Generate(schema, layoutId)` — which makes the intent visible at the call site.

This is the same line as the earlier decision that a `FormLayout` is the authority on what appears on screen. `Bee.Analyzers` already carried **BEE2005** ("a FormSchema should have a corresponding FormLayout") as a preview of this position, but the thing it warned about was silently patched over at runtime, so the warning had no consequence behind it. It now does.

Three runtime paths change:

- `FormDefinitionLoader.GetRuntimeLayoutAsync` throws `InvalidOperationException` when neither the tenant layer nor the base layer stores a definition, instead of generating one. The message names the missing `layoutId` and the relative path the file belongs at.
- `FormView` (Avalonia) resolves its layout through the new `ResolveLayoutAsync`: the `Layout` a host supplied, else the `DefinitionLoader`'s assembled runtime layout, else the stored base definition fetched through `ClientInfo.DefineAccess`.
- `FormPage` (Blazor Server) reads `GetDefineAsync<FormLayout>` on its no-loader path rather than deriving from the schema it just fetched.

The decision and its alternatives are recorded in [ADR-039](../adr/adr-039-formlayout-design-time-only.md).

What does **not** change is how the two layers combine. `CustomizeOverlay.PickFormLayout` is untouched — a tenant's layout still wins outright over the base layout, whole-file, and the two are never merged.

Note that a missing base definition usually surfaces from the *server* rather than from the loader's own guard: `ClientDefineAccess.GetFormLayoutAsync` goes through `GetDefine` / `DefineType.FormLayout`, which reaches `CacheDefineAccess.GetFormLayout(layoutId)` — and that overload already threw on a missing file. The loader's `InvalidOperationException` covers the remaining case where the server answers with an empty payload.

**Who this breaks.** Any deployment relying on runtime derivation — that is, one with a `FormSchema` and no matching `FormLayout` file — will fail when the form is opened. That is the intent of the change, and BEE2005 lists exactly which schemas are affected at build time. See the Upgrade section.

## Added

### `FormLayoutGenerator` becomes public API

`Bee.Definition.Layouts.FormLayoutGenerator` changes from `internal` to `public`, with `<remarks>` stating its design-time position. It stays in `Bee.Definition` rather than moving to `tools/`, for three reasons: the existing generator tests would have nowhere to live (`tools/DefineEditor` has no test project, only its own `Smoke.cs`); the repo's scaffolding workflow calls it as a framework public API; and `DefineEditor` is not the only definition tool anyone might build.

`GetListLayout()` and `GetLookupLayout()` are deliberately **left alone**. The list and lookup field sets are declared on `FormSchema` itself (`ListFields`, `LookupFields`), there is no `DefineType` for them and no file form — they are projections of the schema rather than independent definitions. A single-record form layout is a different thing.

### `FormView.Layout` (Avalonia)

A public styled property, the counterpart of `FormView.Schema`, and it exists for the same case: a host may drive the view with definitions it built itself and no backend behind them. `samples/Avalonia.DemoCenter` is exactly that — its layout modules build a schema in code and never talk to a server. Such a host now supplies the layout it wants rendered; the view does not invent one.

### "Generate FormLayout" in `tools/DefineEditor`

The FormSchema editor's schema node gains a context-menu command that writes `{DefinePath}/FormLayout/{ProgId}.FormLayout.xml` and opens it. This is where a layout comes from now, so the tool that edits definitions had to be able to produce one.

Regenerating over an existing file **asks for confirmation first** — it discards any hand-tuning of the layout, and that is the only destructive thing the command does. A new `DocumentViewModelBase.DefineFileGenerated` event carries the written path to the main window, which rescans the tree and selects the file; a document view-model has no reference to the solution tree, so having it raise an event keeps the dependency pointing one way.

## Fixed

### The Blazor demos could not sign in

`samples/Blazor.Server.Demo` and `samples/QuickStart.Server` both failed at login with `no such table: st_user`. The cause was a misreading baked into the demo backend: overriding authentication was taken to mean the common system tables were not needed. It does not. `AuthenticateUser` replaces the credential check and nothing else — the rest of the login path still reads the user's locale from `st_user` and persists the session seed to `st_session`.

`DemoBackend` now materializes both tables alongside `st_cache_notify`, and `DemoSchemaSeeder` creates them and seeds the matching locale row. The seeded row carries no password and no locale values: a blank stored hash is rejected outright by `UserRepository.VerifyPassword`, so the row cannot be signed in to on its own, and blank locale values are what make the session fall back to the deployment-wide defaults in `BackendConfiguration`.

## Changed

### `st_*` system tables are documented as required infrastructure

The demo defect above traced back to something that had never been stated: the framework reads and writes its `st_*` tables while serving ordinary requests, so a deployment creates them whether or not it has a use for them of its own — and overriding a framework behaviour does not exempt a deployment from the tables behind it.

[Framework-Reserved Names](../framework-reserved-names.md) §1 now says so, since it is the single source of truth for which `st_*` tables exist and therefore where a reader looking them up will be. Five places that said the opposite are corrected, including the one that started it: `SystemBusinessObject.ApplyUserLocale`'s remarks read "a deployment may authenticate against something other than `st_user`, in which case there is no row to read", which describes a missing **row** but reads like a missing **table**.

`UserRepository.GetLocale` is left as it is. It tolerates a missing row and not a missing table, and under this rule that is correct: the table is required, so its absence is a deployment error and should fail loudly.

## Upgrade

**Every `FormSchema` needs a `FormLayout` file.** Build with the analyzers enabled and BEE2005 lists the schemas that lack one:

```
BEE2005: FormSchema 'X' has no corresponding layout at FormLayout/X.FormLayout.xml,
so opening the form fails at run time.
```

To produce the missing files, open the definition folder in `tools/DefineEditor`, select the FormSchema node, and run **Generate FormLayout**. The generated file is a starting point meant to be reviewed and adjusted — it is a definition from that point on, not a derived artifact.

Mechanical substitution for code that called the removed method:

```diff
- var layout = schema.GetFormLayout(layoutId);
+ var layout = FormLayoutGenerator.Generate(schema, layoutId);
```

Note the `using Bee.Definition.Layouts;` this needs, and note also that it is the right substitution only for design-time code — a definition tool, a test fixture, or a host building definitions in memory. **Runtime code should read the stored definition instead**, through `FormDefinitionLoader.GetRuntimeLayoutAsync` or `IDefineAccess`.

Hosts that drive `FormView` with a schema and no backend set the new property:

```diff
  var view = new FormView { Schema = schema };
+ view.Layout = FormLayoutGenerator.Generate(schema, progId);
```

No coordinated deployment is required: the wire format and the customization overlay semantics are unchanged.
