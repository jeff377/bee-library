# Bee.NET 4.17.0 — Detailed Release Notes

[English](4.17.0.md) ・ [繁體中文](4.17.0.zh-TW.md) ・ [← CHANGELOG](../../CHANGELOG.md)

This document is the detailed version of the `[4.17.0]` entry in [CHANGELOG.md](../../CHANGELOG.md). The main CHANGELOG lists one line per change; this file keeps the full narrative — the *why*, the constraints, and the design context behind each change.

> The headline of this release is **business logic plugins**: attaching customer code to the existing flow of a packaged BO — without replacing the whole BO class, adding only a step at a specific point. This is the fifth customization mechanism and fills the "lightweight extension" gap: previously, adding a single pre-save check for one tenant meant inheriting and overriding an entire BO, a granularity far heavier than the need. Plugins also bring the customization layer's **first write path** — `PluginSettings` is the only customization definition with a maintenance API; the rest of the layer stays read-only.
>
> Two customization behaviour fixes ship alongside: `ProgramItem` override semantics change from *whole-item replacement* to **property-level inheritance**, and BO type resolution failure changes from silent fallback to **fallback with logging**. Both surfaced only after `ProgramItem` gained its `Repository` binding in 4.16.0.

## Added

### Business logic plugins

- **`PluginSettings` is a new definition type (the 13th `DefineType` member).** It carries "which plugins are bound to each progId", structured as `PluginSettings` → `ProgramPluginItemCollection` → `ProgramPluginItem` (keyed by `ProgId`) → `PluginItemCollection` → `PluginItem` (**keyed by type name**). Keying on the type name means declaring the same type twice for one program is rejected at load time rather than silently running twice. The new member is appended to the end of the enum, so wire values are not renumbered. The full read pipeline landed — file paths in `PathOptions` and `CustomizeOnlyPathOptions`, three storages (File / CustomizeOnly / Db), `PluginSettingsCache`, `ICacheContainer` and `CacheContainerService`, `CacheDefineAccess`, `CustomizeDefineReader`.

- **`FormBusinessPlugin` and four mount points.** `BeforeSave` / `AfterSave` / `BeforeDelete` / `AfterDelete`, executed in order **after the final implementation** of the corresponding `Do*` sub-method — that final implementation may be the packaged BO's base or a custom BO's override, so **inheritance and plugins compose**. The base class provides four virtual no-ops; a plugin overrides only the points it needs.

  There are deliberately only four mount points. The draft had one per `Do*` sub-method (six); the two post-`DoSave` / `DoDelete` points were cut not for lack of use cases but because they behave identically to the `After` points: both run outside the transaction, both can modify `RefreshedDataSet`, and auditing reads the diffgram captured before `DoSave`, so neither affects it. Keeping them would only force a choice with no correct answer. The bar for adding a mount point is three tests: distinguishable from its neighbours, has a concrete use case, and does not lead people somewhere dangerous — the third rejects otherwise-useful candidates, e.g. a pre-`DoSave` point falls after the audit snapshot, so data changed there reaches the database but not the audit trail. The asymmetry is recorded in the design: mount points are public contract, **adding is non-breaking, removing is breaking**, so the default is few, expanded by real demand.

- **Execution: `FormPluginChain` / `FormPluginRunner` / `IFormPluginResolver` / `PluginSettingsResolver`.** The chain determines which points each type implements via reflection (comparing `MethodInfo.DeclaringType`) — one piece of data serving two purposes: filtering out no-op calls, and `TypesForStage` for maintenance tooling to display execution order, offsetting the readability cost of "you can't tell from the settings file which plugin runs at which point".

  **Instance lifetime is per-operation**: constructed once per Save / Delete, with all points in that call sharing the same instance and passing state through instance fields. This is the only substantive advantage of the chosen declaration granularity ("the settings file lists types only; points are decided by the class overriding them") — with per-point construction it would reduce to "a few less lines of XML", not worth giving up the readability of an explicit *point × type* settings file.

  **Resolution failure always throws, the opposite of the BO axis's silent fallback.** A binding names "this program *is* this type"; falling back still leaves working code. A plugin is something the author deliberately added — skipping it means the customization silently did not happen, and silently dropping a credit-limit check is worse than refusing to save.

- **The two layers add, they do not choose.** `CustomizeOverlay.GetPluginTypes` is the only additive granularity in the customization overlay: the packaged chain first, the tenant chain after. **The cost is that a tenant cannot disable a packaged plugin** — there is no tombstone syntax; removing one means inheriting the BO and overriding that step.

### The customization layer's first write path

- **`SystemBO.GetCustomizePluginSettings` / `SaveCustomizePluginSettings` (`LocalOnly`).** These let a deployment maintain a tenant's plugin bindings through the framework's own API instead of placing files by hand. Both are guarded twice — `LocalOnly` plus `IsLocalCall` (the attribute only guards the JSON-RPC dispatch path; callers constructing the BO directly never pass through it). Reading returns an empty string when there is no customization, so the caller edits from a blank definition without distinguishing "absent" from "empty"; writing replaces wholesale, and empty XML clears, so no second API is needed.

  **Every type is validated before the write** — loadable, derives from `FormBusinessPlugin`, and overrides at least one point; one bad entry rejects the whole document. Placing validation here is the point: the person editing finds out about the typo immediately, not weeks later when some document fails to save. Changes are written to the deployment audit trail.

- **`ICustomizeDefineWriter` and `CustomizeDefineWriter`.** A single write method; the rest of the customization layer stays read-only. In file mode the write evicts that tenant's cache slot immediately — a maintenance tool will read back what it just saved, and the file watcher's "eventually" is not the right contract here. `CustomizeOnlyStorage` remains fully read-only; writes go through the writer directly via `CustomizeOnlyPathOptions`, so that class's read-only promise does not have to break for a single exception.

- The wire carries **XML strings in both directions**, not `PluginSettings` objects. `Items` / `Plugins` are get-only nested collections — the same shape that layout customization already hit, where objects arrive at a .NET client and silently come back empty.

### Documentation

- **New [tenant customization guide](../customization.md) (bilingual).** With all five customization mechanisms complete, the material was scattered across three places and had three real gaps: language and layout customization had **no how-to at all** (the most common need), there was no "I want to change X → use Y" table, and `docs/README` had no customization entry. The new document fills gaps and serves as the entry point: a decision table (noting "use the lightest mechanism that works"), a language how-to (namespace equals ProgId, three sub-key forms, a minimal complete example, and the whole-enum replacement exception), a layout how-to (whole-file replacement, "owning it completely cuts both ways", and that it is actually assembled by the client's `FormDefinitionLoader`), what cannot be customized and why, and read-only vs writable.

- **`development-cookbook` gains a "business plugins" section (bilingual).** Inheritance vs plugin selection criteria, what each of the four points can see, per-operation instances, binding file format and additive semantics, the `LocalOnly` maintenance API, and a division-of-labour table for "where should external system sync live" — **plugins run outside the transaction, so a process dying before the plugin runs means the data is committed, the sync never happened, and nothing records that**. Sync that cannot be missed belongs in an outbox registered inside the transaction; plugins suit best-effort work or work with a reconciliation backstop.

## Changed

### `ProgramItem` moves to property-level inheritance

Since `ProgramItem` gained its `Repository` binding in 4.16.0, whole-item replacement became a trap: **a customization that only wants to swap the BO, without restating `Repository`, silently drops the entire document's data access back to the generic `DataFormRepository`** — an empty string is a legitimate "use the framework default", not an error, so the loss is never reported. The reverse (writing only `Repository`) drops the BO back to `FormBusinessObject`.

`CustomizeOverlay.FindProgramItem` now returns a composite: when both layers declare, a new `ProgramItem` is built property by property (custom when non-empty, otherwise packaged); when only one layer declares, that layer's instance is returned directly. **The composite must be a new instance** — both layers are process-wide caches and must not be mutated. "Deliberately falling back to the framework generic" is now expressed by naming the type explicitly, not by clearing the property. A reflection guard test enumerates every public writable string property on `ProgramItem`, so adding one without updating the composition logic turns the suite red. [ADR-016](../adr/adr-016-multitenant-customization-overlay.md)

### BO type resolution failure now logs

When a regular progId's BO type cannot be loaded or does not derive from `BusinessObject`, the fallback to `FormBusinessObject` remains (service is not interrupted), but an **error is now logged** with the progId, the type name, and whether it was declared by the customization or packaged layer — **without which multi-tenant diagnosis is impossible**. The logger arrives via a new three-parameter constructor rather than a defaulted parameter on the existing one: the latter is source-compatible but a **binary breaking change**. It is injected with `GetService`, so hosts without logging are unaffected. Because of the type cache, each `(customizeId, progId)` logs once.

### Other

- **`DeleteContext.Snapshot` loading now also considers "does this progId have a delete-point plugin".** Without it, whether a snapshot exists depends on the change-audit toggle — the same sync plugin working in one deployment and receiving `null` in another is the hardest class of difference to diagnose.

- **`IDefineAccess` / `IDefineStorage` / `ICustomizeDefineReader` / `ICacheContainer` gain `PluginSettings` members.** Anyone implementing these interfaces must add the corresponding members. `IDefineAccess` deliberately does **not** get a `GetPluginSettings(customizeId)` overload — `ProgramSettings` has none either, and the consumer performs the overlay; an overload that looks like it overlays but returns base only would mislead.

- **`DbDefineStorage.Write` gains a `customizeId` parameter.** Tenant rows and base rows differ only by `customize_id`, so the two layers never overwrite each other. `define_type` comes from `typeof(T).Name`, so no schema change is required.

- **`BusinessObject` gains `protected IBeeContext Context`.** Plugin constructors take the whole context, whereas the BO previously exposed only the individual services. The resolver is obtained lazily through `Services.GetRequiredService<T>()` rather than added to `IBeeContext` (mirroring `RuleProcessor` in the same file, avoiding a public contract change).

- **The transaction boundary of BO extension points is now an explicit contract (documentation only, zero behaviour change).** It has always been the case that **only `Do*` runs inside the database transaction** — the transaction is opened and committed by the repository inside `DoSave` / `DoDelete` — but that fact existed only in the implementation. Someone overriding `DoAfterSave` had no way to know they were outside the transaction with data already committed; someone doing a concurrency check in `DoBeforeSave` had no way to know it was a **TOCTOU window**. Each of the six sub-methods now carries `<remarks>` stating whether it runs in the transaction; `DoBefore*` additionally documents the TOCTOU window and aborting via `UserMessageException`; `DoAfter*` documents "throwing here leaves data committed" and recommends queueing side effects. Public `Save` / `Delete` gain a pipeline diagram and guidance to override the sub-methods rather than themselves. The existing `development-cookbook` example in that section demonstrated overriding `SaveResult Save` — which also takes over `AuthorizeSave` and the write-scope check, contradicting this contract — and now overrides `DoBeforeSave`.

- **`api-bo-contract-design` naming table gains an `XxxContext` row.** The framework has two parameter conventions, but only `Args`/`Result` was documented. The rule: **`Args`/`Result` for cross-layer transport, `Context` for state shared within a flow.**
