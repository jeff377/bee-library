# Bee.NET 4.31.0 — 詳細變更說明

[English](4.31.0.md) ・ [繁體中文](4.31.0.zh-TW.md) ・ [← CHANGELOG](../../CHANGELOG.zh-TW.md)

本文件是 [CHANGELOG.zh-TW.md](../../CHANGELOG.zh-TW.md) 中 `[4.31.0]` 條目的詳細版本。主 CHANGELOG 每項變更一行；本檔保留完整敘述——每項變更背後的**原因**、限制與設計脈絡。

> 本版把三條**靜默的退路換成出聲的失敗**。每條退路在它被寫下的地方看起來都無害，代價卻都出現在別處：一個沒人選過的小數位數、租戶覆寫整批關閉而每個請求照樣成功、以及把「漏註冊」回報成「找不到建構子」。**兩項破壞性變更依 pre-stable 政策以 minor 發佈。**

## 破壞性變更

### 公司本幣改為必填

`NumberFormatResolver` 依金額的參照幣別解析小數位數：欄位的 `CurrencyField`，否則主檔列的 `sys_currency`，否則公司的 `DefaultCurrency`。在此之前公司本幣允許空白，遞補鏈會一路退到框架預設的兩位。

現在三個條件同時成立時擲 `InvalidOperationException`：金額沒有參照幣別、上下文中有公司、且該公司的 `DefaultCurrency` 為空或純空白。**完全沒有公司上下文時**——client 尚未進入公司，或 `RoundingContext.ForCompany(null)`——仍退框架預設，因為那不是設定錯誤。這項檢查與是否部署幣別主檔無關。

**為何這裡不該退回**：兩位看起來沒錯，但那不是該公司任何幣別選的位數，而下游沒有任何東西分辨得出來。本位幣金額（`home_amount`）也會以同樣錯的位數捨入。

**為何失敗落在計算，而不是載入或進入公司時**：框架本身不寫入 `st_company`——公司主檔在框架之外維護——所以沒有寫入路徑可以檢查。若在 `EnterCompany` 就拒絕，只需要公司名稱的呼叫也會跟著失敗。

會在哪裡浮現：

| 路徑 | 是否擲出 |
|------|---------|
| 伺服端存檔捨入（`FormBusinessObject` → `FormExpressionCalculator` → `RoundByKind`） | 是 |
| client 即時計算（`FormLiveComputation`） | 是——而且**不會**被 degrade 吞掉；degrade 是給客戶寫錯運算式用的，不是給設定錯誤用的 |
| `NumericEdit` / `GridControl` 的顯示格式 | 否——它們建立的上下文不帶公司，幣別代碼改以參數傳入 |
| 交付 schema（`NumberFormatApplier.Bake`） | 否——金額從不 bake |

框架不代選預設幣別，`st_company.default_currency` 也仍然沒有資料庫預設值：由建立公司資料的一方寫入。

**相容性**：二進位相容，公開 API 未變。`CompanyInfo.DefaultCurrency` 的屬性預設值仍是空字串，讓序列化器能 round-trip 未設定的值。決策記於 [ADR-026](../adr/adr-026-numeric-semantics-rounding.md) 的修訂紀錄。

### `RepositoryFactory` 的型別解析交給 `IRepositoryTypeResolver`

起因是 SonarCloud 的 S107（建構子八個參數），但做法不是把參數塞進 options 物件。第七、第八個參數（`customizeReader` / `sessionInfoService`）連同 `ResolveFormRepositoryType`、`FindProgramItem`、`GetCustomizeId`，其實是同一件事：**progId → repository 型別，含租戶客製 overlay**。BO 軸早已把這件事獨立成 `IBoTypeResolver`，repository 軸卻 inline 在工廠裡。抽出 `IRepositoryTypeResolver` / `ProgramSettingsRepositoryTypeResolver` 之後，工廠只剩「建構」一件事。

三個設計重點：

- **resolver 收 access token 而不是客製代碼**——刻意與 `IBoTypeResolver` 不同。客製代碼只能取自 session，介面簽章不留傳入它的位置，這道跨租戶防護就由簽章本身執行。
- **`typeResolver` 為必填。** 若給一個只看基底註冊表的預設值，宿主漏註冊 resolver 時，每個租戶的 Repository 覆寫會整批失效，而每個請求照樣成功。
- **工廠會檢查任何 resolver 回傳的型別**都衍生自 `DataFormRepository`，因為 resolver 現在可以被替換。

API 變更：

- `RepositoryFactory` 建構子移除 `customizeReader` / `sessionInfoService`，並在 `cacheNotify` 之前新增必填的 `IRepositoryTypeResolver typeResolver`。
- **移除**：`protected RepositoryFactory.ResolveFormRepositoryType`。
- **新增**：`IRepositoryTypeResolver`、`ProgramSettingsRepositoryTypeResolver`。

**相容性**：原始碼與二進位皆破壞——以舊建構子編譯的呼叫端會得到 `MissingMethodException`。**經 `AddBeeFramework` 建構工廠的部署不受影響**，Hosting 層已註冊 resolver。保留舊建構子並另加多載的做法試過且否決：它解決不了 S107，而且 `ActivatorUtilities` 與容器仍會選用參數較多的舊建構子。

## 修正

### Hosting 浮出相依注入的建構失敗

`ActivatorUtilities` 解不出建構子參數時，會擲出訊息寫明缺哪個服務的 `InvalidOperationException`。`CreateConfigurableService` 原本把它 catch 後丟掉、改走無參數建構子；型別沒有無參數建構子時，最後浮出的是 `MissingMethodException: Constructor on type ... not found`——完全看不出是漏註冊。

catch 加上 exception filter：只在型別宣告了 public 無參數建構子時才退回，否則原始例外原封不動往上拋；退回本身失敗時，原始例外掛為 `InnerException`。只有無參數建構子的舊實作行為不變——那種情況下 `ActivatorUtilities` 本來就會自行選用它。

### `apps/Bee.Northwind`：`OrderBO` 對齊框架的 `isLocalCall` 預設值

4.28.0 把 `BusinessObject` 與 `FormBusinessObject` 的 `isLocalCall` 預設值由 `true` 改為 `false`：直接建構 BO 是唯一繞過 `ApiAccessValidator` 的路徑，預設信任等於把四道第二線防護開在最不該信任的那條路上。`OrderBO` 自帶 `= true`，因此**沿用了被刻意改掉的舊行為**——而且編譯不會有任何訊號，它只是一個獨立宣告的預設值。

案例本身的曝險有限（唯一的建構路徑會顯式傳值），但 `apps/Bee.Northwind` 是寫給人抄的範本，範本帶著已被否決的預設值，擴散得比框架本身更遠。

### `apps/Bee.Northwind`：訂單金額以兩位小數顯示

訂單表單原本把 `amount` 顯示為 `252`、`total_amount` 顯示為 `352`。兩份 `Order.FormLayout.xml`（`Define/` 與 `Customize/northwind-demo/`）都是手寫的，沒有 `NumberKind`。框架只有在**產生** layout 時才從 `FormField` 帶入 `NumberKind`，手寫 layout 在執行期不會被補上，於是編輯器把兩個欄位都當成 `NumberKind.None`。

| 欄位 | 補上的屬性 | 為何這樣就夠 |
|------|-----------|-------------|
| 明細 `amount`（`LayoutColumn`） | `NumberKind="Amount"` | grid 的儲存格文字一律經數值格式化處理，不看 `ControlType`；幣別分支由幣別主檔與公司本幣解析 |
| 表頭 `total_amount`（`LayoutField`） | `NumberKind="Amount"`、`ControlType="NumericEdit"` | `LayoutField.ControlType` 預設為 `TextEdit`，只有 `NumericEdit` 會套數值格式 |

兩份都要改，因為客製 layout 是整份取代套裝 layout，不會合併。

刻意留著、仍未格式化的：`unit_price`（公司來源的種類在 grid 只讀 bake 過的 `NumberFormat`，手寫 layout 沒有，單補 `NumberKind` 不會有任何變化），以及清單的 Total Amount 欄（清單 layout 由 schema 產生，而 schema 的 `total_amount` 沒有宣告 `NumberKind`）。讓框架在執行期依 schema 補齊手寫 layout 可以一併解決兩者，但不在本版範圍內。

## 變更

### `apps/Bee.Northwind`：示範公司設定本幣

示範公司的 `default_currency` 為 `USD`（`NorthwindCredentials.DefaultCurrency`），並部署複製自框架 scaffold 預設值的 `Define/CurrencySettings.xml`。沒有幣別主檔時，解析器根本不會去看公司本幣，案例就只能展示一個「必填但沒有作用」的值。

訂單的 `amount` 沒有綁幣別欄，所以它的兩位小數現在走的是框架設計的那條路：公司本幣 `USD` → 幣別主檔 → `0.01`。本版之前同樣是兩位，但來自框架預設，本幣完全沒有參與。

既有的 `northwind.db` 會在啟動時回填，不需要刪檔重建。

### `tools/Bee.LoadTests`：SonarCloud 的 S2077 與 S1075

這兩類自工具建立以來一直沒被報出來，因為 Sonar analyzer 只在完整模式的 CI 執行。

- **S2077**——`SchemaPreparer.CreateDatabaseIfMissing` 內插的四處字串分屬兩類。PostgreSQL 的存在性查詢查的是**值**，改為參數化。三處 `CREATE DATABASE` 內插的是**識別碼**，任何引擎都不接受以 bind 參數傳入；改由 `GuardDatabaseName` 在內插處就地驗證，並加上長度上限 63（PostgreSQL 的上限，三家中最短）。
- **S1075**——`serve` 的監聽位址自 `Program.Serve` 移入 `TargetOptions.ServeUrl`，預設埠改為具名常數；`--help` 改指向該設定鍵，不再複寫預設值。

non-shipping tool（`IsPackable=false`）。

## 升級指引

經 `AddBeeFramework` 建構工廠的部署不需要改程式碼。兩種情形要檢查。

**每家公司都要有本幣。** 沒有本幣的公司，升級後存檔含計算金額的單據——以及 client 的即時計算——會擲例外。請在升級前補上，幣別依各公司實際情況填寫，框架不代為選擇：

```sql
UPDATE st_company SET default_currency = 'USD'
 WHERE default_currency = '' OR default_currency IS NULL;
```

`IS NULL` 那半是給 Oracle 的——它把空字串存成 `NULL`。

**直接建構 `RepositoryFactory` 的程式碼**改傳一個 resolver，取代原本的兩個客製相依：

```csharp
- new RepositoryFactory(services, defineAccess, dbAccessFactory, connectionManager, router,
-     cacheNotify, customizeReader, sessionInfoService);
+ new RepositoryFactory(services, defineAccess, dbAccessFactory, connectionManager, router,
+     new ProgramSettingsRepositoryTypeResolver(defineAccess, customizeReader, sessionInfoService),
+     cacheNotify);
```

部署有用到租戶客製時，`customizeReader` 與 `sessionInfoService` 兩個都要傳：它們在 resolver 上是選用參數，漏傳會讓租戶的 Repository 覆寫關閉而不報錯。覆寫過 `ResolveFormRepositoryType` 的子類，改為實作 `IRepositoryTypeResolver`。
