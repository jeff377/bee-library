# Bee.NET 4.19.0 — Detailed Release Notes

[English](4.19.0.md) ・ [繁體中文](4.19.0.zh-TW.md) ・ [← CHANGELOG](../../CHANGELOG.md)

This document is the detailed version of the `[4.19.0]` entry in [CHANGELOG.md](../../CHANGELOG.md). The main CHANGELOG lists one line per change; this file keeps the full narrative — the *why*, the constraints, and the design context behind each change.

> This release decouples the definition layer from the transport format. Before it, `Bee.Definition` carried a `MessagePack` package reference and 37 source files annotated with `[MessagePackObject]`, `[Key]`, `[Union]` and `[IgnoreMember]`. None of its consumers — `Bee.Db` and its five provider command builders, `Bee.Repository`, `Bee.Business`, `Bee.UI.Avalonia`, `Bee.Cli`, `DefineEditor` — needed MessagePack, yet all of them inherited it through the dependency chain. The deeper problem was that the definition types were welded to one transport technology: changing formats later would have meant editing the definitions themselves.
>
> The dividing line drawn here is not "is it a transport format" but **"does it cost the definition layer an external package"**. `[XmlIgnore]` and `[JsonIgnore]` are platform vocabulary and carry no dependency, so XML and JSON stay. MessagePack is a technology choice that propagates down the chain, so it moves out. See [ADR-036](../adr/adr-036-wire-serialization-externalized.md).

## Breaking changes

### The wire format changes for two type families

Most types are unaffected: `[MessagePackObject(keyAsPropertyName: true)]` and the contractless resolver both key on the property name, so removing the attribute produces byte-identical output. Two families are not in that group.

- **`FilterNode` / `FilterCondition` / `FilterGroup`** move from MessagePack's `[Union]` encoding — a two-element array of `[typeCode, integer-keyed map]` — to a map carrying a named `Kind` discriminator alongside named members. The discriminator is written as a member rather than a leading array element so the payload stays self-describing: a reader that logs the map sees `Kind` named, not a bare integer whose meaning lives in another file. This also brings MessagePack in line with the JSON wire, where `FilterNodeCollectionJsonConverter` has always read `Kind` to choose the concrete type.

- **`ParameterCollection`** moves from a single-key map (`{0: [items]}`, produced by the `[Key(0)] ItemsForSerialization` proxy property) to a plain array of items. The proxy existed only because a MessagePack `[Key]` attribute has to sit on a property; with the binding written out in a formatter, neither the property nor the attribute is needed.

**`ParameterCollection` rides on `ApiMessageBase.Parameters`, which means every request and every response carries it.** A 4.18 client therefore cannot talk to a 4.19 server, or the reverse. Deploy both sides together.

### Removed public API

- **`Bee.Definition.Collections.MessagePackCollectionBase<T>` / `MessagePackCollectionItem` / `MessagePackKeyCollectionBase<T>` / `MessagePackKeyCollectionItem`.** These four were deliberate copies of the `Bee.Base.Collections` types, and the reason was documented in their own remarks: `Bee.Base` takes no external package references, so it could not carry the MessagePack attributes these needed. With the attributes gone, so is the reason — the four collapse back into the originals. Replace the base type and the `using`; nothing else changes.

  The copies came with a maintenance tax that the remarks tried to hold at bay ("Keep the two in step — the divergence is meant to be the attributes, nothing else"). That requirement had already been broken: `Bee.Base.KeyCollectionBase.GetOrDefault` never had a counterpart on the MessagePack side.

- **`Bee.Definition.Serialization.SafeTypelessFormatter`.** `Parameter.Value` is typed `object?` — deliberate flexibility, so a caller can pass extra parameters through `ExecFunc` — which means the payload has to carry a type name and the reader has to instantiate from it. That is the classic deserialization-gadget path, and this formatter is the allow-list that closes it. It is a transport-side security boundary, so it now lives in `Bee.Api.Core` and is `internal`; nothing outside the transport plumbing should reach it.

- **`Bee.Base.IObjectSerializeProcess`, `SerializeFormat`, `SerializationLifecycle.NotifyAfterDeserialize`.** The interface had no production implementer; its only implementer was a test payload written to exercise it. Both of its historical uses — `SystemSettings`, then `DatabaseSettings` — had been deliberately migrated away, because letting a DTO touch process-wide static state during serialization is a pattern the framework had already decided against. Leaving the interface on the public surface was an invitation to repeat it. `SerializeFormat` existed only to feed its three method parameters.

### Retired analyzer rules

`BEE4001` (a collection must be registered with a formatter), `BEE4002` (a JSON rename disagreeing with the MessagePack key), `BEE4003` (a union hierarchy must keep integer `[Key]`) and `BEE4004` (constructor parameter order versus `[Key]` order) are removed. Each policed a property of the attribute mechanism, and the mechanism is gone: there is no `[MessagePackObject]`, no `[Key]`, no `[Union]` anywhere in the repository, and no registration list to forget an entry in.

`BEE4005` and `BEE4006` stay. What they guard — a single public `Add`, a public parameterless constructor — is a requirement of the reflection-only `XmlSerializer` path on the mobile heads, and has nothing to do with the transport format.

## Changed

### Wire binding: contractless plus hand-written formatters

Binding now lives in `src/Bee.Api.Core/MessagePack/`. Types with no framework-managed members to exclude need no formatter at all — the contractless resolver keys on the property name, which is what the attribute did. The nine formatters cover the cases where that is not enough:

| Formatter | Why it exists |
|-----------|---------------|
| `SortFieldFormatter`, `DepartmentNodeFormatter`, `NumberFormatItemFormatter`, `CashRoundingItemFormatter`, `AllowedCurrencyItemFormatter`, `ParameterFormatter` | Naming the wire members explicitly keeps framework-managed ones (`Tag`, and the collection back-reference that would otherwise recurse forever) off the wire |
| `FilterNodeFormatter` | Polymorphism, via the `Kind` discriminator |
| `KeyCollectionBaseFormatter` | The contractless resolver binds a `KeyedCollection<TKey, TItem>` as a dictionary and returns `Dictionary<object, object>` in place of the item type |
| `CollectionBaseFormatter`, `DataSetFormatter`, `DataTableFormatter` | Pre-existing |

**Why hand-written rather than reflection-driven.** The first design was a single generic formatter that read a custom attribute to decide which members to include. It does not work on the mobile heads: recursing into an arbitrary property type can only go through the non-generic `MessagePackSerializer.Serialize(Type, ref MessagePackWriter, object, options)`, and because `MessagePackWriter` is a `ref struct`, that overload needs `Reflection.Emit` to build a delegate that can pass it. With dynamic code unavailable it throws `NotSupportedException`. Naming every member at compile time keeps the whole path generic, so device and desktop run the same code.

The cost is that adding a property to one of these types means updating its formatter, and nothing in the compiler ties the two together. Each formatter therefore publishes a `WireMemberCount` constant that the wire tests assert against the map header, so the two shapes cannot drift apart silently.

### Package references

`Bee.Definition` and `Bee.Api.Contracts` no longer reference `MessagePack`. The only remaining reference in the repository is `Bee.Api.Core`.

### BEE4006 keeps its coverage of item types

Its predicate used to be "carries `[MessagePackObject]` **or** is a framework collection". With the attributes gone the first branch is dead — but item types were covered by exactly that branch, and the reflection-only `XmlSerializer` genuinely needs them to have a parameterless constructor. `FrameworkCollectionTypes.IsFrameworkCollectionItem` now makes that coverage explicit rather than incidental.

## Upgrade

### Collection base types

```diff
- using Bee.Definition.Collections;
+ using Bee.Base.Collections;

- public class MyItems : MessagePackCollectionBase<MyItem> { }
+ public class MyItems : CollectionBase<MyItem> { }

- public class MyItem : MessagePackCollectionItem { }
+ public class MyItem : CollectionItem { }
```

The `Bee.Base` types are the same shape — plus `KeyCollectionBase<T>.GetOrDefault`, which the MessagePack copies never had.

### Deployment

Server and clients must be upgraded together. See the wire note above.

### Defining a new wire type

If it has no framework-managed members to exclude, do nothing — the contractless resolver handles it. If it does, write a formatter in `Bee.Api.Core/MessagePack/`, register it in `MessagePackCodec`, publish a `WireMemberCount` constant and assert it in a wire test.

## Known limitation

Simulating the mobile AOT path (`IsDynamicCodeSupported=false`) leaves failures in `Bee.Api.Core.UnitTests`, concentrated in `TypelessFormatter`, `DataTable` and `DataSet`. They predate this release — the baseline before these changes was 51 of 694 — and the hand-written formatters reduce but do not eliminate them.

This sits uneasily beside the existing conclusion that MessagePack works under mobile AOT, and is worth investigating separately. Two caveats on reading it: the simulation runs on a JIT runtime and real device behaviour may differ, and some failures throw `InvalidProgramException` rather than a clean `NotSupportedException` — the signature of *Emit ran and produced invalid IL*, which is plausibly an artefact of the simulation itself rather than a real defect.

### Postscript (2026-08-11)

**The caveat above was wrong, and 4.20.0 corrects it.** Those failures were a real defect, not a simulation artefact: they reproduce on NativeAOT and on a real Mono runtime, and `DynamicCodeSupport=false` is what the .NET for iOS SDK sets for *every* iOS, tvOS and MacCatalyst build. The exception *type* differs by runtime — that part of the caveat holds — but the pass/fail boundary does not, and reading a real failure as an artefact of the measurement is what delayed the fix by a release. See [ADR-037](../adr/adr-037-wire-explicit-registration.md).

The instruction under **Defining a new wire type** is also superseded. There is no longer a `WireMemberCount` constant to publish: every wire type registers a contract in `Bee.Api.Core/MessagePack/WireContracts.*.cs`, and `WireContractDriftTests` walks the type closure to catch anything missing.
