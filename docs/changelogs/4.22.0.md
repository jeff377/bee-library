# Bee.NET 4.22.0 — Detailed Release Notes

[English](4.22.0.md) ・ [繁體中文](4.22.0.zh-TW.md) ・ [← CHANGELOG](../../CHANGELOG.md)

This document is the detailed version of the `[4.22.0]` entry in [CHANGELOG.md](../../CHANGELOG.md). The main CHANGELOG lists one line per change; this file keeps the full narrative — the *why*, the constraints, and the design context behind each change.

> This release is small and corrective, and two of its four items share a theme: **a mechanism that was in place, looked healthy, and did nothing.**
>
> The analyzers shipped their definition-file injection in `build/`, which NuGet imports only for a *direct* `PackageReference` — so a project reaching `Bee.Definition` transitively loaded the analyzer assemblies, found no files, and passed every rule silently. `BEE1004`, when it did fire, described a consequence that was only true for half the attributes it covers. Around those sit two breaking changes: the audit trail's change axis folds into the shared list contract it duplicated, and a declared business-object binding that will not resolve now throws instead of quietly degrading to generic CRUD.

## Breaking Changes

### The AuditLog change axis folds into the shared list contract

`IGetChangeLogResponse` and `ILogListResponse` had identical members — `Table` and `Paging`. That was a leftover from phased implementation: Phase 2a built the change axis when it was the only list and gave it a dedicated contract; Phase 2b added the login, access and anomaly axes the same day and extracted the shared `ILogListResponse`, but never went back to fold Phase 2a into it. A later namespace move carried the duplicate along unchanged.

Three types are removed and the change axis moves onto `LogListResult` / `LogListResponse`:

- `Bee.Api.Contracts.AuditLog.IGetChangeLogResponse`
- `Bee.Api.Core.Messages.AuditLog.GetChangeLogResponse`
- `Bee.Business.AuditLog.GetChangeLogResult`

Two signatures change with them — `LogBusinessObject.GetChangeLog` now returns `LogListResult`, and `LogApiConnector.GetChangeLogAsync` returns `Task<LogListResponse>`. Both are return-type widenings to the shared type, which is source- and binary-breaking for anything that declared the old type by name.

**The wire format does not change.** The two types have identical members and identical serialised shape, so an older client receives exactly the payload it did before. `ApiOutputConverter` follows the `XxxResult` → `XxxResponse` naming convention, so `LogListResult` → `LogListResponse` resolves with no extra registration; the removal also takes out one formatter registration in `WireContracts.AuditLog.cs` and one redundant branch each in `DateTimeWireGuard` and `PayloadZoneConverter`, both of which had the same body as the case beside them.

### A declared business-object binding that will not resolve now throws

`ProgramSettingsBoTypeResolver` treated an ordinary progId differently from every other axis: a binding naming a type that would not load fell back to `FormBusinessObject` and wrote an error to the log, while the repository and plugin axes both threw. Two axes with opposite failure policies had no justification behind them — it was phasing, not design.

The fallback bought only the appearance of a running system. `FormBusinessObject` accepts any progId in its constructor, so it always constructs; the failure then surfaces later as a missing method or as generic behaviour where custom logic was expected, and the diagnosis points at the API layer rather than at the registry. In a multi-tenant deployment a typo in a customization file failed silently — and customization is the main reason the registry exists at all.

The change covers exactly one path: **a name was declared, and that name does not resolve to a usable type.**

- The type will not load (`FileNotFoundException`, `FileLoadException`, `BadImageFormatException`, or `GetType` returning `null`) → `InvalidOperationException`
- The type does not derive from the expected base → `InvalidOperationException`

Every message carries the progId, the type name, and where the binding was declared (the package settings, or which customization file). Reserved progIds additionally constrain the base type through `ReservedProgIdBinding.ExpectedBaseType`; an ordinary progId only has to derive from `BusinessObject`.

**An absent entry is still not a failure.** A progId the registry does not mention, or one whose `BusinessObject` element is empty, resolves to the framework default as before — `FormBusinessObject` for an ordinary progId, and the framework's own type for a reserved one. Startup self-registration and incremental adoption are unaffected.

A failed resolution is not written to the type cache: `GetOrAdd`'s value factory does not store a result when it throws, so every call throws rather than the second one silently passing.

The public surface does not change — the `ILogger` constructor overload is kept, with the parameter now ignored — so this is **binary compatible and behaviourally breaking**. The decision and its revision are recorded in [ADR-034](../adr/adr-034-progid-type-registry.md).

## Fixed

### The analyzers loaded, found no files, and passed everything

`Bee.Definition.targets` injects the consuming project's definition files into `AdditionalFiles` so the `BEE1xxx` / `BEE2xxx` rules have something to read. It was packed into `build/`, and **NuGet imports a package's `build/` folder only for a direct `PackageReference`.**

Every project that reached `Bee.Definition` transitively — anything referencing only `Bee.Business`, `Bee.Db`, `Bee.Api.AspNetCore` or `Bee.Hosting` — therefore got the analyzer assemblies, which do flow transitively and load normally, with zero files to analyse. Every rule passed, and nothing in the build said so. The failure had no symptom at all; it surfaced only when an external repo consuming the 4.21.0 packages was measured and found to have zero `AdditionalFiles`.

The targets move to `buildTransitive/`. Measured locally with two package sets against a consumer referencing only `Bee.Business`: the baseline saw 0 files transitively and 3 directly; after the move, both paths see 3, all sourced from `buildTransitive/`. End to end, a `FormSchema` with an invalid `CategoryId` produced no diagnostic on the baseline and the correct `BEE1001` afterwards. Keeping the file in both folders was measured too — it does not double-import, since a direct consumer still selects only `buildTransitive/` — so `build/` is pure redundancy and only one copy is kept.

`BeeDefinitionFilesGlob` still defaults to the project directory as its root. Searching upwards would let a solution-root definition file be picked up once per referencing project, reporting the same diagnostics N times; for the same reason, "warn when the glob matches nothing" would fire on every project in a solution that legitimately has no definition files. Observability is added through two zero-noise mechanisms instead: a message at `normal` verbosity printing the glob and the match count, and an opt-in `BeeRequireDefinitionFiles` that raises `BEE9003`.

`BuildAssetPackagingGateTests` turns the folder location and `PackagePath` into an executable check, because this particular failure has no symptom to notice.

**Consumers need this release to benefit** — the packaging lives in the package.

### `BEE1004` described a consequence that was true for only half its attributes

`BEE1004` covers both `ListFields` and `LookupFields`, but its message — "Unknown entries are skipped silently" — held only for the latter. `FormSchema.GetLookupFields` filters through `master.Fields.Contains`, so an unknown lookup entry really does vanish quietly.

`ListFields` is silent only on the layout half, where `ListLayoutGenerator` applies the same `.Where(master.Fields.Contains)`. The query half is not filtered: `ListView.ComputeSelectFields` splits the original string and sends it through, `DataFormRepository.GetList` falls back to `_schema.ListFields` when `selectFields` is empty, and `SelectBuilder.Build` throws `InvalidOperationException` on an unknown column. A developer reading the old message would have expected a missing column and got a runtime failure.

`s_listAttributes` becomes `(Name, Consequence)` pairs and the message format opens a `{3}` slot for the consequence clause; the descriptor's description now states both outcomes. The tests assert the two branches separately so the message cannot drift back to a single wording.

Diagnostic text only — no public API change.

### XML doc drift across the repo

A full audit of `src/**/*.cs` doc comments (26,263 lines across 991 files) found ten substantive errors, eight of which were inventory counts that had drifted. `IFormCommandBuilder` and its five provider implementations claimed to produce Select/Insert/Update/Delete when only `BuildSelect`, `BuildCount` and `BuildDelete` remain — and all six summaries omitted Count. `CustomizeDefineReader` and `CustomizeOnlyStorage.GetChangeSource` said "four customizable types" against an actual five. `CacheInfo.Initialize` pointed at a `CacheBootstrapper` that no longer exists. `RepositoryBase` said "nine framework repositories" against a mapping table of eleven.

These ship in the `.xml` alongside each package and appear directly in consumer IntelliSense, which is why they are listed here rather than treated as internal documentation.

`<see cref>` was already guarded — a dangling one is `CS1574`, which fails the build under `TreatWarningsAsErrors` — but prose `<c>` references are not. `check-xmldoc-refs.sh` closes that gap. The counting problem itself is not something an analyzer can judge, so the editing rule changed instead: doc comments list names rather than counts, since a wrong name is visible to a reader and a wrong number is not.

Doc comments only — no signatures touched, no `PublicAPI.*.txt` movement.

## Added

- `Bee.Definition`: `SystemActions.CheckPackageUpdate` and `SystemActions.GetPackage`. The new `ActionSurfaceTests` gate found both on its first run — `SystemBusinessObject.CheckPackageUpdate` and `GetPackage` were anonymous-callable API surface with no action constant, so callers had to use magic strings. Purely additive.

## Internal

`ActionSurfaceTests` verifies the JSON-RPC action surface in both directions against the `*Actions` constant classes as the single source of truth. The existing pairing tests check whether a type has its contract interface, but a JSON-RPC method is a *string* — `JsonRpcExecutor` takes the action and calls `GetType().GetMethod(action)`. A typo in a constant left both pairing tests green and surfaced as a runtime `MissingMethodException`; a missing constant left callers with nothing but a literal. The new gate asserts that every constant has a matching public method taking a single `BusinessArgs` and returning a `BusinessResult` under `[ApiAccessControl]`, and that every such method has a constant.

## Upgrade

Mechanical substitutions:

```diff
- Bee.Api.Contracts.AuditLog.IGetChangeLogResponse
+ Bee.Api.Contracts.AuditLog.ILogListResponse

- Bee.Api.Core.Messages.AuditLog.GetChangeLogResponse
+ Bee.Api.Core.Messages.AuditLog.LogListResponse

- Bee.Business.AuditLog.GetChangeLogResult
+ Bee.Business.AuditLog.LogListResult
```

Requires a check rather than a substitution:

- **Verify every `BusinessObject` type name in `ProgramSettings.xml`, including each tenant's customization file, actually resolves.** A binding that named a type which would not load previously degraded to generic CRUD and logged an error; it now throws on every request for that progId. A deployment that has been running on a silent fallback will fail visibly after upgrading — which is the point, but it is better found before the upgrade than after.

No coordinated deployment is required for the AuditLog change: both types serialise identically, so an older client and a newer server interoperate unchanged.
