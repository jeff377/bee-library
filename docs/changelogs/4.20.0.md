# Bee.NET 4.20.0 — Detailed Release Notes

[English](4.20.0.md) ・ [繁體中文](4.20.0.zh-TW.md) ・ [← CHANGELOG](../../CHANGELOG.md)

This document is the detailed version of the `[4.20.0]` entry in [CHANGELOG.md](../../CHANGELOG.md). The main CHANGELOG lists one line per change; this file keeps the full narrative — the *why*, the constraints, and the design context behind each change.

> Three threads run through this release. A deserialization hole in the wire's type whitelist is closed. `object` values on the wire stop naming their own type and move to a discriminated envelope, which is what makes them work on a runtime with no dynamic code. And the expression abstraction sinks into `Bee.Base`, so a consumer that only reads definitions no longer inherits an expression engine.
>
> The first is a security fix; the other two are the completion of a boundary the previous release started drawing. All three touch things a caller can observe: two change the wire, one changes a namespace, and a fourth change — framework login gaining a working default — changes behaviour for deployments that never overrode it.

## Security

### The type whitelist screened the outer type and nothing else

`ApiPayload.TypeName` lets a caller name the type its payload should be deserialized into. That is the classic deserialization-gadget shape, and the framework's answer has always been a whitelist: a type is accepted only if it sits in one of the allowed namespaces.

The whitelist was applied to the text before the first comma of the assembly-qualified name, on the reasoning that the comma separates the type from its assembly. For a generic type it does not. The assembly-qualified name of a constructed generic embeds each argument's own assembly-qualified name in brackets, and **the argument's comma comes first**:

```
Bee.Base.Collections.Dictionary`1[[Disallowed.Type, Other.Assembly]], Bee.Base
                                                  ↑
                                    the first comma is here
```

Splitting there yields `` Bee.Base.Collections.Dictionary`1[[Disallowed.Type ``, which still starts with `Bee.Base.` and so passes. The argument was never screened, and `Type.GetType` then resolved the whole name — assembly and all.

Three things made this worse than a narrow parsing bug:

- **It was reachable without authentication.** `System.Login` is `[ApiAccessControl(Public, Anonymous)]` and sits in the no-authorization set. Access validation deliberately runs before decryption, but its subject is the *method*, not the payload's type name; payload restoration happens immediately after and is what consumes `TypeName`.
- **The failure direction was open.** A name the parser could not make sense of produced a fragment that happened to pass, rather than a rejection.
- **The same shape existed twice.** `WireValueFormatter`, written for this release cycle, reproduced the split verbatim when it took over the escape hatch from `SafeTypelessFormatter`. New code copied the defect from old code.

The fix replaces the split with a bracket-aware parser that collects **every** type named — the outer type, each generic argument, recursively, and array element types — and requires all of them to pass. A name it cannot parse is refused. It also caps nesting depth and name length, so a crafted name cannot drive unbounded work. The already-resolved-`Type` check in `SafeMessagePackSerializerOptions` gets the matching treatment: it walks the type's shape instead of testing one `FullName` string, because a constructed generic's `FullName` embeds its arguments and testing that single string screens only the outer type. The writer side of the escape hatch was checking `FullName` too, and now uses the same shape walk — the two ends of a security boundary should not disagree about what they are checking.

Present since 4.0.2 (2026-04-12). No exploitation is known; the whitelist means the reachable set was bounded by what is deployable on the server's probing path.

**This is a stopgap, and deliberately labelled as one.** The whitelist's real weakness is not the parser but its unit: it lists *namespaces*, so the accepted set is every public type in five namespaces — a number nobody maintains, which grows whenever anyone adds a type. Meanwhile the set of types that legitimately cross the wire is now known exactly, because [ADR-037](../adr/adr-037-wire-explicit-registration.md) requires each one to be registered. The durable fix is to resolve `TypeName` against that registration table and drop `Type.GetType(arbitrary string)` altogether, at which point string parsing stops being a security boundary. That is a wire-level design change and is being treated separately.

### The lockout tracker was an unauthenticated memory lever

`LoginAttemptTracker` keys its map by whatever user id the caller supplied, and `System.Login` is anonymous. Every entry is therefore attacker-chosen. Removal happened in two places only: a successful login for that user, and an expired lockout observed on a later call naming the same user. **An entry below the lockout threshold had no expiry at all**, and nothing swept the map — so a stream of distinct random user ids grew it without limit, at roughly a hundred bytes per request, and none of the removal paths could ever fire because the attacker never repeats an id.

Three changes: entries carry their own expiry and are swept on a schedule rather than only when re-named; the failure count is windowed, so typos months apart no longer accumulate into a lockout; and the number of tracked accounts is capped.

The cap deliberately applies to **new** accounts only. Evicting an existing entry to make room would hand back the same lever in a worse form — flood the map with unknown ids and the account you actually want loses its lockout state. Dropping new entries under flood degrades lockout tracking for accounts not yet seen, which is the lesser of the two.

This was introduced, in effect, by 4.18.0: the tracker had existed since earlier but was never registered, so `RecordFailure` never ran. Registering it by default turned an unused class into a live one.

### Losing the API key gate is now visible

With no enabled key, the gate accepts any non-empty `X-Api-Key`. That fallback is deliberate — it is what lets a deployment upgrade before it has issued its first key. But **the same state is reached by disabling the last enabled key**, which is an ordinary step in rotation, and the only signal was a warning logged by `UseBeeFramework` at startup. A downgrade that happened at run time produced nothing at all: no log, no audit, no change in behaviour an operator could observe.

Disabling the last enabled key now logs an error naming the key. The startup check also reports at error rather than warning level outside Development, because the distinction it draws — having an API key gate versus not having one — is not what a warning is for.

**Startup is deliberately not failed.** The earlier review proposed exactly that for non-Development environments, and it would break every deployment that has not yet issued a key — the population the fallback exists to serve. Making that a hard failure belongs in a major release with an opt-out, not in a minor one.

## Breaking changes

### `object` values on the wire move to a discriminated envelope

A handful of wire members are typed `object?` — `Parameter.Value`, `FilterCondition.Value` and `SecondValue`, `SerializableDataColumn.DefaultValue`, and the cell values inside `SerializableDataRow`. Previously each such value carried its own assembly-qualified type name and was dispatched through MessagePack's typeless machinery. That machinery needs `Reflection.Emit`, and .NET for iOS turns dynamic code off for every build — so on the mobile heads these values did not merely run slowly, they threw.

They now ride a two-element envelope: an integer discriminant plus the value, written and read through closed generic delegates chosen by array index. The framework's own value types are all in the closed set. A named-type escape hatch remains for host-supplied types, and it is the only part that still needs dynamic code.

Two consequences worth stating plainly:

- **The wire format changes, and these members ride on every request and response.** A 4.19 client cannot talk to a 4.20 server or the reverse. Deploy both sides together.
- **The payload gets smaller and the path gets faster.** Each value previously wrote a full assembly-qualified type name — roughly 50 to 100 bytes — and resolved a formatter through a non-generic reflection call. It now writes one byte of discriminant and takes an array index. For a wide table this is measured in megabytes, not bytes.

See [ADR-037](../adr/adr-037-wire-explicit-registration.md) for the registration model this sits inside.

### The expression abstraction moves to `Bee.Base`

`Bee.Definition` referenced `Bee.Expressions`, which references `DynamicExpresso.Core`. The definition layer therefore handed that package to every consumer down the chain — including `Bee.Cli` and `DefineEditor`, which only read and write definition files and have no use for an expression engine.

The abstraction and the implementation now live apart. `IExpressionEvaluator`, `ExpressionPolicy` and `ExpressionEvaluationException` move to `Bee.Base.Expressions`, whose public surface uses nothing but BCL types and one framework enum. `Bee.Expressions` keeps `DynamicExpressoEvaluator` and the package reference, and a composition root — `Bee.Hosting`, or a UI head — decides which implementation is used.

**There is no type forward.** `using Bee.Expressions;` against the moved types is a compile error, which is the intended outcome: a silent redirect would leave the old namespace looking alive. Change the `using` and nothing else moves.

Three constructors take the evaluator and therefore change signature: `FormExpressionCalculator`, `FormRuleProcessor` and `FormLiveComputation`. The first two take it as a required parameter, so a caller notices at compile time. **`FormLiveComputation`'s is optional**, which is the case that needs saying out loud: source that omits the argument still compiles against the new assembly, but an assembly compiled against 4.19 throws `MissingMethodException` at runtime. Rebuild anything that constructs it.

See [ADR-038](../adr/adr-038-definition-dependency-boundary.md) for the judgement rule this applies, and for the two build-time gates that now hold the boundary.

### Framework login has a working default

`SystemBusinessObject.AuthenticateUser` is the extension point a host overrides to authenticate. Its default implementation returned `false` unconditionally — a placeholder, since the framework had no credential store of its own to check against.

It now verifies against `st_user` through the new `IUserRepository.VerifyPassword`. The hash never leaves the repository: returning it so the caller could compare would put a credential into a caller-side variable, which is one more place it can reach a log or an exception message. An unknown user and a wrong password both return `false`, deliberately — a caller that could tell them apart would be an account enumeration oracle.

**The behaviour change is one-directional.** A deployment that overrides `AuthenticateUser` is unaffected. A deployment that does not had no working login at all, and now accepts accounts present in `st_user`. That is a widening, so it is listed as breaking even though nothing that previously worked stops working. If you were relying on the default to refuse every login, override it.

`IUserRepository` gains a member, which is source-breaking for anyone implementing the interface outside the framework.

## Added

### Two build-time gates

**BEE9001** locks `Bee.Base` and `Bee.Definition` to an explicit dependency allowlist. Anything added to those two is inherited by every consumer of the framework, so widening the list is allowed but has to be a decision someone made on purpose. It is complemented by a test that walks `Bee.Definition`'s full transitive closure — the two are not duplicates: the target catches a direct edge as it is written, the test catches a package arriving indirectly through a project reference, which is exactly how `DynamicExpresso.Core` got in.

**BEE9002** requires `Version`, `AssemblyVersion` and `FileVersion` to stay in step. See the version fix below for why this exists rather than a note in a checklist.

Both are documented in [Analyzer rules](../analyzer-rules.md).

## Fixed

### `LanguageEnum.Entries` broke definition loading on iOS

`Entries` was a get-only collection property mapped to repeated `[XmlElement]`. On the desktop that is fine. On the reflection-only `XmlSerializer` path — which is what iOS uses, because dynamic code is off — a member mapped that way is **assigned**, not added to, so a missing setter throws `ArgumentException: Property set method not found`. That surfaces as `There is an error in XML document (line, position)`, which points at the XML and not at the type.

The setter clears the existing collection and refills it rather than replacing the field, so the owner back-reference survives. A repository-wide scan found this to be the only property of its shape.

`[XmlArray]`-mapped get-only collections are not affected — the difference is in how the member is mapped, not in the collection.

### `st_user.password` could not hold a password hash

The column was 40 characters. `PasswordHasher` produces 79. SQLite does not enforce length; the other four providers truncate, and a truncated hash can never verify. Nothing in the framework wrote a hash to `st_user` before this release, which is why a defect this direct went unnoticed.

### Assembly identity had drifted from package version again

4.17.0 shipped assemblies stamped `4.16.0.0`. That was corrected by hand in 4.18.0 — and then 4.19.0 shipped assemblies stamped `4.18.0.0`.

**And a third copy had been drifting the whole time.** `tools/Bee.Cli` is published to NuGet but does not inherit from `src/`, so it carried its own three properties with a comment saying to bump them alongside the framework. They stayed at 4.8.0 for twelve minor versions; every published `Bee.Cli` since 4.9.0 contains an assembly stamped `4.8.0.0`.

A per-project gate cannot catch that last one — BEE9002 checks the three properties agree *with each other*, and 4.8.0 / 4.8.0.0 / 4.8.0.0 agrees with itself perfectly. So the version now lives in a single `Version.props` at the repository root, imported by both trees. The gate handles a project disagreeing with itself; the single source removes the possibility of two projects disagreeing.

Twice is a mechanism problem, not an attention problem. Both times the number was corrected and nothing was added to catch the next occurrence, and both times the next occurrence was found by a person reading the file. BEE9002 now fails the build when the three properties disagree, at the moment the edit is made.

**The published 4.19.0 packages are not being re-published.** Their assemblies claim `4.18.0.0` and cannot be distinguished from 4.18.0 by assembly identity. If you have tooling that keys off `AssemblyVersion` rather than package version, that is the version pair to be aware of.

## Changed

`Bee.Definition`'s package no longer lists `Bee.Expressions`, and therefore no longer pulls in `DynamicExpresso.Core`. For a consumer that only reads definitions this removes an expression engine from the dependency graph.

`samples/Avalonia.Demo` is removed. The Avalonia end-to-end example is `apps/Bee.Northwind`, which covers the same ground with three database scopes and a real login.

## Upgrade

```diff
- using Bee.Expressions;
+ using Bee.Base.Expressions;
```

- **Deploy server and clients together.** The `object` envelope change affects every request and response.
- **Rebuild anything that constructs `FormLiveComputation`**, including callers that do not pass an evaluator.
- **If you implement `IUserRepository`**, add `VerifyPassword`.
- **If you rely on `AuthenticateUser` refusing every login**, override it — the default now checks `st_user`.
