# Bee.NET 4.17.0 — 詳細發行說明

[English](4.17.0.md) ・ [繁體中文](4.17.0.zh-TW.md) ・ [← CHANGELOG](../../CHANGELOG.zh-TW.md)

本檔是 [CHANGELOG.zh-TW.md](../../CHANGELOG.zh-TW.md) 中 `[4.17.0]` 條目的詳細版。主 CHANGELOG 每條只列一行重點，本檔保留完整敘事——每項變更的 *why*、限制與設計脈絡。

> 本版的主線是**業務邏輯 plugin**：在套裝 BO 的既有流程上掛載客製程式碼——不換掉整個 BO 類別，只在特定時點追加一段。這是客製化的第五種機制，補上了「輕量擴充」這一格：先前要為單一租戶加一段存檔前檢查，唯一手段是繼承整個 BO 覆寫它，粒度過重。plugin 同時帶來客製層的**第一條寫入路徑**——`PluginSettings` 是唯一有維護 API 的客製定義，其餘客製層維持全面唯讀。
>
> 另有兩項客製化行為修正：`ProgramItem` 的覆寫語意由「整筆取代」改為**屬性級繼承**，以及 BO 型別解析失敗由靜默降級改為**降級並記錄**。兩者都是 `ProgramItem` 新增 `Repository` 綁定（4.16.0）之後才浮現的問題。

## 新增

### 業務邏輯 plugin

- **`PluginSettings` 是新的定義型別（`DefineType` 第 13 個成員）。** 它承載「每個 progId 綁了哪些 plugin」，結構為 `PluginSettings` → `ProgramPluginItemCollection` → `ProgramPluginItem`（key 為 `ProgId`）→ `PluginItemCollection` → `PluginItem`（**key 為型別名**）。以型別名為 key 的用意是：同一個 program 重複宣告同一型別會在載入時就被拒絕，而不是靜默跑兩次。新成員加在列舉尾端，wire 值不重排。讀取管線完整落地——`PathOptions` 與 `CustomizeOnlyPathOptions` 的檔案路徑、三個 storage（File / CustomizeOnly / Db）、`PluginSettingsCache`、`ICacheContainer` 與 `CacheContainerService`、`CacheDefineAccess`、`CustomizeDefineReader`。

- **`FormBusinessPlugin` 與四個掛載點。** `BeforeSave` / `AfterSave` / `BeforeDelete` / `AfterDelete`，在各自 `Do*` 子方法的**最終實作之後**依序執行——最終實作可能是套裝 BO 的 base，也可能是客製 BO 的覆寫，因此**繼承與 plugin 兩種擴充手段可以疊著用**。基底提供四個虛擬空實作，plugin 只 override 需要的時點。

  掛載點刻意只有四個。草案原為每個 `Do*` 子方法一個（六個），砍掉 `DoSave` / `DoDelete` 兩個後置點的理由不是「想不到用途」，而是它們與 `After` 行為完全相同：都在交易外、都能改 `RefreshedDataSet`，稽核讀的是 `DoSave` 之前擷取的 diffgram、兩者皆不影響。留著只是逼使用者做一個沒有正確答案的選擇題。新增掛載點的判準是三關：與相鄰點可區分、有具體用途、不會把人引到危險位置——第三關會刷掉「有用途」的候選，例如 `DoSave` 前置落在稽核快照之後，改了資料會寫進 DB 卻不進稽核。成本不對稱也記在設計裡：掛載點是公開契約，**加是非破壞性的、減是破壞性的**，所以預設偏少、由真實需求推著擴充。

- **執行機制：`FormPluginChain` / `FormPluginRunner` / `IFormPluginResolver` / `PluginSettingsResolver`。** chain 以反射判定每個型別實作了哪些時點（比對 `MethodInfo.DeclaringType`），一份資料兩個用途——過濾無效呼叫，以及 `TypesForStage` 供維護工具顯示執行順序，中和「設定檔看不出誰在哪個時點跑」的可讀性代價。

  **實例生命週期為 per-operation**：Save / Delete 各建構一次，該次呼叫的所有時點共用同一實例，跨時點的狀態靠 instance field 傳遞。這正是「設定檔只列型別、時點由類別自己 override」這個宣告粒度的唯一實質優勢——若改成每個時點各建一次，就只剩「設定檔少打幾行」，不值得為此放棄「設定檔明寫時點 × 型別」的可讀性。runner 延遲建構但一建就建整條鏈：per-operation 的保證是「後面的時點找到同一個物件」，只有把建構綁在操作而非時點上才成立。

  **解析失敗一律拋，與 BO 軸的靜默降級相反。** binding 指名的是「這個程式就是這個型別」，退回仍是能跑的程式；plugin 是作者刻意加上的，略過等於客製沒生效——靜默漏掉一段信用額度檢查比拒絕存檔更糟。

- **兩層相加，而非擇一。** `CustomizeOverlay.GetPluginTypes` 是客製覆蓋層裡唯一「相加」粒度的項目：套裝鏈在前、客製鏈在後。一個 binding 指名的是「這個程式就是這個型別」，客製要換就得取代；plugin 只是多一個步驟，兩層的 plugin 不衝突。**代價是客製無法停用套裝的 plugin**——沒有 tombstone 語法，要拿掉就得繼承 BO 覆寫該步驟。

### 客製層的第一條寫入路徑

- **`SystemBO.GetCustomizePluginSettings` / `SaveCustomizePluginSettings`（`LocalOnly`）。** 讓部署以框架自己的 API 維護租戶的 plugin 綁定，而不是手動擺檔案。兩個方法都是 `LocalOnly` + `IsLocalCall` 兩道防線（attribute 只擋 JSON-RPC 派發路徑，直接建構 BO 的呼叫端不會經過它）。讀取在沒有客製時回空字串，呼叫端從空白定義開始編輯，不必分辨「不存在」與「空」；寫入為整份取代，空 XML 等同清空，不需另一支 API。

  **寫入前逐一驗證**每個型別可載入、繼承 `FormBusinessPlugin`、且至少 override 一個時點，一筆不合格整份拒存。驗證放在這裡是重點——編輯的人當場知道打錯字，而不是幾週後某張單據存不了。什麼時點都沒 override 的 plugin 掛了等於沒掛，屬設定錯誤，儲存時就擋。變更寫入部署層稽核。

- **`ICustomizeDefineWriter` 與 `CustomizeDefineWriter`。** 只有一個寫入方法，客製層其餘維持唯讀。檔案模式寫完即 evict 該租戶的 cache slot——維護工具會馬上讀回自己剛存的東西，file watcher 的「最終會到」不是這裡該有的契約。`CustomizeOnlyStorage` 維持全面唯讀，寫入改由 writer 直接經 `CustomizeOnlyPathOptions` 落檔：兩者共用同一份路徑來源，那個類別的唯讀承諾不必為單一例外破功。

- wire 兩個方向都走 **XML 字串**，不送 `PluginSettings` 物件。`Items` / `Plugins` 是 get-only 巢狀集合，正是 layout 客製決策踩過「送到 .NET 用戶端靜默收不回來」的同一形狀。

### 文件

- **新增[租戶客製化指引](../customization.zh-TW.md)（雙語）。** 五種客製全部做完後，材料卻散在三處（架構總覽有概念、定義檔全景有覆蓋層機制、開發指引有 BO / Repository / plugin 的 how-to），且有三個實際缺口：語系與 Layout 客製**沒有任何 how-to**（而那正是最常見的需求）、沒有「我想改 X → 用 Y」的對照表、`docs/README` 索引裡完全沒有客製化條目。新文件以填缺口與當入口為主：決策表（並點明「能用輕的就別用重的」）、語系 how-to（namespace 即 ProgId、三種 sub-key、最小可用範例、enum 整組取代的例外）、Layout how-to（整檔取代、「完整擁有是雙向的」、它其實由用戶端的 `FormDefinitionLoader` 組裝）、不能客製什麼與為什麼、唯讀 vs 可寫。

- **`development-cookbook` 新增「業務 plugin」一節（雙語）。** 繼承 vs plugin 的選用準則、四個時點各自看得到什麼、per-operation 實例、綁定檔格式與兩層相加語意、`LocalOnly` 維護 API，以及「外部系統同步該寫在哪」的分工表——**plugin 在交易外，行程在 plugin 執行前掛掉就是資料已提交而同步沒發生且不留痕跡**；不能漏的同步要在交易內登記 outbox，plugin 只適合盡力而為或有對帳兜底的場景。

## 變更

### `ProgramItem` 改屬性級繼承

`ProgramItem` 自 4.16.0 加入 `Repository` 綁定後，「整筆取代」的覆寫語意變成陷阱：**客製只想換 BO 時若不重述 `Repository`，整張單據的資料存取會無聲掉回通用 `DataFormRepository`**——空字串是合法的「用框架預設」而非錯誤，所以這個損失不會有任何回報。反向（只寫 `Repository`）則 BO 掉回 `FormBusinessObject`。

`CustomizeOverlay.FindProgramItem` 改為合成回傳：兩層都宣告時 new 一個 `ProgramItem` 逐屬性取捨（客製非空取客製，否則取套裝），只有一層宣告時直接回該層實例。**合成必為新實例**——兩層都是 process-wide 快取，不可異動。「刻意退回框架通用」現以顯式指名型別表達，不是清空屬性。反射防護測試列舉 `ProgramItem` 所有 public 可寫字串屬性，日後加屬性沒同步進合成邏輯就會紅。[ADR-016](../adr/adr-016-multitenant-customization-overlay.md)

### BO 型別解析失敗改為降級 + 記錄

一般 progId 的 BO 型別載不到或不繼承 `BusinessObject` 時，維持降級到 `FormBusinessObject`（不中斷服務），但**記一筆 error**，訊息帶 progId、型別名，並標示由客製層或套裝層宣告——**多租戶下沒有這個就無從診斷**。logger 走新增的三參數建構子而非在既有建構子加預設參數：後者 source 相容但屬**二進位破壞性變更**。DI 以 `GetService` 注入，無 logging 的 host 照常運作。因 type cache，同一 `(customizeId, progId)` 只記一次。

### 其他

- **`DeleteContext.Snapshot` 的載入條件加入「該 progId 有 delete 時點的 plugin」。** 沒有這條，snapshot 的有無會取決於變更稽核開關——同一個同步 plugin 在一個部署正常、在另一個拿到 `null`，是最難查的那種差異。

- **`IDefineAccess` / `IDefineStorage` / `ICustomizeDefineReader` 新增 `PluginSettings` 相關成員。** 自行實作這些介面者需補上對應成員。`IDefineAccess` 刻意**不加** `GetPluginSettings(customizeId)` 多載——`ProgramSettings` 就沒有，疊加由消費端自己做；加一個「看起來會疊加、實際只回 base」的多載反而誤導。

- **`DbDefineStorage.Write` 新增 `customizeId` 參數。** 租戶列與 base 列只差 `customize_id`，兩層不會互相覆蓋。`define_type` 取自 `typeof(T).Name`，因此不需要 schema 變更。

- **`BusinessObject` 新增 `protected IBeeContext Context`。** plugin 建構子收整個 context，而 BO 原本只暴露拆開的個別服務。resolver 走 `Services.GetRequiredService<T>()` 延遲解析，不加進 `IBeeContext`（比照同檔的 `RuleProcessor`，避免動公開契約）。

- **BO 擴充點的交易邊界寫成明文契約（純文件、零行為變更）。** 現況早已是「只有 `Do*` 在資料庫交易中」——交易由 repository 在 `DoSave` / `DoDelete` 內部開啟並提交——但這件事只存在於實作裡。覆寫 `DoAfterSave` 的人不會知道自己在交易外、資料已提交；在 `DoBeforeSave` 做並發檢查的人不會知道那是個 **TOCTOU 空窗**。六個子方法各加 `<remarks>` 標明在不在交易中，`DoBefore*` 額外寫 TOCTOU 空窗與 `UserMessageException` 的中止方式，`DoAfter*` 寫「拋例外時資料已提交」與副作用進佇列的建議；public `Save` / `Delete` 加管線圖與「覆寫子方法而非本方法」的指引。`development-cookbook` 同節既有範例原本示範 override `SaveResult Save`——覆寫 public 方法會連 `AuthorizeSave` 與寫入 scope 檢查一起接手，與本契約牴觸，一併改為覆寫 `DoBeforeSave`。

- **`api-bo-contract-design` 命名表補 `XxxContext` 一列。** 框架有兩套參數慣例，但只有 `Args`/`Result` 寫在命名表裡。判別法：**跨層傳輸用 `Args`/`Result`，流程內共享狀態用 `Context`**。
