# Bee.NET 4.18.0 — 詳細發行說明

[English](4.18.0.md) ・ [繁體中文](4.18.0.zh-TW.md) ・ [← CHANGELOG](../../CHANGELOG.zh-TW.md)

本檔是 [CHANGELOG.zh-TW.md](../../CHANGELOG.zh-TW.md) 中 `[4.18.0]` 條目的詳細版。主 CHANGELOG 每條只列一行重點，本檔保留完整敘事——每項變更的 *why*、限制與設計脈絡。

> 本版是一次框架全面體檢的產出，不是功能週期。主線是 **`System.ExecFunc` 的派發面**：兩個維運操作只要持有有效 access token 的人都能觸達——`UpgradeTableSchema` 會在呼叫端指定的任一資料庫裡把表刪掉重建，`TestConnection` 會對呼叫端指定的任一 host:port 發出站連線。兩者現已限本機呼叫，且派發器對「未標註的 handler」的預設由*放行已認證*改為**拒絕**。新增的建置期 analyzer 讓造成這件事的漏標不可能再發生一次。
>
> 帳號鎖定也換了狀態：`ILoginAttemptTracker` 的完整實作一直躺在 repo 裡卻從未註冊，於是開箱即用的部署完全沒有鎖定。現在改為預設註冊。此外修正一項版號缺陷——已發布的 4.17.0 套件內組件標的是 `AssemblyVersion` 4.16.0.0，見[升級指引](#升級指引)。

## 破壞性變更

### ExecFunc 派發面

- **`IExecFuncHandler` 的方法未標 `[ExecFuncAccessControl]` 時改為拒絕，不再視同 `Authenticated`。** 下面兩個操作之所以能被觸達，就是這個舊預設造成的：派發器只在*required == Authenticated 且 current == Anonymous* 這個組合下拒絕，所以未標註的方法對任何已登入者一律放行。fail-closed 本來就是 BO 軸的 `ApiAccessValidator` 在做的事，不一致的是 ExecFunc 軸。form 與 system 兩個 handler 上的 `Hello` 已顯式標註，保持原行為而非跟著放寬。（`e2c89452`）

- **移除 `SystemActions.ExecFuncLocal`、`SystemApiConnector.ExecFuncLocalAsync` 與 `FormApiConnector.ExecFuncLocalAsync`。** 它們指向的 BO 方法已於 2025-10-03 刪除，而刪除它的是同一個引入 `ExecFuncAccessControlAttribute` 的 commit——local-only 語意當時就搬到 attribute 上，wire action 被留在原地。由於 `JsonRpcExecutor` 以 `Type.GetMethod(action)` 解析，這兩個 connector 方法十個月來每次呼叫都擲 `MissingMethodException`；該表面零測試覆蓋，因此無人察覺。4.16.0 建立公開 API 快照時把它原樣記為「已發布 API」——快照守得住*變更*，守不住本來就是錯的東西。（`50e9ec78`）

### 移除的公開 API

- **移除 `ISerializableClone` 與 `DatabaseSettings.CreateSerializableCopy()`。** 該介面文件宣稱的用途是「序列化管線會就地加密敏感欄位，故快取物件須先深複製」。**那條管線並不存在**：`DatabaseSettings` 從未實作 `IObjectSerializeProcess`，加密是 `CacheDefineAccess` 透過 `DatabaseSettingsCryptor` 顯式完成的。而 `DatabaseItem.Clone()` 原樣複製 `Password`、快取實例持有的又是解密後的明文，所以那次 clone 什麼也沒保護到。它唯一的實質作用是「不去翻共用實例的序列化旗標」，而這件事現在有更直接的達成方式，見[安全性](#安全性)。（`e0c072b5`、`d45b6b48`）

- **`DbParameterSpecCollection` 的兩個便利 `Add` 多載移為 `DbParameterSpecCollectionExtensions`。** 集合只能公開一個 public `Add`：XmlSerializer 的 reflection-only 路徑以單一 `Type.GetMethod("Add")` 解析 add 方法，多個 public 多載會擲 `AmbiguousMatchException`——這種失敗只在 iOS 等 AOT target 上出現，桌面永遠測不到。這是 repo 內僅存的一處違規，而它能存活是因為執行該規則的 analyzer 沒掛在 `Bee.Db` 上。寫成 `collection.Add(...)` 的呼叫端照樣編譯，破壞的是二進位相容而非原始碼相容。`DataRowVersion` 的 optional 參數拆成兩個明確多載，因為位移後兩個 `Add` 參數個數相同，而 RS0027 要求帶 optional 參數者必須是參數最多的多載。（`344839e7`）

## 安全性

- **`UpgradeTableSchema` 與 `TestConnection` 改為僅限本機呼叫。** 兩者都掛在 `System.ExecFunc` 下，而它是 `[ApiAccessControl(Public, Authenticated)]`，兩者都沒宣告存取控制 attribute。`UpgradeTableSchema` 會走到 `TableUpgradeOrchestrator`，在 `ALTER` 不可行時退回*建暫表 → `DROP TABLE` → 改名*，對象是請求指定的任一 `DatabaseId`。`TestConnection` 接受呼叫端送來的 `DatabaseItem`——它屬 `Bee.Definition.*`，因此通過 typeless 白名單、可完全由 wire 構造——並對它呼叫 `connection.Open()`；`ServerId` 留空時連線字串與 provider 完全來自呼叫端，等於把伺服器變成對外掃描器（回應時間差即可區分開放埠與關閉埠），`ServerId` 有值時 `{@DbName}` / `{@UserId}` / `{@Password}` 的代入是未逃逸的字串替換，可注入額外連線字串參數。兩者現在都要求 `LocalOnly`，與 `SaveDefine` 同列為行程內維運操作。（`e2c89452`）

- **帳號鎖定改為預設啟用。** `Login` 是唯一可匿名觸達的憑證驗證面，而三處鎖定邏輯在 tracker 為 null 時全部短路。`AddBeeFramework` 現以 `TryAdd` 註冊 `LoginAttemptTracker`（5 次 / 15 分鐘），故 host 自帶實作仍勝出。這對既有部署是行為變更，見[升級指引](#升級指引)。（`3ca48eff`）

- **`GetDefine(DefineType.DatabaseSettings)` 不再回傳明文密碼。** 原本回應建構自 process-wide 快取實例，而該實例持有的是解密後的密碼——因為 `GetDatabaseSettings()` 對它跑過 `DecryptInPlace`。BO 現在直接讀定義檔，那裡的密碼仍是 `enc:` 密文。這同時讓 `GetDefine` 符合它自己宣告的契約——serve the definition *as stored*——而且因為回傳的是新實例，被刪掉的那個 clone 名義上要保護的共用物件也就不存在了。改動做在 business object 而非 `CacheDefineAccess`：後者是框架通用的定義入口、有五個 default interface method 繞道它，而一個以「快取」為名的類別若對某個型別靜默繞過快取，對直接使用它的人是陷阱。此路徑沒有任何消費端需要明文——連線解析與 `DatabaseRepository.TestConnection` 都走 `GetDatabaseSettings()`，那是另一個抽象成員。（`e0c072b5`、`d45b6b48`）

## 新增

- **`ExecFuncAccessControlAttribute.LocalOnly`**，以及帶 `isLocalCall` 的 `InvokeExecFunc` 多載。舊多載保留並視同遠端呼叫，二進位相容不破。（`e2c89452`）

- **BEE3003（`ExecFuncAccessControlAnalyzer`）。** `IExecFuncHandler` 實作上的 public 方法必須宣告 `[ExecFuncAccessControl]`，漏標即建置失敗。BEE3001 涵蓋不到這裡——它掃的是 `BusinessObject` 子類的 public 方法，而 handler 不在那個階層裡，上述兩個操作漏掉的正是這個縫。文件見 [analyzer 規則](../analyzer-rules.zh-TW.md)。（`e2c89452`）

- **`DbParameterSpecCollectionExtensions`**——位移過來的 `Add` 多載，與集合本體同檔，讓「為何是擴充方法」的理由留在看得到的地方。（`344839e7`）

- **序列化 analyzer 擴及 `Bee.Api.Contracts` 與 `Bee.Db`。** BEE4002–4006 是 per-compilation 規則（只有 BEE4001 跨 assembly），因此在此之前它們對前者的 wire DTO 與後者的框架集合完全靜默——gate 存在但沒接滿。`Bee.Api.Contracts` 掃出來是乾淨的；`Bee.Db` 則現形了上述那兩個 `Add` 多載。（`344839e7`）

## 變更

- **`JsonCodec` 改為共用 `JsonSerializerOptions`，不再每次呼叫新建。** `JsonSerializerOptions` 是 System.Text.Json 的型別 metadata 快取容器；每次新建等於 contract 快取 100% miss，外加三個 converter 的配置，而這條路徑每請求走四次（兩端各一進一出）。現以六個 `static readonly` 實例涵蓋三種 ignore condition × 縮排與否。wire 路徑（`Serialize` / `Deserialize` / `ToJson`）同時改為 compact——縮排本來就只屬於 `SerializeToFile`，它寫的是給人閱讀的定義檔。隔壁的 `MessagePackCodec` 一直都用 static 實例；這個歧異源自 Newtonsoft → STJ 的機械式移植，在 Newtonsoft 下 per-call 建立 `JsonSerializerSettings` 是無害的。（`659325ed`）

- **`AssemblyVersion` 與 `FileVersion` 恢復與 `Version` 同步。** 這對 4.16.0 與 4.17.0 的意義見[升級指引](#升級指引)。

## 修正

- **三個會被並行讀取的共用集合改為並行安全集合。** `DbProviderRegistry` 與 `DbDialectRegistry` 在 production 啟動後唯讀，但測試中不是——註冊與查找跨類別平行執行，resize 期間的並行讀會得到 `IndexOutOfRangeException` 或無限迴圈，是典型的*本機綠、CI 紅*根因。`ClientDefineAccess` 的快取文件宣稱「同一 key 的並行讀者共用單一 in-flight 請求」，但 `TryGetValue` 後接索引賦值並非原子，而 `ListView` 的 fire-and-forget 呼叫會把續行丟到 thread pool。快取現為 `ConcurrentDictionary<string, Lazy<Task<object>>>`；`Lazy` 是關鍵，因為 `GetOrAdd` 的 value factory 在競爭下可能被呼叫多次，而對這個快取而言那就是它存在要防的重複往返。（`bb27e568`）

- **`SystemBusinessObject` 供應 `PluginSettings` 時不再直接序列化共用快取實例。** 它原本呼叫 `XmlCodec.Serialize(cached)` 而非既有的守門路徑。`XmlCodec.Serialize` 會在*來源*物件上翻序列化狀態並遞迴傳播到子集合，因此它不是免費的 deep clone。（`11c106f2`）

## 升級指引

### ExecFunc handler 必須宣告存取控制

```diff
  public class MyExecFuncHandler : IExecFuncHandler
  {
+     [ExecFuncAccessControl(ApiAccessRequirement.Authenticated)]
      public void DoSomething(ExecFuncArgs args, ExecFuncResult result) { ... }
  }
```

未標註的方法在派發時會被拒絕。BEE3003 會先讓建置失敗，所以漏標在編譯期就現形，不會拖到執行期才被拒。只應在行程內執行的操作改用 `[ExecFuncAccessControl(LocalOnly = true)]`。

### `ExecFuncLocalAsync` 呼叫端

沒有可遷移的去處，也沒有可用的東西需要遷移——任何既有呼叫自 2025-10-03 起都在擲 `MissingMethodException`。刪掉該呼叫，或把該操作改走 `ExecFunc`，並在 handler 上標 `[ExecFuncAccessControl(LocalOnly = true)]`。

### `DbParameterSpecCollection.Add`

原始碼不受影響——`collection.Add(name, value)` 與 `collection.Add(field)` 照樣解析，只是解析到擴充方法。對 4.17.0 或更早版本編譯的組件必須重新編譯。

### 帳號鎖定

既有部署升上來後，密碼在十五分鐘內連錯五次會開始鎖定帳號。要維持原行為，在呼叫 `AddBeeFramework` 之前先註冊一個 no-op 的 `ILoginAttemptTracker`——框架自己是以 `TryAdd` 註冊的。

### 組件版本 identity

`AssemblyVersion` 與 `FileVersion` 最後一次調整是為 4.16.0，4.17.0 沒有跟著動，因此**已發布的 4.17.0 套件內組件標的是 4.16.0.0**——兩個版本在組件 identity 上無從區分。4.18.0 恢復慣例（三個欄位一起動）並直接跳到 `4.18.0.0`；`4.17.0.0` 從未存在，也不會補發。4.17.0 不重新發布。任何依組件版本（而非套件版本）做判斷的地方，都需要把這個斷點納入考量。

## 回溯補記：`IExcelHelper` 移除於 4.16.0

`IExcelHelper` 刪除於 `206d29ff`，屬 4.16.0 的一部分，卻從未出現在任何 CHANGELOG——那個 commit 的訊息自己寫了「須列入 CHANGELOG breaking change」，而該步驟被跳過。該條目現已補進它該在的位置：[4.16.0 說明](4.16.0.zh-TW.md)。之所以在這裡也記一次，是因為手上已經是 4.16.0 的讀者沒有理由回頭重看那一版的說明。

這是產出本版的同一次體檢查出來的，同時查出兩份維運文件把這個缺口描述成「已關閉」。兩處都已更正。那兩份文件與它並列的 `IEvictableCache`，在 4.16.0 是**有**正確記錄的。
