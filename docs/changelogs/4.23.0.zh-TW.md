# Bee.NET 4.23.0 — 詳細版本說明

[English](4.23.0.md) ・ [繁體中文](4.23.0.zh-TW.md) ・ [← CHANGELOG](../../CHANGELOG.zh-TW.md)

本文件是 [CHANGELOG.zh-TW.md](../../CHANGELOG.zh-TW.md) 中 `[4.23.0]` 條目的展開版。主 CHANGELOG 每項變更一行；本檔保留完整脈絡——每項變更背後的**為什麼**、限制條件與設計考量。

> 本版補上「`FormLayout` 是畫面權威來源」這條規則的一個破口。該規則在客製層本來就成立——base schema 新增欄位不會自動出現在已客製的租戶畫面上——但在**版面檔缺席**時卻不成立：執行階段會默默由 `FormSchema` 推導一份。而推導出來的版面是一份沒有人審過、也不存在於任何地方的投影，那恰恰是「權威來源」應該排除的東西。**版面現在一律在設計階段產出、執行階段原樣讀取；缺檔屬設定錯誤。** 產生器留在框架內並轉為公開 API，`tools/DefineEditor` 則補上產生該檔案的入口。

## 破壞性變更

### `FormLayout` 於設計階段產出，執行階段不再推導

**移除** `FormSchema.GetFormLayout(string)`。它本身只是對 `FormLayoutGenerator` 的一行呼叫，問題出在它的形狀：`Schema.GetFormLayout()` 正是執行階段路徑「沒有經過決定就會順手叫到」的樣子。現在產生版面必須顯式指名產生器——`FormLayoutGenerator.Generate(schema, layoutId)`——意圖就攤在呼叫點上。

這與先前「`FormLayout` 是畫面上有什麼的權威來源」是同一條線。`Bee.Analyzers` 的 **BEE2005**（「FormSchema 應有對應的 FormLayout」）早已是這個定位的先聲，只是它警告的東西在執行期會被默默補上，所以那道警告背後沒有任何後果。現在有了。

三條執行階段路徑改變：

- `FormDefinitionLoader.GetRuntimeLayoutAsync` 在客製層與 base 層都沒有定義時擲 `InvalidOperationException`，不再產生一份。訊息會指出缺的是哪個 `layoutId`、該檔案應落在哪個相對路徑。
- `FormView`（Avalonia）改由新的 `ResolveLayoutAsync` 解析：host 設定的 `Layout`，其次 `DefinitionLoader` 組裝出的執行階段版面，最後是經 `ClientInfo.DefineAccess` 取得的 base 定義。
- `FormPage`（Blazor Server）的無 loader 分支改讀 `GetDefineAsync<FormLayout>`，不再由剛取得的 schema 推導。

本決策與被排除的替代方案記錄於 [ADR-039](../adr/adr-039-formlayout-design-time-only.md)。

**沒有改變**的是兩層如何疊加。`CustomizeOverlay.PickFormLayout` 完全未動——租戶的版面仍然整份勝出、覆蓋 base 版面，兩層永不合併。

另外要留意：base 定義缺檔時，錯誤通常來自**伺服端**而非 loader 自己的防線——`ClientDefineAccess.GetFormLayoutAsync` 走的是 `GetDefine` / `DefineType.FormLayout` 這條，對應到 `CacheDefineAccess.GetFormLayout(layoutId)`，而該多載本來就會對缺檔擲例外。loader 的 `InvalidOperationException` 涵蓋的是剩下那種情形：伺服端回了空的 payload。

**誰會被這項變更打到。** 任何依賴執行期推導的部署——也就是有 `FormSchema` 卻沒有對應 `FormLayout` 檔的部署——在開啟表單時會失敗。這正是本次變更的意圖，而 BEE2005 會在建置階段列出究竟是哪些 schema。見「升級指引」。

## 新增

### `FormLayoutGenerator` 轉為公開 API

`Bee.Definition.Layouts.FormLayoutGenerator` 由 `internal` 改為 `public`，並以 `<remarks>` 敘明其設計階段定位。它留在 `Bee.Definition` 而非搬到 `tools/`，理由有三：既有的產生器測試將無處安放（`tools/DefineEditor` 沒有測試專案，只有自帶的 `Smoke.cs`）；本 repo 的 scaffolding 流程是以框架公開 API 的形式呼叫它；以及 `DefineEditor` 並非唯一可能被建出來的定義工具。

`GetListLayout()` 與 `GetLookupLayout()` 刻意**維持原樣**。清單與 lookup 的欄位集本來就宣告在 `FormSchema` 上（`ListFields`、`LookupFields`），沒有對應的 `DefineType`、也沒有任何落檔形式——它們是 schema 的投影，不是獨立定義。單筆表單的版面是另一回事。

### `FormView.Layout`（Avalonia）

一個公開的 styled property，對稱於 `FormView.Schema`，存在理由也相同：host 可能以自己建出來的定義驅動畫面，背後根本沒有後端。`samples/Avalonia.DemoCenter` 正是這種情形——它的版面模組以程式碼建 schema，從不與伺服器往來。這類 host 現在自行供應要渲染的版面，畫面不再自己憑空生一份。

### `tools/DefineEditor` 的「產生 FormLayout」

FormSchema 編輯器的 schema 節點新增右鍵命令，寫出 `{DefinePath}/FormLayout/{ProgId}.FormLayout.xml` 並開啟它。版面現在只能從這裡來，所以編輯定義的工具必須能產出它。

對既有檔案重新產生會**先要求確認**——那會丟掉版面上所有人工調整，是本命令唯一的破壞性動作。新增的 `DocumentViewModelBase.DefineFileGenerated` 事件把寫出的路徑帶給主視窗，由主視窗重掃方案樹並選取該檔；document view-model 沒有方案樹的參考，改由它拋事件可讓相依維持單向。

## 修正

### Blazor 範例無法登入

`samples/Blazor.Server.Demo` 與 `samples/QuickStart.Server` 的登入都以 `no such table: st_user` 失敗。根因是烙在範例 backend 裡的一個誤讀：把「覆寫認證」當成了「不需要 common 系統表」。並非如此。`AuthenticateUser` 取代的只有憑證檢查那一段——登入路徑的其餘部分仍要從 `st_user` 取該使用者的語系設定，並把 session 種子寫進 `st_session`。

`DemoBackend` 現在會連同 `st_cache_notify` 一起 materialize 這兩張表，`DemoSchemaSeeder` 則負責建表並種入對應的 locale 列。該列不帶密碼、也不帶語系值：空白的雜湊會被 `UserRepository.VerifyPassword` 直接拒絕，因此這筆列本身無法用來登入；而空白的語系值正是讓 session 落回 `BackendConfiguration` 部署層預設的方式。

## 變更

### `st_*` 系統表明訂為必備設施

上述範例缺陷可以一路追到一件從未被寫明的事：框架在服務一般請求的過程中就會讀寫它的 `st_*` 表，因此部署端一律要建，不論自己用不用得到——而**覆寫框架行為不等於豁免其背後的資料表**。

[框架保留命名](../framework-reserved-names.zh-TW.md) §1 現在明文寫出這點，因為那裡是「有哪些 `st_*` 表」的唯一權威來源，也就是讀者查這件事時會待的位置。五處講法相反的敘述一併修正，包括最初惹禍的那一處：`SystemBusinessObject.ApplyUserLocale` 的 remarks 原文寫「a deployment may authenticate against something other than `st_user`, in which case there is no row to read」，講的是缺**列**，讀起來卻像缺**表**。

`UserRepository.GetLocale` 維持原狀。它容忍缺列、不容忍缺表，而在本規則下這是正確的：表本來就必須存在，缺表屬部署設定錯誤，應該大聲失敗。

## 升級指引

**每一份 `FormSchema` 都需要對應的 `FormLayout` 檔。** 開著 analyzer 建置，BEE2005 就會列出還缺哪些：

```
BEE2005: FormSchema 'X' has no corresponding layout at FormLayout/X.FormLayout.xml,
so opening the form fails at run time.
```

要補齊這些檔案，用 `tools/DefineEditor` 開啟定義資料夾，選取該 FormSchema 節點，執行 **產生 FormLayout**。產出的檔案是一個「起點」，本就該經人工檢視與調整——自該刻起它是一份定義，不再是推導出來的產物。

呼叫了被移除方法的程式碼，機械替換如下：

```diff
- var layout = schema.GetFormLayout(layoutId);
+ var layout = FormLayoutGenerator.Generate(schema, layoutId);
```

注意這需要補 `using Bee.Definition.Layouts;`，也請注意這只是**設計階段程式碼**的正確替換——定義工具、測試 fixture，或在記憶體中建定義的 host。**執行階段的程式碼應改為讀取已存檔的定義**，經 `FormDefinitionLoader.GetRuntimeLayoutAsync` 或 `IDefineAccess`。

以 schema 驅動 `FormView` 而無後端的 host，改設新屬性：

```diff
  var view = new FormView { Schema = schema };
+ view.Layout = FormLayoutGenerator.Generate(schema, progId);
```

不需要協調式部署：wire 格式與客製層的疊加語意都未變更。
