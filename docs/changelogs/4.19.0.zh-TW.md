# Bee.NET 4.19.0 — 詳細發行說明

[English](4.19.0.md) ・ [繁體中文](4.19.0.zh-TW.md) ・ [← CHANGELOG](../../CHANGELOG.zh-TW.md)

本文是 [CHANGELOG.zh-TW.md](../../CHANGELOG.zh-TW.md) 中 `[4.19.0]` 條目的詳細版。主 CHANGELOG 每項變更只留一行；本檔保留完整敘事——WHY、限制，以及每項變更背後的設計脈絡。

> 本版把定義層與傳輸格式解耦。在此之前，`Bee.Definition` 帶著 `MessagePack` 套件參考，37 個原始檔標註了 `[MessagePackObject]`、`[Key]`、`[Union]`、`[IgnoreMember]`。它的消費者——`Bee.Db` 與五個 provider 的 command builder、`Bee.Repository`、`Bee.Business`、`Bee.UI.Avalonia`、`Bee.Cli`、`DefineEditor`——沒有一個需要 MessagePack，卻全部經相依鏈繼承了它。更根本的問題是定義型別與單一傳輸技術焊死：日後換格式，就得回頭改定義本身。
>
> 這裡畫的分界線不是「是不是傳輸格式」，而是**「會不會讓定義層長出外部套件相依」**。`[XmlIgnore]` 與 `[JsonIgnore]` 屬平台詞彙、不帶任何相依，所以 XML 與 JSON 留下；MessagePack 是會沿相依鏈傳染的技術選擇，所以外置。見 [ADR-036](../adr/adr-036-wire-serialization-externalized.md)。

## 破壞性變更

### 兩個型別家族的 wire 格式有變

多數型別不受影響：`[MessagePackObject(keyAsPropertyName: true)]` 與 contractless resolver 都以屬性名為鍵，移除標註後產出的位元組完全相同。有兩個家族不在此列。

- **`FilterNode` / `FilterCondition` / `FilterGroup`** 由 MessagePack 的 `[Union]` 編碼（`[型別碼, 整數鍵 map]` 兩元素陣列）改為帶具名 `Kind` 判別碼的 map。判別碼寫成具名成員而非陣列首元素，是為了讓 payload 自我描述——把 map log 出來看得到 `Kind`，而不是一個意義寫在別的檔案裡的裸整數。這也讓 MessagePack 與 JSON 對齊：JSON 端的 `FilterNodeCollectionJsonConverter` 一直都是讀 `Kind` 判型的。

- **`ParameterCollection`** 由單鍵 map（`{0: [items]}`，來自 `[Key(0)] ItemsForSerialization` proxy 屬性）改為純 items 陣列。那個 proxy 存在的唯一理由是「MessagePack 的 `[Key]` 標註只能標在屬性上」；改由 formatter 寫出綁定後，屬性與標註都不再需要。

**`ParameterCollection` 掛在 `ApiMessageBase.Parameters` 上，也就是每一個 request 與 response 都帶著它。** 因此 4.18 的 client 無法與 4.19 的 server 溝通，反之亦然。兩端須一併部署。

### 移除的公開 API

- **`Bee.Definition.Collections.MessagePackCollectionBase<T>` / `MessagePackCollectionItem` / `MessagePackKeyCollectionBase<T>` / `MessagePackKeyCollectionItem`。** 這四個是 `Bee.Base.Collections` 對應型別的刻意複製，理由寫在它們自己的 remarks 裡：`Bee.Base` 不引任何外部套件，因而無法承載這些型別需要的 MessagePack 標註。標註消失，理由也就消失——四個型別合併回原本的實作。改基底型別與 `using` 即可，其餘不變。

  複製品帶著一筆維護稅，remarks 曾試圖擋住它（「Keep the two in step——分歧應該只有 attribute」）。但那條要求早就被違反了：`Bee.Base.KeyCollectionBase.GetOrDefault` 在 MessagePack 版中從未有對應物。

- **`Bee.Definition.Serialization.SafeTypelessFormatter`。** `Parameter.Value` 的型別是 `object?`——這是刻意保留的彈性，讓呼叫端能經 `ExecFunc` 傳遞額外參數——意味著 payload 必須自帶型別名、讀取端據以實例化。那正是經典的 deserialization gadget 路徑，而這支 formatter 就是把它關起來的白名單。它是傳輸層的安全邊界，因此遷入 `Bee.Api.Core` 並改為 `internal`；傳輸管線以外不該有人碰得到它。

- **`Bee.Base.IObjectSerializeProcess`、`SerializeFormat`、`SerializationLifecycle.NotifyAfterDeserialize`。** 該介面在 production 沒有任何實作者，唯一的實作者是為了測它而寫的 test payload。它的兩個歷史用途——先是 `SystemSettings`，後是 `DatabaseSettings`——都已被刻意遷走，因為「讓 DTO 在序列化過程觸碰 process-wide static state」是框架已經否決過的模式。把介面留在公開表面上，等於邀請同一個反模式再來一次。`SerializeFormat` 的唯一用途是餵那三個方法的參數。

### 退役的 analyzer 規則

`BEE4001`（集合須註冊 formatter）、`BEE4002`（JSON 改名與 MessagePack 鍵不一致）、`BEE4003`（union 階層須維持整數 `[Key]`）、`BEE4004`（建構子參數順序 vs `[Key]` 順序）移除。四者各自把關標註機制的某個性質，而機制已經不存在：全 repo 沒有 `[MessagePackObject]`、沒有 `[Key]`、沒有 `[Union]`，也沒有會漏填的註冊清單。

`BEE4005` 與 `BEE4006` 保留。它們把關的「單一 public `Add`」「public 無參數建構子」是行動端 reflection-only `XmlSerializer` 路徑的要求，與傳輸格式無關。

## 變更

### wire 綁定：contractless 加手寫 formatter

綁定現在住在 `src/Bee.Api.Core/MessagePack/`。沒有框架管理成員需排除的型別完全不需要 formatter——contractless resolver 以屬性名為鍵，正是標註原本做的事。九支 formatter 涵蓋那些不夠用的情況：

| Formatter | 存在理由 |
|-----------|---------|
| `SortFieldFormatter`、`DepartmentNodeFormatter`、`NumberFormatItemFormatter`、`CashRoundingItemFormatter`、`AllowedCurrencyItemFormatter`、`ParameterFormatter` | 逐一具名 wire 成員，把框架管理的成員擋在 wire 之外（`Tag`，以及會無限遞迴的集合反向導航） |
| `FilterNodeFormatter` | 多型，以 `Kind` 為判別碼 |
| `KeyCollectionBaseFormatter` | contractless 會把 `KeyedCollection<TKey, TItem>` 綁成 dictionary，元素還原為 `Dictionary<object, object>` 而非 item 型別 |
| `CollectionBaseFormatter`、`DataSetFormatter`、`DataTableFormatter` | 既有 |

**為何手寫而非反射驅動。** 最初的設計是一支泛型 formatter，讀取自訂標註決定納入哪些成員。它在行動端不可行：對任意屬性型別遞迴只能走非泛型的 `MessagePackSerializer.Serialize(Type, ref MessagePackWriter, object, options)`，而 `MessagePackWriter` 是 `ref struct`，該多載需要 `Reflection.Emit` 產生能傳遞它的委派。動態程式碼不可用時直接擲 `NotSupportedException`。逐一具名成員讓整條路徑維持泛型，裝置與桌面跑同一份程式碼。

代價是：為這些型別新增屬性就必須同步更新其 formatter，而編譯器不會把兩者綁在一起。因此每支 formatter 都公開一個 `WireMemberCount` 常數，由 wire 測試對 map header 斷言，兩邊形狀無法靜默漂移。

### 套件參考

`Bee.Definition` 與 `Bee.Api.Contracts` 不再引用 `MessagePack`。全 repo 僅存 `Bee.Api.Core` 一處。

### BEE4006 保住對 item 型別的覆蓋

它的判定原本是「帶 `[MessagePackObject]` **或** 是框架集合」。標註消失後第一條路失效——但 item 型別正是靠那條被涵蓋的，而 reflection-only 的 `XmlSerializer` 確實需要它們有無參數建構子。`FrameworkCollectionTypes.IsFrameworkCollectionItem` 讓這段覆蓋從順帶變成顯式。

## 升級指引

### 集合基底型別

```diff
- using Bee.Definition.Collections;
+ using Bee.Base.Collections;

- public class MyItems : MessagePackCollectionBase<MyItem> { }
+ public class MyItems : CollectionBase<MyItem> { }

- public class MyItem : MessagePackCollectionItem { }
+ public class MyItem : CollectionItem { }
```

`Bee.Base` 的型別形狀相同——外加 `KeyCollectionBase<T>.GetOrDefault`，那是 MessagePack 複製版從未有過的。

### 部署

Server 與 client 必須一併升級。見上方 wire 說明。

### 定義新的 wire 型別

若沒有框架管理成員需排除，什麼都不用做——contractless resolver 會處理。若有，在 `Bee.Api.Core/MessagePack/` 寫一支 formatter、於 `MessagePackCodec` 註冊，並公開 `WireMemberCount` 常數在 wire 測試中斷言。

## 已知限制

模擬行動端 AOT 路徑（`IsDynamicCodeSupported=false`）時，`Bee.Api.Core.UnitTests` 仍有失敗，集中於 `TypelessFormatter`、`DataTable`、`DataSet`。這些在本版之前即已存在——改動前的基準是 694 項中失敗 51 項——手寫 formatter 降低了數量但未清零。

這與「MessagePack 在行動端 AOT 可用」的既有結論並存得不太舒服，值得獨立追查。判讀時有兩點保留：模擬跑在 JIT runtime 上，真實裝置行為未必相同；且部分失敗擲的是 `InvalidProgramException` 而非乾淨的 `NotSupportedException`——那是「Emit 仍執行、但產出無效 IL」的徵狀，很可能是模擬本身的假象而非真實缺陷。

### 後記（2026-08-11）

**上述的保留判斷是錯的，4.20.0 已更正。** 那些失敗是真實缺陷而非模擬假象：在 NativeAOT 與真實 Mono runtime 上都能重現，而 `DynamicCodeSupport=false` 正是 .NET for iOS SDK 對**每一種** iOS / tvOS / MacCatalyst 建置所設的預設值。例外的**種類**確實隨 runtime 而異——那半的保留成立——但 pass / fail 的邊界不會變，而把一次真實失敗讀成量測的假象，讓這個修正延後了一整個版本。見 [ADR-037](../adr/adr-037-wire-explicit-registration.md)。

**〈定義新的 wire 型別〉那段指示亦已被取代。** 不再有 `WireMemberCount` 常數需要公開：每個 wire 型別在 `Bee.Api.Core/MessagePack/WireContracts.*.cs` 註冊合約，由 `WireContractDriftTests` 走型別閉包攔截遺漏。
