# Bee.NET 4.29.0 — 詳細變更說明

[English](4.29.0.md) ・ [繁體中文](4.29.0.zh-TW.md) ・ [← CHANGELOG](../../CHANGELOG.zh-TW.md)

本文件是 [CHANGELOG.zh-TW.md](../../CHANGELOG.zh-TW.md) 中 `[4.29.0]` 條目的詳細版本。主 CHANGELOG 每項變更一行；本檔保留完整敘述——每項變更背後的**原因**、限制與設計脈絡。

> `PluginSettings.xml` 只列型別。每個 plugin 跑在哪個時點來自對類別的反射，於是這份檔案答不出任何人打開它想問的那一個問題。[ADR-035](../adr/adr-035-business-logic-plugin.md) 當初接受這個代價，靠的是「由維護工具算出並顯示各時點」這個補償——而那個工具從未被做出來，可讀性代價因此一直是淨損失。本版把時點寫進設定檔，並讓一個 plugin 只掛一個時點。**放棄了什麼直說**，因為 ADR-035 自己稱它是該機制的唯一實質優勢：plugin 不能再用 instance field 把狀態從 `BeforeSave` 帶到 `AfterSave`，因為那現在是兩個類別。

## 破壞性變更

### `PluginItem` 明寫時點，且一個 plugin 一個時點

```xml
<PluginItem Type="Acme.Plugins.CreditLimitCheck, Acme.Plugins" Stage="BeforeSave" />
<PluginItem Type="Acme.Plugins.OrderSync, Acme.Plugins"        Stage="AfterSave" />
```

`Stage` 是必填的，而且類別必須覆寫該時點、且不覆寫其他時點。「存檔前檢查」加上「存檔後通知」因此是兩個類別，兩者之間沒有共享欄位：`After` 那個類別需要的資料要自己重讀或重算。

理由是責任單一，不是型別限制。四個時點的簽章只在 Save 管線與 Delete 管線之間不同——`BeforeSave` 與 `AfterSave` 都收 `SaveContext`——所以一個類別兼做兩件事在型別上一直做得到。它之所以不再被允許，是因為兩者的工作性質不同，也因為一份寫著時點的檔案才讀得出誰跑在哪裡。

**不附遷移指引，也不需要**：整個 repo 沒有任何 `PluginSettings.xml`（套裝與範例皆無），這個格式沒有消費者。

### 反射沒有退場，降為驗證器

建鏈時會把宣告與類別對帳，任何不一致一律拒絕——型別什麼都沒覆寫、覆寫超過一個時點、沒宣告 `Stage`、或宣告了一個它沒覆寫的時點。訊息會列出類別實際覆寫的時點，所以修法就寫在訊息裡。

兩道閘門執行它，而且不是重複的。`SystemBusinessObject.SaveCustomizePluginSettings` 在儲存時拒絕，編輯繫結的人當場就知道；`PluginSettingsResolver` 在解析時拒絕，而那是**手寫檔**唯一會經過的閘門——套裝層的 `{DefinePath}/PluginSettings.xml` 根本沒有維護 API。

代價要誠實寫出來：改變類別覆寫的時點，現在必須連帶改 XML。以前重新部署組件就自動生效。失敗是大聲的而不是靜默的，而且付代價的人就是編輯那份檔案的人。

### API 變更

- **移除** `Bee.Business.Form.FormPluginStage`。宣告用的型別必須存在於 `PluginItem` 所在的 `Bee.Definition`，而相依方向是 Business → Definition。`Bee.Definition.Settings.PluginStage` 取代它成為唯一的列舉。沿用舊名放到新命名空間已被否決：同名不同命名空間的兩個列舉，會在同時 using 兩邊的消費端造成 `CS0104`。
- `PluginStage.None = 0` 是「未宣告時點」的哨兵，兩道閘門一律拒絕。它為診斷而存在、不為相容：XML 少一個屬性會靜靜拿到列舉的 0 值而不報錯，把 0 值留給「沒宣告」，訊息才說得出「你沒宣告 `Stage`」，而不是比較兩個剛好對不上的時點。
- `PluginItem(string type)` 改為 `PluginItem(string type, PluginStage stage)`，`PluginItemCollectionExtensions.Add` 同理。**不留舊多載**——「建得出沒有時點的 `PluginItem`」的入口正是本次要移除的東西。公開的無參數建構子保留，供 `XmlSerializer` 的 reflection-only 路徑使用。
- `PluginSettings.GetPluginTypes` 與 `CustomizeOverlay.GetPluginTypes` 改名為 `GetPluginBindings`，回傳 `IReadOnlyList<PluginBinding>`——型別名與時點的 `readonly record struct`。回傳的是值複本而不是 `PluginItem` 實例：設定物件是 process-wide 快取的，交出它的項目等於邀請呼叫端去改每個 session 都讀得到的東西。兩層語意不變——套裝鏈在前、租戶鏈在後，一樣沒有 tombstone。
- `FormPluginChain.Create` 改收 progId 與 `IReadOnlyList<FormPluginBinding>`；`HasStage` 與 `TypesForStage` 改收 `PluginStage`。

**二進位相容性：不相容，且可接受。** 移除公開列舉、更換建構子與方法簽章，會讓任何已編譯的消費端斷掉。業務 plugin 沒有消費者——格式自 4.17.0 出貨，本 repo 內沒有任何定義檔在用，`src/` 之外也沒有任何東西讀 `PluginSettings`。

## 變更

### plugin 改為按需建構

`FormPluginRunner` 原本第一次用到就建整條鏈，包含只掛 delete 時點的 plugin。那在「後面的時點要找到同一個物件」的前提下是必要的；一個 plugin 一個時點之後純屬浪費。現在 plugin 只在它自己那個時點第一次執行時才被建出來，否則完全不建，因此一次 Save 不會建構只掛 delete 時點的 plugin。建構仍走 `ActivatorUtilities`，所以 plugin 可以在三個定位參數之外宣告自己的注入相依。

實例仍是每次操作各自的、不跨呼叫共用，因此不需要考慮鎖。不再具備的是跨時點承載狀態。

### `DeleteContext.Snapshot` 的載入條件行為不變

`FormBusinessObject.Delete` 仍然先問 chain「有沒有 plugin 跑在 delete 時點」再決定要不要載入快照。答案的來源從反射換成宣告，而既然兩者已對帳，值與先前完全相同。
