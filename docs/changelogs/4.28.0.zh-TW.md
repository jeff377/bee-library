# Bee.NET 4.28.0 — 詳細版本說明

[English](4.28.0.md) ・ [繁體中文](4.28.0.zh-TW.md) ・ [← CHANGELOG](../../CHANGELOG.zh-TW.md)

本文件是 [CHANGELOG.zh-TW.md](../../CHANGELOG.zh-TW.md) 中 `[4.28.0]` 條目的詳細版本。主 CHANGELOG 每項變更一行；本檔保留完整敘事 —— 每項變更背後的*理由*、限制與設計脈絡。

> 本版是一次系統性框架健檢的產出。幾乎每一條發現最後都是同一種形狀：**一道防護機制的實際涵蓋範圍比它看起來的窄，而沒有任何東西會說出這件事。** 這個形狀值得明講，因為它不是紀律問題。一道被跳過而不是失敗的守衛、一道因為問錯問題所以是綠的閘門、一條因為比對對象是空檔案所以永遠不可能觸發的規則 —— 它們都不會自己出聲，也都不是「記得再仔細一點」就能解決的。所以本版同時做兩件事：把破口關上，並把那些「本來該發現」的機制自己也納入把關。

## 破壞性變更

### `System.CheckPackageUpdate` 與 `System.GetPackage` 移除

兩者都是基底實作擲 `NotSupportedException`、供宿主覆寫的擴充點。兩者都沒有消費者。判準用的是真正能決定這個問題的那一條：**API 合約方法的直接消費者就是 API connector。** `Bee.Api.Client` 對兩者都沒有 connector 方法，而文件明寫它們不給 JavaScript 前端用 —— 兩條路徑都是空的。

那條判準有一個已載明的例外，而誠實地套用它很重要。40 個 BO 公開 API 方法中，有四個未被 `Bee.Api.Client` 引用。其中三個 —— `GetFormSchema`、`GetFormLayout`、`GetLanguage` —— 是給非 .NET 客戶端的逐型別入口；.NET 呼叫端用 `GetDefineAsync` 即可，寫 wrapper 只會複製一份。刪掉它們等於打斷它們存在的理由。`GetPackage` 是唯一真正沒有消費者的，而 `CheckPackageUpdate` 是它的另一半 —— 兩者是同一個流程（檢查更新 → 下載套件），留下一半只會剩下比整體更沒有意義的東西。

移除先後涉及三層共八個與七個檔案，另加 `SystemActions` 常數、`SystemBusinessObject` 方法、五處 MessagePack wire 註冊、四個專案共 126 行 `PublicAPI` 基準、六份 README、四份公開文件與五個測試檔。`MessagePackContractsTests` 一併移除 —— 兩批刪完之後它只剩空殼。契約組件至此已無任何列舉，README 的「穩定列舉值」規範因此失去對象，也一併移除。

ADR-014 的決策原文保留為它本來的性質（紀錄），只加註兩個方法皆已移除 —— 讀者不該去找一個不存在的東西。

### 契約集合收斂為唯讀型別

契約介面的五個集合成員中有四個曝露具象 `List` / `Dictionary`，而兩個較新的 —— `IListApiKeysResponse.ApiKeys` 與 `IGetChangeDetailResponse.Fields` —— 已經在用 `IReadOnlyList`。慣例已經成形；這四個是沒人回頭收的舊債。留著就是同一份契約帶著兩套慣例。

四個當中有兩個隨 `CheckPackageUpdate` 一起消失；實際出貨的是 `ISaveResponse.AffectedRows` 與 `IEnterCompanyResponse.Capabilities`。序列化零影響。八個實作端的具象可寫屬性一字未改，各只多一行顯式介面實作，照抄 `ApiKeys` / `Fields` 早已在用的模式而非自創寫法。wire DTO 與 BO 仍是可寫的具象集合，繫結不受影響，而 `wire-contracts/` 與 `wire-fixtures/` 零 diff。

會壞的是「透過契約介面」取得該集合並想寫入它的外部程式碼。但契約介面本來就全是 `{ get; }` —— 能透過它們拿到可變集合，是當初宣告型別選錯造成的意外能力，不是設計。

### `isLocalCall` 預設改為 `false`

預設 `true` 的意思是：直接建構 BO —— 唯一繞過 `ApiAccessValidator` 的路徑 —— 預設被當成可信的行程內呼叫。數個方法的第二道防線正是以 `IsLocalCall` 為條件：免 deployment admin 鑄造 API key、授予 deployment admin、寫入 server-only 定義。那幾道守衛對預設路徑全數放行，只擋刻意寫了 `isLocalCall: false` 的呼叫端 —— 而那是最不需要擋的一種。

四處守衛的註解都寫著「直接建構 BO 的呼叫端不會經過 `ApiAccessValidator`」。寫得沒錯，只是漏了下半句：*所以它們預設就是 local。*

影響範圍實測後比預期小很多。`src/`、`apps/`、`samples/`、`tools/` 完全沒有直接建構 BO，全部 120 多個建構點都在 `tests/`，而 `BusinessObjectFactory` 一律顯式傳入。這個預設值在框架內部從來沒被用到過。它只作用於測試與外部消費者 —— 而後者正是最不設防的那群。

28 筆測試因此變紅，全部集中在那四道守衛保護的區域。它們原本能過，正是*因為*預設值讓守衛失效。六個建構點現在明講 `isLocalCall: true`，把「我要走本機路徑」變成寫出來的，而不是撿到的。

二進位相容性值得講精確：optional 參數的預設值是在*呼叫端*編譯時烘入的，所以既有已編譯的組件維持舊行為，只有重新編譯才會拿到 `false`。

### 搬遷與移除

`ApiCallContext` 從不上 wire，卻一直被發佈進產生的 TypeScript 合約。移除它的 MessagePack 註冊什麼也沒改變，因為產生器不讀註冊清單 —— 它按命名空間反射掃。根因是它根本不該在 `Bee.Api.Core.Messages`：它是 `ApiAccessValidator` 的輸入，由 `JsonRpcExecutor` 每次呼叫建一個。搬到 `Bee.Api.Core.Validator` 之後，合約裡同時少掉它與 `PayloadFormat` —— 而後者才是更有價值的那個移除，因為 `PayloadFormat` 在合約裡是字串聯集（`'Plain' | 'Encoded' | 'Encrypted'`），而 wire 上帶的是數字。同名欄位的合約與 wire 互相矛盾。

`ApiPayloadOptionsFactory.CreateSerializer` 沒有任何 production 呼叫者，而它的「不存在」需要的是說明而不是補齊：body codec 是逐請求宣告的（[ADR-044](../adr/adr-044-payload-codec-negotiation.md)），不是逐部署設定。不過移除它並沒有關上那扇危險的門 —— `ApiServiceOptions.Initialize(serializer, …)` 仍然收一個，而任何人都可以 `new JsonPayloadSerializer()`。所以那個參數現在帶著一段警告，寫明它的實際語意：不是「本部署用哪個 codec」，而是「未宣告 codec 的請求被當成哪個 codec 讀」，那是相容性常數。換掉它等於用既有 client 從未用過的 codec 去讀它們的 body，而失敗發生在伺服端反序列化時，離這個呼叫很遠。

`HttpUtilities` 搬離 `Bee.Base` 的理由就是 `rules/dependency-boundary.md` 寫的：`Bee.Base` 不是抽屜。它是每一個專案的相依 —— 含只讀定義的 UI head 與離線的定義檔工具 —— 所以放在那裡的任何東西都會出現在每個消費者的公開表面上，不管它用不用得到。它的三個呼叫點從頭到尾都在 `Bee.Api.Client`。新增的閘門斷言 `Bee.Base` 的 IL 參考不得含 `System.Net.Http`，刻意只擋這一個組件而非整個 `System.Net`：`IPValidator` 的 `IPAddress` 是 CIDR 值比對、不會連到任何地方，混為一談的閘門會逼人為了通過而搬錯東西。

## 安全性

### 雜湊段為空的值對任何密碼都驗證通過

`PasswordHasher.VerifyPassword` 對雜湊段為空的儲存值回傳 `true`。PBKDF2 要 0 個輸出位元組會回空陣列，而 `FixedTimeEquals` 判兩個空 span 相等。`v2.100000..` 因此對任何東西都驗證通過，v2 與 legacy 兩個分支皆然。`UserRepository` 既有的短路只擋整串為空的字串。

單就這一點，還需要有寫入 `st_user.password` 的能力，這正是另一半的重要之處：該欄先前不在 `ProtectedFields` 內。任何在 `st_user` 上建了使用者維護表單的部署，都能經 FormSchema 資料路徑寫它。兩者合起來是一條完整的提權鏈，所以兩半一併關閉。

`ProtectedFieldsTests` 原本把 `("st_user", "password")` 列在*不受保護*的案例裡 —— 等於把這條提權路徑寫成規格。現已改為正向斷言，並就地寫明理由。

刻意不加 `iterations` 下限。低迭代數不是活的繞過 —— 要利用它得先有本次移除的寫入權 —— 而下限會把迭代數較低的合法 legacy 雜湊鎖在門外。

### 只帶明細列的存檔完全跳過記錄範圍檢查

`FormBusinessObject.Save` 的層二檢查以主檔表存在於 DataSet 中為前提：`HasExistingMasterWrite` 與 `EnforceWriteScope` 在它缺席時都直接 return。但 `DataFormRepository.Save` 是對每張表獨立判斷是否在 DataSet 裡，主檔缺席時明細照樣寫入。於是只含明細表的存檔根本沒有呼叫到檢查 —— 對範圍外的主檔記錄插入、修改或刪除明細列。

這與 `Save` 自己的註解直接矛盾：「Scope is master-only, so once the master passes the whole record persists with it.」—— 主檔不在 payload 裡時，沒有任何 master 通過過。

修正的過程中浮出同一個破口的第二條走法。明細列的 `sys_master_rowid` 是 payload 原樣採用 —— 它不在 `ProtectedFields`，而 `Modified` 列會被完整欄位 UPDATE 一起改寫。所以帶一個範圍內的主檔、明細卻指向另一筆主檔，同樣輕易過關，而 `Modified` 更可以把既有明細列從別人的記錄裡*搬出來*。只修第一種會製造已經修好的錯覺，故兩者一起。

`EnforceWriteScope` 改為無條件呼叫 —— 會被拒的 payload 形狀，正是先前會跳過呼叫的那些 —— 並加兩道結構檢查：宣告了主檔表、payload 卻只帶待寫的明細列，拒絕；每個待寫明細列的 `sys_master_rowid` 必須是本次 payload 帶著的主檔列之一，而那些正是剛通過範圍檢查的列。`Modified` 檢查 Original 與 Current 兩個版本：把資料搬離別人的記錄，與搬進來一樣是越界。

兩者都是拒絕而非靜默丟棄，因為這些形狀沒有合法用途。框架自己的明細-only 編輯會帶著 `Unchanged` 狀態的主檔列，這正是 `WriteScopeActionForRowState` 把該狀態映為 Update 的理由。未宣告 `PermissionModelId` 的表單完全不受影響 —— 整個方法第一行即 return —— 所以尚未採用權限模型的部署看不到任何變化。

`HasExistingMasterWrite` 隨修正一併移除：它的兩個 `false` 情形（純新增、主檔表缺席）語意相反，卻回同一個答案，那正是這個 bug 的形狀。

### 稽核記錄查詢在租戶邊界上是 fail-open

`company_id` —— 一個租戶邊界 —— 與 `prog_id`、`user_id` 這類選用篩選共用同一個「null 就略過」的 helper。尚未進入公司的 session 因此讓條件消失，拿到所有公司的稽核記錄。七個入口全部改為 fail-closed。

沒有需要保留的合法跨租戶讀取：`LogBusinessObject.CurrentCompanyId()` 就是 session 的 `CompanyId`，而 deployment admin 沒有旁路。

有六筆既有測試在守相反的行為（「無 company filter → 兩列都回」）。每一筆都先逐一判讀再改，因為守著相反行為的測試有時候是被寫下來的刻意決定。這裡不是 —— 沒有任何註解宣告允許跨租戶讀取，而本次修改正是在說那個形狀是錯的。測試改為斷言新規格，並多驗一條租戶隔離：種子資料改為兩列同屬一家公司、另一列屬另一家，於是第二個租戶確實看不到第一個的列。

### 伺服器路徑外洩給遠端呼叫者，以及 MySQL 字面值可以跳脫

定義檔反序列化失敗會擲 `InvalidOperationException`，它映射為 `UserMessage`，而該分支原樣回傳 `ex.Message` —— 於是打到損毀定義檔的已認證遠端呼叫者，就拿到了伺服器的目錄配置。這違反 `scanning.md`「例外訊息禁止包含內部路徑」。訊息現在只留檔名；完整路徑移到 `Exception.Data` 的 `SerializationErrorData.FilePath`，伺服端記錄仍然用得到。

`MySqlSchemaSyntax.EscapeSqlString` 只做引號加倍。MySQL 是這裡唯一預設把 `\` 當逸出字元的方言 —— SQL Server、Oracle、SQLite，以及開著 `standard_conforming_strings` 的 PostgreSQL 都不是 —— 所以結尾的反斜線會吃掉後面那個引號，字面值一路跑進後續語句。走框架自己的逸出、送進 MySQL 8 容器實測：`ends with backslash \` 產生語法錯誤，`a\' , (SELECT 1) , '` 亦然。

**正確性的衝擊比注入面更早到。** 一段以反斜線結尾的欄位說明（例如註記裡的 Windows 路徑）就足以讓產生的 DDL 語法錯誤，不需要任何攻擊者。體檢報告把它歸類為「定義作者 → 升級時任意 DDL」，但部署會先撞上升級壞掉的那一半。

報告列了三處 sink，實際有四處 —— `MySqlCreateTableCommandBuilder` 的資料表 COMMENT 不在其中。四處都經同一個函式。反斜線先逸出、引號後加倍；只有這兩條規則時順序不影響結果，但「先逸出逸出字元」才是日後再加規則仍然正確的順序。明示的前提是伺服器的預設 `sql_mode`：啟用 `NO_BACKSLASH_ESCAPES` 的部署會讓反斜線變成普通字元，於是看到雙反斜線。這個函式沒有連線、讀不到 `sql_mode`；PostgreSQL 方言對 `standard_conforming_strings` 早就做著同一類假設。

## 新增

### BEE1008 —— 未宣告 `PermissionModelId` 的表單對所有已認證呼叫者全開

層一授權讀表單的 `PermissionModelId`，為空就直接 return。那是刻意的 —— `FormBusinessObject.Authorize` 的 XML doc 稱之為漸進採用，未標記的表單保持開放 —— 但後果從來沒有任何地方看得到。一張該標而沒標的表單對每個已認證呼叫者全開，而 build、測試與每一個既有 analyzer 全都是綠的。

`PermissionModelAnalyzer` 報告這件事。刻意只報告不強制：改為執行期失敗會讓每個採用到一半的部署當場壞掉，而那正是 opt-in 存在的理由。缺的從來不是規則，是「這張表單是開放的」沒有地方說得出來。

嚴重度為 `Info`，而這份誠實的代價寫進了 `docs/analyzer-rules` 雙語版：`Info` 對應 MSBuild message、預設 verbosity 不印，而定義層的 analyzer 都是 `CompilationEnd`，IDE 也不會即時顯示。機制存在，但預設看不到。導入完成後在 `.editorconfig` 提升為 `warning` 才有實際把關 —— 以 `warning` 為預設會讓每個採用到一半的消費者 build 失敗，那是漸進的反面。

### 接縫、共用規則與閘門

`IApiKeyGateStateProvider` 讓 API 層不必解析 `ICacheContainer` 就能問到「API key gate 生不生效」，而後者宣告在 `Bee.ObjectCaching` —— 快取*實作*組件。那一層沒有立場知道答案是被快取的，更不該知道由哪個組件快取。`null` 與擲例外的區別刻意保留並寫進介面 doc：`null` 是「沒有東西可問」，例外是「有 store 但連不上」—— 把後者當成前者，會讓一個連不上的資料庫讀起來像一道開著的門。

`FormValueBinding` 與 `FormDataGuard` 收攏了兩個 UI head 各自帶著私有副本的表單資料規則，而它們的 doc 寫著「刻意平行」且沒有任何機制強制。漂移已經發生：五個 helper 中三個逐字相同、兩個已漂 —— 而其中一個是活的 bug，見「修正」一節。它們拆成兩個類而非一個共用袋，並放在 `Bee.Api.Client`，因為兩個 head 都已經直接參考它，而它不帶 `Bee.UI.*` 家族語意。

六道宣稱有檢查而實際沒有的閘門現在是真的了。架構閘門是最有教育意義的一道：它的第一版比對 `deps.json` 的直接邊，**而在一個刻意製造的違規面前照樣是綠的。** SDK 會在 Build 之前把傳遞專案參考併進 `@(ProjectReference)`，所以程式碼可以 `using` 一個只是經傳遞進來的組件，而那條邊在 csproj 與 `deps.json` 上都不存在。`deps.json` 抓得到「宣告了卻沒用」，抓不到「用了卻沒宣告」。改用 `Assembly.GetReferencedAssemblies()` —— 編譯後 IL 真正參考了誰 —— 之後負向驗證才正確變紅。

## 變更

### 兩項效能變更，都經實測

寫入路徑從未設過 `UpdateBatchSize`，而 ADO.NET 的預設值是 1 —— 每一個異動列各一次 `ExecuteNonQuery`，也就是各一次 round trip。對本機 SQL Server 容器實測：100 列 INSERT 32 ms → 3 ms、500 列 INSERT 145 ms → 9 ms。作為對照，上一輪被判為雜訊的效能項是每請求 0.50 µs；這一項在一張 100 列明細的單據上比整條序列化管線還貴，而本機容器已經是最樂觀的情境。

支援與否以「問 adapter」偵測，因為 `DbDataAdapter` 基底的 setter 擲 `NotSupportedException` —— 所以問這件事*本身*就是檢查。硬寫一份 provider 清單會在兩個方向上出錯：provider 日後支援了它不會跟上，也管不到宿主實際為某個 `DatabaseType` 註冊了哪個 factory。上限取 100 而非 0（provider 能吃多少就多少）：收益幾乎全在「脫離逐列往返」，而有界可避免一次病態的大量存檔組出一個巨大命令。

這順帶關上一個覆蓋缺口。在此之前 adapter 寫入路徑的 DB 測試**只有 SQLite** —— 而它正是不支援批次的兩個之一 —— 也就是說批次實際生效的三個 provider 對這條路徑是零覆蓋。新增的測試守的是「批次不改變結果」（停用批次它仍全綠，那是刻意的：行為不變正是驗收條件），而支援度矩陣另由一組測試釘住，provider 哪天改了行為就會紅。

`ApiServiceController.ReadRequestAsync` 呼叫 `Request.EnableBuffering()`，把 body 包進超過 30 KB 就寫到暫存檔的 `FileBufferingReadStream`。而框架從來沒有把 body 倒回去讀過：全 repo 只有這一處讀 `Request.Body`，controller 也沒有 `[FromBody]` 參數 —— 進來時 body 本來就在位置 0，`EnableBuffering()` 與 `Position = 0` 兩行都不產生任何語意。每個超過 30 KB 的請求都為了一個沒有人使用的重繞能力付出一次磁碟往返，而 `params.value` 是 base64 的 gzip body（1.33× 膨脹），任何帶明細的存檔或取數都在門檻之上。完整 HTTP 往返、20 次平均：16 KB 0.15 → 0.14 ms、64 KB 0.46 → 0.22 ms、1 MB 2.81 → 1.28 ms、4 MB 9.51 → 4.76 ms。**16 KB 那列毫無差異，正是因果證明** —— 收益來自越過 30 KB 的 spill 門檻，而不是少了一份字串。

有一項行為差異值得寫明：只含空白字元的 body 現在回報 `ParseError` 而非 `InvalidRequest`。HTTP 狀態仍是 400，而「收到的不是合法 JSON」本來就是 `ParseError` 的語意。

### 一支稽核寫入器足以帶走整個部署

`AuditLogWriterService.ExecuteAsync` 只 catch `OperationCanceledException`。`_sink.WriteBatch` 逸出的任何其他例外會讓 `BackgroundService` 進入 Faulted，而 .NET 預設的 `BackgroundServiceExceptionBehavior.StopHost` 會停掉整個應用 —— **一次失敗的 log 寫入就能把部署帶走。** [ADR-017](../adr/adr-017-db-cache-invalidation.md) 早就為 `CacheNotifyPoller` 立下這條規則，而這支是唯一沒拿到的。

這個 catch 刻意不加過濾，而且刻意與姊妹服務不同。`CacheNotifyPoller` 與 `ExpiredSessionCleanupService` 呼叫的是框架內部程式碼，失敗型別列舉得出來；這一支呼叫的是 `IAuditLogSink` —— 公開的 DI 接縫，部署自訂的 sink 什麼都可能擲，框架沒有清單可寫。掉一批 log 記錄嚴格優於停掉整個應用，且失敗以 error 層級回報而非吞掉。類別 doc 原本宣稱「records are never silently lost」，那只對佇列飽和那條路成立，已一併更正。

### analyzer 出貨紀錄是空的，所以守它的規則永遠不可能觸發

`AnalyzerReleases.Shipped.md` 一行都沒有，而 analyzer 自 4.16.0 就隨 `Bee.Definition` 出貨。它依 tag 快照回填而非憑記憶：4.16.0 新增 22 條、4.18.0 新增 BEE3003、4.19.0 移除 BEE4001–BEE4004。

負向驗證證明這個盲點確實關上了：把一條已出貨規則（BEE1007）改掉 id 之後，RS2003 現在會擋 —— 「shipped in analyzer release '4.16.0', but is no longer a supported diagnostic」。`Shipped` 是空的時候這條規則永遠不可能觸發，那正是 BEE4001–BEE4004 在 4.19.0 悄悄退役而沒有任何東西出聲的原因。這份檔案現在與兩個 `PublicAPI` 檔並列，登記為發版的第三份基準。

### 239 處散文型別引用移到編譯器底下

`check-xmldoc-refs.sh` 的檔頭寫著「能改用 `<see cref>` 的就改用，讓編譯器接手」—— 但沒有任何機制在執行那句話。腳本驗的是「這個名字還存在嗎」，不驗「這裡本來就該用 cref」。散文裡的自家型別引用於是以 `<c>` 的形式愈積愈多，不受保護。

144 個檔中的 239 處已轉換，做法是拿編譯器當驗證器：全部轉成 cref 後 build，依編譯器回報的檔案與行號精準退回解不到的，迭代至收斂。不同 namespace 的型別改用完全限定名而非補 `using` —— 補 using 會觸發 IDE0005，而完全限定名一樣受編譯器把關。同專案內的殘留因此從 88 降到 26，其中 17 處是檔名（`Foo.xml`、`Bar.razor`），本來就該用 `<c>`。反向檢查現已納入該腳本。

那道檢查隨即抓到本輪體檢自己引入的四筆違規 —— 而它們之所以能活下來，是因為那支本來就擋得住的腳本，從來沒有被跑過。

## 修正

### 所有經 JSON-RPC 的 `AuditRule.*` 呼叫都擲例外

`AuditRuleBusinessObject` 只宣告三參數建構子，而 `BusinessObjectFactory` 固定以四個引數啟動。C# 建構子不繼承，於是每一個呼叫都映射為 `InternalError` —— 4.25.0 出貨的每表單稽核規則維護表單，從出貨那天起遠端就從未能用。

它唯一的測試直接建構該型別、從不走工廠，所以出貨時整套是綠的。`ReservedProgIdConstructionTests` 現在從兩個層次涵蓋它：走真實工廠一層、純反射一層（後者不需容器）。兩者都不硬編工廠的引數形狀 —— 反射版從 `BusinessObject` 基底的建構子推導。

### 全新部署的 cache-notify 基準落在未來

`CacheNotifyReader` 的空表基準自帶一份方言對照表、回的是本地時間（`getdate()`、`LOCALTIMESTAMP`、`CURRENT_TIMESTAMP(6)`），而每一列的 `sys_update_time` 都由寫入端戳 UTC —— 欄位 DEFAULT 與 `CacheNotifyService.BuildUpsertSpec` 都讀 `IDialectFactory.GetDefaultValueExpression`。五個方言中四個不一致，只有 SQLite 相符。這違反 [ADR-032](../adr/adr-032-datetime-timezone.md) D1：資料庫一律存 UTC、時區轉換在用戶端。

後果是：全新部署的第一個 poll 游標落在未來，之後每次 poll 的視窗都撈不到列。快取失效機制靜默停擺，直到牆鐘追上 —— UTC+8 就是八小時。

負向驗證時取得的活證據：Oracle 回 `15:18:34` 而 UTC 是 `07:18:34`。且 Oracle 的 `LOCALTIMESTAMP` 取的是**用戶端** session 的時區而非資料庫的，所以基準取決於哪台機器在跑 poller —— 比伺服器時區更糟。

一直沒被發現，是因為本機四個容器與 GitHub runner 全跑 UTC，兩式在那裡剛好相等。Oracle 是唯一會現形的方言，正是因為它看的是用戶端。

讀取端現在從寫入端的同一個來源取得該表達式，那份重複的方言表已刪除。兩份必須一致的對照表一定會漂，而這一份漂得無聲無息。閘門有兩層：表達式必須與寫入端完全相同（純邏輯 —— UTC 環境下兩式回值相等，比對表達式是唯一驗得到*基準*的方式），以及四個方言實跑該語句、驗回傳值貼近 UTC。

### sweep 可能淘汰一個正在使用的重放視窗

`MemoryReplayWindowStore` 在 `GetOrAdd` 建立項目之後才寫 `Entry.LastTouchedMs`，中間那段時間它是 0。落在那個空隙的 sweep 讀到 0、判定它比任何 cutoff 都舊，於是移除一個正在使用中的 window —— 該 session 接著拿到全新 window，重放防護被靜默重置一次。

閘門刻意用結構性斷言而非行為測試。這個 race 沒辦法用行為乾淨隔離：要撞到它得把淘汰期調到毫秒級，但在那個尺度下，執行緒被排程延遲超過淘汰期就是*合法*淘汰 —— 修正在位時測試三次紅一次。第一版更糟：那個並行測試在 bug 放回去之後仍然全綠，而那種測試比沒有更差。

### 序列化失敗是永久的，不是瞬時的

`XmlCodec.Serialize` 與 `JsonCodec.SerializeCore` 都寫成一條直線：`NotifyBefore` → 序列化 → `NotifyAfter`。序列化擲例外時最後一步永遠不會執行，物件就**永久**停在 `SerializeState.Serialize`。

「永久」是重點。被序列化的往往是 process-wide 的快取定義實例 —— `SerializeDefine` 有六個呼叫點作用於快取物件。一次失敗之後，該實例的所有空集合 getter 從此回 `null`（`IsSerializeEmpty` 只在 `Serialize` 狀態下成立），而數個呼叫端以 `!` 解參考它們。空集合本來就是完全正常的狀態 —— 例如沒有索引的資料表。瞬時的失敗被轉成了永久的失敗。

修法是用 scope 而不是在兩處各加 `try`/`finally`：「`NotifyBefore` 必須配對 `NotifyAfter`」正是適合結構性保證的不變式，而重複兩次的同一種形狀就是會分岔的形狀。`SerializationLifecycle.BeginSerialize` 回傳一個 `readonly struct` scope，`using` 在具體型別上不產生配置。

### Blazor head 的 NOT NULL 欄位收到 `DBNull`

比對兩個 head 各自的私有副本後發現，五個 helper 中三個逐字相同、兩個已漂。其中一個是活的 bug：Avalonia head 早已修好「`DefaultValue` 仍是 `DBNull` 的 NOT NULL 欄位不可回 `DBNull`」—— 否則 `EndEdit` 會擲 `NoNullAllowedException` —— 而 Blazor 的副本還帶著它。原始 ADO.NET column 正是伺服器回應的常態形狀，所以這不是邊角情境。把共用實作下沉順帶把修正帶了過去。

### `ClientInfo` 的單一使用者限制寫明了，延遲初始化也有了保護

`ClientInfo` 以 process-wide 靜態持有**一個**登入使用者的狀態：access token、capability 快照、已進入的公司，以及帶該使用者 tenant 客製化的定義快取。對桌面 head 是正確的 —— 一個 process 一個使用者 —— 對服務多個使用者的 host 則是錯的：每個 session 寫同一組欄位，最後登入的贏，先前的使用者讀到別人的身分。

這是既定限制而非疏漏，但**型別系統上沒有任何東西標記這條邊界**，於是以本套件建的 server-side UI head 會靜默繼承這個缺陷。`Bee.Api.Client` 已經走過同一遭 —— per-user 靜態移到 `ApiSessionContext`，每 session 一份 —— 對照組就在旁邊，卻只有這裡沒有警語。它現在帶著與 `ApiSessionContext` 對等的 WARNING，隨 NuGet 進消費端 IntelliSense。

三處 `??=` 延遲初始化也有了保護。那些 getter 會同時被 UI 執行緒與 `ConfigureAwait(false)` 續行進入，兩條執行緒可能各建一個實例。浪費的那個不是問題，**孤兒才是** —— `ResetDefineCache` 清掉的是它手上那個，而呼叫端繼續用另一個，於是切換租戶時舊的客製化定義還留著。刻意不用 `Lazy<T>`：這些是*可重設的*，換掉整個 `Lazy` 實例只是把競態搬家。

### 定義層 README 的五處失實宣稱

體檢回報的是兩行；同一份 README 有五處已出貨改動造成的漂移，而只修兩處會製造已經修好的錯覺。

相依清單仍列著 MessagePack，而它在 4.19.0 就移除了 —— 這句話直接推翻 [ADR-036](../adr/adr-036-wire-serialization-externalized.md) 與 [ADR-038](../adr/adr-038-definition-dependency-boundary.md) 的核心結論，而且出現在外部開發者的第一手讀物裡。另一處宣稱「no business logic and no I/O」，而定義層現有 7 個檔、1,121 行的檔案 IO。後者不是「還沒更新」，是主動否認一個已知且被記錄兩輪的架構問題。既然把 IO 搬離定義層仍維持遞延，敘述改為陳述現況並說明它為何還在：`BackendDefaultTypes.DefineStorage` 的型別名寫在每個既有部署的 `SystemSettings.xml` 裡，搬家必須配套舊型別名的相容對映 —— 屬資料遷移而非重構。刻意不只是刪掉「no I/O」三個字：留下的敘述仍會讀成保證。

## 升級

多數部署不需要任何改動。六件事值得看一下：

- **透過契約介面取用集合成員。** `ISaveResponse.AffectedRows` 與 `IEnterCompanyResponse.Capabilities` 現在是 `IReadOnlyDictionary`。透過具象的 `SaveResponse` / `SaveResult` 取用不受影響；只有經介面而宣告為 `Dictionary<,>` 的地方需要改。
- **直接建構 BO。** 若程式碼依賴本機路徑，就明講：`new SystemBusinessObject(sessionInfo, isLocalCall: true)`。否則四道第二線守衛此後會生效 —— 而那正是本次變更的重點。注意已編譯的組件會維持舊的預設值，直到重新編譯為止。
- **`HttpUtilities`** 由 `Bee.Base` 搬到 `Bee.Api.Client`。改一行 `using`；呼叫寫法不變。
- **`System.CheckPackageUpdate` 與 `System.GetPackage` 已不存在。** 實作過任一擴充點的宿主應移除該覆寫。沒有替代品，而它本來就沒有呼叫者。
- **跨語言 client 讀 `DataTable` 儲存格**時，必須能接受 `decimal`、`long`、`ulong` 為帶引號的 JSON 字串。它的寫入端不需要改 —— 讀取端仍接受裸數字，所以依 4.27.0 fixtures 實作的 client 在那個方向上仍可運作。
- **兩項要往下游檢查的行為變更。** 自行算好密碼雜湊、經 FormSchema 資料路徑寫入 `st_user.password` 的部署，此後會被 `RemoveProtectedFields` 擋下；框架自己沒有任何寫入該欄的路徑。以及，未進入公司就發出的稽核記錄查詢，此後回傳空結果而不是所有租戶的記錄。

欄位說明或預設值含反斜線的 MySQL 部署，先前根本升級不了（產生的 DDL 是語法錯誤），此後會正確寫入 —— 前提是伺服器的預設 `sql_mode`，不含 `NO_BACKSLASH_ESCAPES`。
